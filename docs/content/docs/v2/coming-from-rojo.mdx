If you use Rojo with `server`, `client` and `shared` folders, `rogen init` keeps your tree. It reads the `default.project.json` you wrote, lifts it into a `rogen.json`, and turns the folders it points at into routes that put each one where Rojo had it:

```json title="default.project.json"
{
	"name": "my-game",
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": { "Shared": { "$path": "src/shared" } },
		"ServerScriptService": { "Server": { "$path": "src/server" } },
		"StarterPlayer": {
			"StarterPlayerScripts": { "Client": { "$path": "src/client" } }
		}
	}
}
```

<Steps>

<Step>
### Run `rogen init`

```bash
rogen init
```

`init` moves the project file's keys into `rogen.json`, since Rogen owns `default.project.json` from now on, and leaves out the nodes that point into `src`: Rogen generates those. Each one becomes a route:

```json title="rogen.json"
{
	"name": "my-game",
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": {},
		"ServerScriptService": {},
		"StarterPlayer": { "StarterPlayerScripts": {} }
	},
	"sourcePaths": ["src"],
	"routes": {
		"Shared": "ReplicatedStorage/Shared",
		"Server": "ServerScriptService/Server",
		"Client": "StarterPlayer/StarterPlayerScripts/Client",
		"*": "ReplicatedStorage/Shared"
	}
}
```

- A mount of a folder directly in a source path (`src/server`) becomes a route named after the folder, to the node's path. The key matches with its first letter in either case, so `server/` and `Server/` both route.
- A mount of a source path itself (`"ReplicatedStorage/Common": { "$path": "src" }`) becomes the `*` route, which takes files that match no route. Otherwise `*` goes where the `shared` folder went.
- A mount deeper down (`src/server/Admin`) can't be a route. `init` says so, and it needs a marker such as `Admin@server`, or a move. If the node carried settings, `init` keeps it as a `$path` mount in the tree instead.
- A mount whose folder holds an `init` file (`init.server.luau`, as `rojo init` writes for `src/server`, or `init.meta.json`) stays a `$path` mount in the tree. Rojo reads such a folder as one instance, a Script or whatever its init file makes, and a route can't make that. Rogen leaves the folder to Rojo, as it does for any `$path` into a source path.
- What a mount carried besides its `$path` (`$properties`, `$attributes`, `$className`, `$ignoreUnknownInstances`, `$id` and child nodes) stays on its node in the `tree`, where the route lands, and the file builds the instances it did. A node no route can land on gets the warning [`init.settingsDropped`](/docs/v2/diagnostics#init-settingsdropped) and is left out.
- A project file whose root is not a DataModel, such as the `$path: "src"` that `rojo init --kind model` and `--kind plugin` write, is lifted as it is, with no `routes` and no `sourcePaths`: there is no service to route to, so Rojo keeps reading the folder.

In a terminal, the **Routes** question offers these routes ticked, with the hint `from default.project.json`, beside the standard ones. With `--non-interactive` or `--json`, `init` takes them.

</Step>

<Step>
### Compare

`init` has already built `default.project.json` from the config, so ask where the files land:

```bash
rogen where src
```

`where` lists every file with the instance it lands at, which should be the node Rojo gave it: `src/server/Main.server.luau` at `ServerScriptService/Server/Main`, and so on. `git diff default.project.json` won't show it, because Rogen writes each file as its own node, so the file differs even when nothing moved.

</Step>

<Step>
### Move one feature

Now you can move code into [feature folders](/docs/v2/architectures/feature-folders) a folder at a time. Move one feature, then ask where its files land:

```bash
rogen where src/Inventory
```

`where` prints each file's instance path and the `require` that reaches it. When a folder's routes are right, move the next one.

</Step>

</Steps>

Already-written requires keep working while you move, because a file's instance path only changes when its route does. See [Routing](/docs/v2/core-concepts/routing) for the rest of the rules, and [Requires](/docs/v2/core-concepts/requires) for reaching code that runs somewhere else.

## By Hand

`rogen.json` is your project file with more keys, so the move is a rename and an addition. `rogen init` does the same, and also reads your folders for the routes.

```bash
git mv default.project.json rogen.json
```

Every Rojo key (`name`, `tree`, `servePort`, `globIgnorePaths`, `syncRules` and the rest) keeps its meaning. With no `routes`, `rogen build` writes the file back as `default.project.json`, tree untouched, and only warns, naming `rogen init`, when `src` holds files the tree doesn't mount. Add the routes when you want Rogen to place files by their folders:

```json title="rogen.json"
{
	"name": "my-game",
	"tree": { "$className": "DataModel" },
	"routes": {
		"Server": "ServerScriptService",
		"Client": "StarterPlayer/StarterPlayerScripts",
		"Shared": "ReplicatedStorage/Shared",
		"*": "ReplicatedStorage/Shared"
	}
}
```

A node you keep in the `tree` wins over a generated one on a clash, with a warning, and a `$path` into a source path stays Rojo's own: Rogen skips that folder. Rojo's `fmt-project` can't read the file, so run `rogen fmt-project` to format it as Rojo formats a project file. Rogen reads `rogen.jsonc` too, since Rojo 7.7 allows comments in a project file.

## Rojo's Other Commands

Rogen replaces the project file you wrote, and Rojo's commands that read it keep working on the one Rogen writes. Your `rogen.json` is that file with more keys (`sourcePaths`, `routes`, `syncPath`, `projects`, `serveProject` and `placePaths`), so Rojo's own keys (`servePort`, `servePlaceIds`, `globIgnorePaths` and the rest) work in it as they did.

- **`rojo serve`** still serves the project file. `rogen serve` builds it first, starts the server for you and rebuilds as files change; see [Studio](/docs/v2/studio) for the plugin settings.
- **`rojo build`** makes a place file from it. `rogen build -o game.rbxl` writes the project files and runs it for you: see [Place Files](/docs/v2/core-concepts/output#place-files).
- **`rojo sourcemap`** works on it as it does on any project file, for luau-lsp and other tools. `rogen sourcemap` writes the project files first and then runs it, and in a root with places writes a `sourcemap.json` for each: see [`sourcemap`](/docs/v2/cli#sourcemap-project).
- **`rojo upload`** uploads it. `rogen upload` writes the project files first and then runs it, with Rojo's flags as Rojo spells them: see [`upload`](/docs/v2/cli#upload-project).
- **`rojo plugin install`** installs Rojo's Studio plugin. `rogen plugin install` has the Rojo your project pins do it, so the plugin matches the server `rogen serve` starts: see [`plugin`](/docs/v2/cli#plugin-install-and-plugin-uninstall).
- **`rojo syncback`** reads the project file's tree to decide where Studio's changes go, and can edit properties in the file it reads, which Rogen overwrites on its next build. Don't run it against a project file Rogen writes. Bring changes from a place back into the feature folders by hand.
