Rogen covers what `rojo` does for a project: `init`, `build`, `serve`, `sourcemap`, `upload`, `plugin`, `syncback` and `fmt-project`. A `default.rogen.json` is a project file with Rogen's keys beside Rojo's, so Rojo's keys keep their meaning.

What changes for a Rojo user:

- **The project file is Rogen's.** You edit `default.rogen.json`, and every write rewrites `default.project.json` from it. See [The Move](#the-move).
- **Files are placed by folder and name.** What differs once Rogen routes your files is [one table](#where-rogen-reads-a-layout-differently).
- **Nothing has to move first.** A folder with only a `default.project.json`, or a project file you name (`rogen build test.project.json -o test.rbxl`), runs under Rogen's commands as it is. See [Rojo's Other Commands](#rojos-other-commands).

Three differences from `rojo` remain on purpose:

- `syncback` without `-y` and without a terminal exits 2. Rojo asks, reads nothing, and exits 0 having written nothing.
- `syncback --list` leaves out the colour codes Rojo prints.
- `serve` calls every client of the server's websocket Studio, since Rojo's log doesn't name the client.

Rogen picks a file the way Rojo does: a bare command reads the current folder only, and `serve`, `build`, `sourcemap` and `upload` take one project. `build -o`, `serve`, `sourcemap`, `upload`, `plugin` and `syncback` take Rojo's flags, and `fmt-project` formats the config.

`init` takes `--kind place|model|plugin`, `--skip-git` and a folder to start in, as `rojo init` does, and a model or a plugin starts with Rojo's template. A new place starts with Rogen's version of Rojo's sample (three hello-world scripts in a `Greeter` feature folder with `Shared`, `Server` and `Client` folders, and the Baseplate, Lighting and SoundService as Rojo files in `place`, which the tree mounts), or with `--no-sample` an empty `src`.

## The Move

The move is one step: rename your project file and add `routes`.

```bash
git mv default.project.json default.rogen.json
```

Every Rojo key (`name`, `tree`, `servePort`, `globIgnorePaths`, `syncRules` and the rest) keeps its meaning. With no `routes`, `rogen write` writes the file back as `default.project.json`, tree untouched, and only warns ([`scan.unmountedSource`](/docs/v2/diagnostics#scan-unmountedsource)) when `src` holds files the tree doesn't mount, saying to add `routes` to place them or to mount the folder with `$path`. Add `routes` when you want Rogen to place files by their folders:

```json title="default.rogen.json"
{
	"name": "my-game",
	"routes": {
		"Server": "ServerScriptService",
		"Client": "StarterPlayer/StarterPlayerScripts",
		"Shared": "ReplicatedStorage/Shared"
	},
	"tree": { "$className": "DataModel" }
}
```

A node you keep in the `tree` wins over a generated one on a clash, with a warning, and a `$path` into a source path stays Rojo's own: Rogen skips that folder. Rojo's `fmt-project` can't read the file, so run `rogen fmt-project` to format it as Rojo formats a project file. Rojo writes the numbers of `$properties` and `$attributes` as floats (`0.0`), by the type of each; Rogen keeps them as you wrote them, and it won't format a file with comments, where Rojo drops them. Rogen reads `default.rogen.jsonc` too, as Rojo 7.7 reads `default.project.jsonc`.

Run `rogen write`: Rogen now owns `default.project.json` and rewrites it. Your repository still tracks the file you renamed, so decide what to do with it:

- **Stop tracking it.** `git rm --cached default.project.json`, and keep `*.project.json` in `.gitignore` (`init` adds the line). A clone then runs `rogen write` before the editor or a compiler needs the file.
- **Keep it tracked.** Commit what `rogen write` writes, and add `!default.project.json` below `*.project.json` if you ignore the pattern. People without Rogen can then run `rojo serve` on it as they did. Rerun `rogen write` before each commit: see [The project file is as fresh as its last write](/docs/v2/core-concepts/output#the-project-file-is-as-fresh-as-its-last-write).

## Let `init` Read Your Folders

If you use Rojo with `server`, `client` and `shared` folders, `rogen init` does the move and keeps your tree. It reads the `default.project.json` you wrote, lifts it into a `default.rogen.json`, and turns the folders it points at into routes that put each one where Rojo had it:

```json title="default.project.json"
{
	"name": "my-game",
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": { "Shared": { "$path": "src/shared" } },
		"ServerScriptService": { "Server": { "$path": "src/server" } },
		"StarterPlayer": {
			"StarterPlayerScripts": { "Client": { "$path": "src/client" } }
		}
	}
}
```

<Steps>

<Step>
### Run `rogen init`

```bash
rogen init
```

`init` moves the project file's keys into `default.rogen.json`, since Rogen owns `default.project.json` from now on, and keeps your values as you wrote them: the Baseplate of `rojo init` stays `512`, not `512.0`. It leaves out the nodes that point into `src`: Rogen generates those. Each one becomes a route:

```json title="default.rogen.json"
{
	"name": "my-game",
	"sourcePaths": ["src"],
	"routes": {
		"Shared": "ReplicatedStorage/Shared",
		"Server": "ServerScriptService/Server",
		"Client": "StarterPlayer/StarterPlayerScripts/Client"
	},
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": {},
		"ServerScriptService": {},
		"StarterPlayer": { "StarterPlayerScripts": {} }
	}
}
```

- A mount of a folder directly in a source path (`src/server`) becomes a route named after the folder, to the node's path. The key matches with its first letter in either case, so `server/` and `Server/` both route.
- A mount of a source path itself (`"ReplicatedStorage/Common": { "$path": "src" }`) becomes the `*` route, which takes files that match no route, as the mount held them. Otherwise `init` writes no `*`, as Rojo synced no file outside a `$path`; `--unmatched shared` sends such files where the `shared` folder went.
- A mount no route can make stays a `$path` mount in the tree, which builds exactly as Rojo built it, and `init` says why: a mount deeper down (`src/server/Admin`), a folder name that is no route name (`my-lib`, `2fast`, `Game Code`), a folder mounted twice, or a name another mount took. A folder with its own `default.project.json` mounts as the nested project it is. Rogen skips what the tree mounts, so the folder is only there. Move such a folder up into a source path, or put a marker file in it, such as `Admin/@server`, when you want routing to place it.
- A mount whose folder holds an `init` file (`init.server.luau`, as `rojo init` writes for `src/server`, or `init.meta.json`) stays a `$path` mount in the tree. Rojo reads such a folder as one instance, a Script or whatever its init file makes, and a route can't make that. Rogen leaves the folder to Rojo, as it does for any `$path` into a source path.
- What a mount carried besides its `$path` (`$properties`, `$attributes`, `$className`, `$ignoreUnknownInstances`, `$id` and child nodes) stays on its node in the `tree`, where the route lands, and the file makes the instances it did. A node no route can land on gets the warning [`init.settingsDropped`](/docs/v2/diagnostics#init-settingsdropped) and is left out.
- A project file whose root is not a DataModel, such as the `$path: "src"` that `rojo init --kind model` and `--kind plugin` write, is lifted as it is, with no `routes` and no `sourcePaths`: there is no service to route to, so Rojo keeps reading the folder.

- Files in a source folder that no node mounted (`src/Loose.luau`) were ignored by Rojo. A route that matches one places it, such as the `.server` suffix of `src/scratch/x.server.luau`; the others stay out, each with a [`route.unrouted`](/docs/v2/diagnostics#route-unrouted) warning. `init` lists them with [`init.unmountedFiles`](/docs/v2/diagnostics#init-unmountedfiles); list them under `globIgnorePaths` to leave them all out, silently, as Rojo did.

- Any other `*.project.json` in the folder (`test.project.json`, `place.project.json`) is not lifted and stays as you wrote it. `init` lists them as left alone, and `rogen build test.project.json -o test.rbxl` builds one as a plain Rojo project. To have Rogen write one, make it a complete `test.rogen.json`; see [More Files](/docs/v2/configuration#more-files). The `*.project.json` line `init` adds to `.gitignore` covers these files too, so add `!test.project.json` to keep one tracked.

`init` writes `default.project.json` at once, and `git diff default.project.json` then shows a full rewrite even when nothing moved: Rogen writes the file in Rojo's format, marks each `$path` as `optional`, and writes a node for each file a folder mount doesn't cover. Compare the instances with `rogen where` (next step), not the diff.

In a terminal, the **Routes** question offers these routes ticked, with the hint `from default.project.json`, beside the standard ones. With `--non-interactive` or `--json`, `init` takes them.

</Step>

<Step>
### Compare

`init` has already written `default.project.json` from the config, so ask where the files land:

```bash
rogen where src
```

`where` lists every file with the instance it lands at, which should be the node Rojo gave it: `src/server/Main.server.luau` at `ServerScriptService/Server/Main`, and so on.

</Step>

<Step>
### Reorganise on a branch

The project now builds as it did, and you can move code into [feature folders](/docs/v2/architectures/feature-folders). Do it on a branch, since moving a file changes its instance path.

A file lands at its route's target followed by every folder above it, so a feature folder adds a segment, and a type folder you leave behind (`Services`, `Controllers`, `Utils`) drops one:

```
before   src/server/Services/InventoryService.luau   ->  ServerScriptService/Server/Services/InventoryService
after    src/Inventory/Server/InventoryService.luau  ->  ServerScriptService/Server/Inventory/InventoryService
```

Every `require` that reached the file by instance path now points at nothing, and Rogen doesn't check requires, so a broken one shows up when the game runs. Move a feature, ask where its files land, and update the requires that reach them:

```bash
rogen where --verbose src/Inventory
```

`where` prints each file's instance path, and `--verbose` adds the `require` that reaches each module. A file you name gets its `require` without the flag. When the requires are right, move the next feature.

Hiding a folder with `(Name)/`, or a file with a `^` prefix, drops folders from the path (see [Hoisted Names](/docs/v2/core-concepts/routing#hoisted-names)). It keeps a path only when the folder you add is the only difference, which a by-type layout rarely allows. Plan to update the requires.

</Step>

</Steps>

Old folders and feature folders build together, so the project keeps building between moves. See [Routing](/docs/v2/core-concepts/routing) for the rest of the rules, and [Requires](/docs/v2/core-concepts/requires) for reaching code that runs somewhere else.

After `init`, `rogen serve` replaces `rojo serve`: it writes `default.project.json`, starts the Rojo your project pins on it and writes again as files change, so you no longer start Rojo yourself. For luau-lsp, which wants a `sourcemap.json`, run `rogen sourcemap --watch -o sourcemap.json` beside it; it writes the project file first and keeps the sourcemap current as files come and go.

## Going Back

`init` changes three things, and each is undone on its own. Nothing outside them is touched.

- **The project file.** Rogen replaced `default.project.json`, and the one you wrote is in git: `git checkout default.project.json` restores it. `init` moved its keys into `default.rogen.json`, so remove `default.rogen.json` too, and Rogen no longer writes anything.
- **The files `init` added.** `AGENTS.md`, `.gitignore` when there was none, and `CLAUDE.md` when `.claude/` was there are new files; remove the ones you don't want. A hook it registered is an entry in the agent's own settings file, and `.agents/hooks/rogen-check.mjs`.
- **Your source.** Routing never renames or moves a file, so a source folder you haven't reorganised is as it was.

Once you have moved to feature folders, the way back is the file Rogen wrote. `default.project.json` is a complete Rojo project, so commit it (add `!default.project.json` if `.gitignore` lists `*.project.json`), delete the `.rogen.json` files, and `rojo serve` and `rojo build` run on it as they are. It lists a `$path` for each folder routing placed whole and for each file it placed apart, so a file you add later reaches it only when its folder is mounted whole, or when you add its node; rerun `rogen write` before you commit it.

## Where Rogen Reads a Layout Differently

In a folder Rogen routes, these differ from what Rojo does with the same files. Everything outside `routes` and `sourcePaths` is Rojo's.

| Rojo | Rogen | What to do |
| --- | --- | --- |
| Files in a source folder that no node mounts are ignored. | Routes place every file below a source path. | `init` lists them ([`init.unmountedFiles`](/docs/v2/diagnostics#init-unmountedfiles)); list them under `globIgnorePaths`. |
| A node that mounts the source path itself holds all of it, `src/server` included. | The mount becomes the `*` route, and the other routes place their folders. | `init` warns ([`init.mountNarrowed`](/docs/v2/diagnostics#init-mountnarrowed)); point those requires at the folder's own node. |
| A folder holding `init.server.luau` or `init.meta.json` is one instance. | The mount stays in the tree and is Rojo's own. | Nothing; `init` says so. |
| A mount in a folder a route covers is also a child of that folder's instance. | The mount is only in the tree: Rogen skips what the tree mounts. | Nothing. |
| `.client` files are Scripts with a RunContext under `emitLegacyScripts: false`. | A route to `StarterPlayerScripts` keeps them LocalScripts with a sync rule. | See [Configuration](/docs/v2/configuration#fields). |
| `Dup.luau`, `Dup.lua` and `Dup.txt` in one folder are three instances. | They are one instance: the last file wins and the others are left out. | Rename the files; [`tree.instanceClash`](/docs/v2/diagnostics#tree-instanceclash) names them. |
| `(Group)/`, `^Hoist.luau` and `Foo@server.luau` are names. | They are routing sigils. | Rename the file, or put it where the tree mounts it. |
| A glob in `globIgnorePaths` that ends in `/**` and names a mounted folder empties the Folder. | The mount is left out of the written file. | None needed; documented in [Configuration](/docs/v2/configuration#fields). |
| A glob starting with `/` or `./` matches nothing. | It is read from the config's folder. | Write globs as Rojo reads them. |
| The project file you wrote. | A folder every file of which routing places under one node is one `$path` mount; any other file is a node of its own. Each `$path` is marked `optional`. | A file added to a mounted folder reaches plain `rojo serve` and `rojo sourcemap` at once; any other waits for the next `rogen write`. |

## Rojo's Other Commands

In a folder with a `default.project.json` and no `default.rogen.json`, Rogen's commands run on the project file as it is: `rogen sourcemap`, `rogen serve` and `rogen build -o game.rbxl` do what `rojo` does there, `check` and `where` read the tree, and `write` lists the project file and leaves it alone. So `rogen` can stand in for `rojo` in a Rojo repo you have not moved, and `rogen init` moves it when you want routes.

Rogen replaces the project file you wrote, and Rojo's commands that read it keep working on the one Rogen writes. Your `default.rogen.json` is that file plus Rogen's keys (`sourcePaths`, `routes` and `compiledPath`), so Rojo's own keys (`servePort`, `servePlaceIds`, `globIgnorePaths` and the rest) work in it as they did.

- **`rojo serve`** still serves the project file. `rogen serve` writes it first, starts the server for you and writes again as files change; see [Studio](/docs/v2/studio) for the plugin settings.
- **`rojo build`** makes a place or model file from it, and needs `--output` or `--plugin`; its `--watch` rebuilds as files change. `rogen build -o game.rbxl` writes the project file and runs it for you, and needs `-o` or `-p` as well; `rogen build --watch` writes the project file and rebuilds as files change. `rogen write` writes the project file alone. See [Place Files](/docs/v2/core-concepts/output#place-files).
- **`rojo sourcemap`** works on it as it does on any project file, for luau-lsp and other tools. `rogen sourcemap` writes the project file first and then runs it: see [`sourcemap`](/docs/v2/cli#sourcemap-project).
- **`rojo upload`** uploads it. `rogen upload` writes the project file first and then runs it, with Rojo's flags as Rojo spells them: see [`upload`](/docs/v2/cli#upload-project).
- **`rojo plugin install`** installs Rojo's Studio plugin. `rogen plugin install` has the Rojo your project pins do it, so the plugin matches the server `rogen serve` starts: see [`plugin`](/docs/v2/cli#plugin-install-and-plugin-uninstall).
- **`rojo syncback`** reads the project file's tree to decide where Studio's changes go, and Rogen's file holds a node per file and per mounted folder, so Rojo can't add to it and can edit properties in the file it reads, which Rogen overwrites on its next write. `rogen syncback` runs it on a mirror of your files laid out as the game is, and writes each change back to the file it came from, the properties and attributes of your `tree`'s nodes into the `tree`: see [`syncback`](/docs/v2/cli#syncback). Every layout takes edits, additions and deletions, and a new instance is put where routing would place a file for it, written like the code around it.
- **`rojo fmt-project`** formats a project file. `rogen fmt-project` formats a `.rogen.json` the same way, byte for byte on Rojo's own build tests: floats as `1.0`, a nameless `default` file named for its folder, and the keys of a sync rule in Rojo's order. The project files `rogen write` writes are in that format, and keep no `$schema`; a plain Rojo project that Rogen runs on is not rewritten.

What a script sees of these commands matches `rojo`: stdout carries Rojo's own lines, Rogen's go to stderr, `-o=game.rbxl` works, `-v` reaches Rojo, a project that can't be found exits 1 and Rojo's argument errors exit 2, and `serve` exits 130 after Ctrl+C.
