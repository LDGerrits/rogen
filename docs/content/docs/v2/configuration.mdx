A folder's **config** is `rogen.json` (or `rogen.jsonc`), a Rojo project file with more keys: `sourcePaths` says where your code is, `routes` where it goes, `syncPath` where Rojo reads it from, and `projects` which other project files to write from the same description. Rojo's own keys keep their meaning, and Rogen writes them to `default.project.json` beside the config. Comments and trailing commas are fine.

A command given no folder reads the `rogen.json` of the working directory, or of the nearest folder above it that has one. Give it a folder with a `rogen.json`, the path to one of that folder's project files, or the name of one of its [projects](#projects), to read another: `rogen build game`. All paths in a config are relative to the config's folder, while paths on the command line are relative to the working directory.

A folder with a `default.project.json` and no `rogen.json` anywhere above it is read as a config whose output is itself: `check`, `build`, `list`, `where`, `sourcemap`, `serve`, `upload` and `fmt-project` run on a plain Rojo project, and Rogen writes nothing to the file. A `rogen.json` above wins, so a package folder inside a Rogen project is still part of it.

## Fields

Rogen's keys:

| Field | Default | What it does |
|---|---|---|
| `sourcePaths` | `["src"]` when `routes` exist | The folders to scan and watch. They merge into one tree, and the later one wins a clash. See [Several Source Paths](/docs/v2/core-concepts/project-layout#several-source-paths). Without `routes` it is an error. |
| `routes` | none | Route keys and their targets, like `"Service/Folder"`. Only declared keys route. Without it, nothing is routed and no source path is scanned. See [Routing](/docs/v2/core-concepts/routing). |
| `syncPath` | none | The folder Rojo syncs from, usually your compiler's output. See [Sync Path](/docs/v2/core-concepts/output#sync-path). |
| `projects` | none | Other project files to write, each the description with some keys changed. See [Projects](#projects). |
| `serveProject` | `default` | The project `rogen serve` serves. See [Projects](#projects). |
| `placePaths` | none | Folder globs that make each matching folder a place. See [Places](#places). |

Rojo's keys. Rogen passes each to the project file as it is, except `globIgnorePaths` and `syncRules`, which it also reads. [Rojo's project format](https://rojo.space/docs/v7/project-format/) documents all of them; this table says only what Rogen does with each:

| Field | What it does |
|---|---|
| `$schema` | The published JSON schema, for editor validation and completion. It covers Rojo's keys and Rogen's, underlines a route key that isn't letters and digits and a route target that doesn't start with a service, and offers the common targets as completions. |
| `name` | The project's name. The project file carries it only when you set one here; Rojo names the project after its folder otherwise. |
| `tree` | The instance tree Rogen merges its generated nodes into. See [Tree](#tree). |
| `globIgnorePaths` | Globs, relative to the config, of files Rojo ignores. Rogen keeps them out of routing too. See [Ignoring Files](#ignoring-files). |
| `syncRules` | How a file name becomes an instance, in front of Rojo's own rules. Rogen reads files by them too. See [Sync Rules](#sync-rules). |
| `servePort`, `serveAddress`, `serveAllowedHosts` | Where `rojo serve` listens. See [`serve`](/docs/v2/cli#serve). |
| `servePlaceIds`, `blockedPlaceIds`, `placeId`, `gameId` | Which places may connect, and the ones a place file is published to. See [Studio](/docs/v2/studio#place-ids). |
| `emitLegacyScripts` | Whether Rojo makes `Script` and `LocalScript` instances for `.server` and `.client` files, rather than a run context. |
| `syncbackRules` | Rojo's syncback rules. |

A key that is on neither list passes through with a warning, since Rojo will reject the written file by that name ([`config.unknownField`](/docs/v2/diagnostics#config-unknownfield)). A wrong type is an error.

## Projects

A **project** is the description with some keys changed, written beside `default.project.json` as `<name>.project.json`. Use one when the same code needs a second project file: a Darklua build that Studio reads while your editor reads the source, a release without the dev packages, a test place.

```json title="rogen.json"
{
	"name": "Game",
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": { "DevPackages": { "$path": "DevPackages" } }
	},
	"sourcePaths": ["src", "dev"],
	"routes": { "server": "ServerScriptService", "*": "ReplicatedStorage" },
	"serveProject": "dist",
	"projects": {
		"dist": { "syncPath": "dist" },
		"release": {
			"sourcePaths": ["src"],
			"globIgnorePaths": ["DevPackages/**", "**/*.spec.luau"]
		}
	}
}
```

This writes `default.project.json`, `dist.project.json` and `release.project.json`. A project may change any key of the description, Rojo's keys included:

- A value replaces the inherited one, and a list replaces the list: `"sourcePaths": ["src"]` in `release` leaves the `dev` overlay out.
- `routes`, `tree` and the nodes below it merge by key, so a project restates only what changes.
- A project leaves a mount out with `globIgnorePaths`, which replaces the list: `"DevPackages/**"` in `release` drops the `DevPackages` mount from `release.project.json`. See [Ignoring Files](#ignoring-files). A key can't be removed, and `null` is an error anywhere in a `rogen.json`.
- `projects` and `serveProject` belong to the whole config, and a project can't set them. `default` is the description itself and can't be a project name.
- A project inherits `name`. Every project file carries a `name`, yours or the folder's, because Rojo can't open a project file without one. Only `default.project.json` may go without, as Rojo names it after its folder.

**A test or subset project.** A project adds and replaces; it can't take a service or a node out of the inherited `tree`. To write a smaller project, keep the top-level `tree` to what every project needs, and give each project the rest: its own `sourcePaths`, its mounts under `tree`, and `globIgnorePaths` for the mounts and specs it leaves out.

```json title="rogen.json"
{
	"tree": { "$className": "DataModel" },
	"sourcePaths": ["src"],
	"routes": { "server": "ServerScriptService", "*": "ReplicatedStorage" },
	"projects": {
		"test": {
			"sourcePaths": ["src", "tests"],
			"tree": { "ReplicatedStorage": { "TestEZ": { "$path": "Packages/TestEZ" } } }
		}
	}
}
```

Rogen writes only `default.project.json` and the files its `projects` name. A `test.project.json` you wrote by hand stays as it is: `rogen build test.project.json` fails with "No project" until `test` is a key of `projects`, and `rogen init` lists such files as left alone. The other way holds too: when you delete a key from `projects`, Rogen does not delete the file it wrote, and Rojo still builds it. Delete the file with the entry.

`rogen serve` serves the project `serveProject` names, `default` when it is not set, so a Darklua setup that serves `dist` never serves unprocessed code by accident. Every other command reads `default`. To use another, give its name or its file: `rogen serve release`, `rogen serve dist.project.json`. A bare name means a project of the config here, unless a folder of that name holds a `rogen.json` or a `default.project.json`: the folder wins, and Rogen says which project file to name instead. `rogen build` writes every project whichever you name, and `rogen list` shows each one's file and which is served.

## Places

A repository with several places puts what they share in a root `rogen.json` and lists the places' folders in `placePaths`:

```json title="rogen.json"
{
	"name": "Game",
	"placePaths": ["places/*"],
	"routes": { "server": "ServerScriptService", "*": "ReplicatedStorage" },
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": { "Packages": { "$path": "Packages" } }
	}
}
```

Each folder that matches is a **place**. It inherits the root's keys and projects, adds its own code, and gets its own project files in its own folder, so an editor that starts one language server per folder gets one sourcemap per place. The [Several Places guide](/docs/v2/setups/places) walks through it. A place needs no config: a folder with no `rogen.json` is a place named after the folder. A place's `rogen.json` holds what differs, and is applied over the root's:

```json title="places/lobby/rogen.json"
{ "name": "Lobby", "servePort": 34880 }
```

- A place's `sourcePaths` are its own folders, relative to its folder (default `["src"]`), and Rogen adds them after the root's. The root's list is never replaced, so the shared code is in every place and a place's own code wins a clash. A project in a place's `rogen.json` replaces the place's own list only.
- A relative path means the same folder wherever it is inherited: a `$path`, a `globIgnorePaths` glob and the `syncPath` of the root are written relative to each place's folder. A place may set its own `syncPath`.
- `name` is not inherited by a place: a place is named after its folder unless it sets one. A project inherits the name of the place it is in.
- A place may declare `projects` and `serveProject` of its own, and may not list places.
- The root writes its own `default.project.json`, for the shared code, and is never served: `rogen serve` serves the places.
- A place sets `servePort`, `servePlaceIds`, `blockedPlaceIds`, `placeId` and `gameId` for itself. The root never serves, so no place inherits them, and setting one in the root or in one of its projects is an error ([`config.placeSetting`](/docs/v2/diagnostics#config-placesetting)).
- A place without a `servePort` is served on 34872 plus its index among the places without one, the places sorted by path, skipping ports other places pin. Studio remembers a place's port, so `rogen init <folder>` pins the port into the place it adds. A port in use is an error that names `servePort`.
- With several places served, a place's `servePlaceIds` are what makes a Studio connected to the wrong place's port refuse to sync. See [Studio](/docs/v2/studio#place-ids).
- `rogen build --watch` and `rogen serve` follow a place's `rogen.json` and the `placePaths` of the config. A folder that starts matching one while they run, because it was created or because it was given a `rogen.json`, is found when they restart.
- A command run inside a place answers for that place. A command run at the root covers the root and every place, and a project named on the command line (`rogen build release`) is the project of that name in each place.

## Tree

`tree` is the same node tree as in any Rojo project file. Rogen merges the nodes it generates into it, so it holds what names can't express: the DataModel name, package mounts and `$properties`.

```json title="rogen.json"
{
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": {
			"Packages": { "$path": { "optional": "Packages" } }
		}
	},
	"routes": { "*": "ReplicatedStorage/Shared" }
}
```

- If `tree` and the generated nodes define the same instance, `tree` wins and Rogen warns ([`tree.nodeClash`](/docs/v2/diagnostics#tree-nodeclash)). A `$path` below a service, like a package mount, owns that whole folder.
- A `$path` that points inside a source path hands that path to Rojo. Rogen skips it, and `rogen where` reports it as `mounted`, which is how you sync a vendored library as it is. Mounting a source path itself or a folder above one is an error.
- With `routes`, the tree's root must be a `DataModel`, since a route target names a service. A root that isn't one, a bare `$path` included, is an error. Leave `tree` out and Rogen starts from an empty `DataModel`.
- Without `routes`, nothing is routed and no source path is scanned. Any root is valid and the project file is `tree` as you wrote it. Rogen warns when `src` holds files the tree doesn't mount.

## Ignoring Files

`globIgnorePaths` lists globs, relative to the config, for files that should stay out of the game. Rojo ignores them, and Rogen doesn't route them or warn about them. Rogen writes the list to the project file for Rojo.

```json
{ "globIgnorePaths": ["**/*.spec.luau", "**/*.story.luau"] }
```

A glob that covers all of a folder a `tree` `$path` mounts with `/**` (`"DevPackages/**"`) leaves the mount out of the project file, since Rojo would otherwise keep it as an empty `Folder`. That is the one place Rogen reads `globIgnorePaths` differently from Rojo. A glob that only names the folder or file (`"DevPackages"`, `"**/DevPackages"`) ignores nothing of the mount, in Rojo too, and so does a glob that ignores only some of its files (`**/*.spec.luau`): the mount stays, and Rojo ignores those files. See [Leaving Out Files](/docs/v2/core-concepts/project-layout#leaving-out-files).

Rogen matches a glob the way Rojo does, so the two agree on what is ignored: `*` crosses folders (`*.tmp.luau` matches at any depth, and so does `src/*.luau`), and a glob that ends in `/` matches nothing. Rojo reads a glob that begins with `/` or `./` as matching nothing, so write the folder name first.

## Sync Rules

`syncRules` is Rojo's own key: a list of rules that turn a file name into an instance, tried before Rojo's built-in rules, the first match winning. Rogen reads files by them, so a custom extension is named, routed and given its meta file as Rojo will read it.

```json
{
	"syncRules": [
		{ "pattern": "*.module", "use": "moduleScript", "suffix": ".module" },
		{ "pattern": "*.hud", "use": "clientScript", "suffix": ".hud" },
		{ "pattern": "*.skip", "use": "ignore" }
	]
}
```

- `pattern` is a glob matched against the path from the config's folder, and `*` crosses folders. `exclude` is a glob of files the rule leaves to the next one.
- `use` is what the file becomes: `serverScript`, `clientScript`, `pluginScript`, `moduleScript`, `legacyClientScript`, `legacyServerScript`, `runContextServerScript`, `runContextClientScript`, `project`, `jsonModel`, `json`, `toml`, `csv`, `text`, `rbxm`, `rbxmx`, `yaml` or `ignore`. A file that `ignore` takes is left out of the tree.
- `suffix` is what Rojo cuts off the end of the file name to name the instance, extension included. Without it only the extension goes. A file whose name doesn't end with the suffix keeps its whole name, extension included, and Rogen warns ([`scan.syncRuleSuffix`](/docs/v2/diagnostics#scan-syncrulesuffix)). The meta file of `Combat.module` is `Combat.meta.json`, found by the cut name.
- Rules never apply to folders or `init` files, and a file a rule of yours doesn't take is read by Rojo's rules.

Rogen writes the rules to each project file, moved with the files they take: a pattern that begins with a folder follows that folder into a place or under a `syncPath`, and a pattern that begins with a wildcard stays as it is. A pattern Rogen can't move becomes one rule per file it takes. Where the `tree` mounts a folder under the old place of a moved pattern, Rogen also keeps the pattern as you wrote it, so Rojo reads that folder by it too (the same goes for `globIgnorePaths`). See [`config.invalidSyncRule`](/docs/v2/diagnostics#config-invalidsyncrule) for a rule Rojo can't read.

With `emitLegacyScripts: false`, Rogen also writes a `legacyClientScript` rule for each `.client` script a route puts in `StarterPlayerScripts` or `StarterCharacterScripts`, after yours, so they stay LocalScripts. It can't for an `init.client` script, which Rojo reads without rules ([`tree.runContextTarget`](/docs/v2/diagnostics#tree-runcontexttarget)).

A project file with `syncRules` is for Rojo alone: Argon rejects it. Without `syncRules`, the files Rogen writes load in Argon too. That includes the file of a project that sets `emitLegacyScripts: false` with routes into those containers.

## Removed Keys

A config is one folder's project file, so these keys are gone. Each is an error that names its replacement.

| Key | Replacement |
|---|---|
| `extends` | None: a `rogen.json` describes one folder. A second output with changed keys is a [project](#projects); a different folder has its own `rogen.json`. |
| `template` | Write the tree inline: move the template's `tree` and its other keys into `rogen.json`. |
| `outFile` | Rogen writes `default.project.json` beside `rogen.json`. |
| `exclude` | `globIgnorePaths`, which also leaves out a mount it ignores. |
| `rootDirs` | `sourcePaths`. |
| `syncDir` | `syncPath`. |
| `modes`, `mode` | A [project](#projects) with the keys the mode set. |
| `variants`, `conflicts` | None. A file that replaces another goes in a later source path; sets that exclude each other are a project each. |
| `server` | None: `rogen serve` starts Rojo. |

There are no config names either: no `<name>.rogen.json`, no `default.rogen.json`, and a command's argument is a folder or a project file, not a config name. `-o` no longer names the project file, as it did with `outFile`: on `build` it names the place file Rojo builds. A `rogen.json` with the keys of a Rogen 1 config, such as `source` or `aliases`, is an error that links to [Migrating from v1](/docs/v2/migrating-from-v1).

## Diagnostics

Every diagnostic points at the problem:

```
rogen.json:7:3 - warning: "outDir" is not a Rojo key and not Rogen's: it is passed through, and Rojo will reject the written file by this name. (config.unknownField)
```

Errors stop the build. Warnings don't, and the build still exits with 0. You'll get warnings for:

- files that match no route,
- names that look like a route key but aren't,
- server code that ships to clients,
- scripts placed where they'll never run,
- an empty sync path or a missing source path,
- instances that clash with the tree,
- a `default.project.json` that differs from what `build` would write, in `rogen check`.

[Diagnostics](/docs/v2/diagnostics) explains every code, with an example and the fix.
