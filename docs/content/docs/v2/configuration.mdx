A folder's **config** is `default.rogen.json` (or `default.rogen.jsonc`), a Rojo project file with one more key, `rogen`. Rojo's own keys stay at the top level and keep their meaning. The `rogen` block holds Rogen's three: `sourcePaths` says where your code is, `routes` where it goes, and `compiledPath` where Rojo reads it from. Rogen writes Rojo's keys, with the routed nodes merged into the tree, to `default.project.json` beside the config. Comments and trailing commas are fine.

Every path in a config is relative to the config's file, and no config reads another. Paths on the command line are relative to the working directory.

---

## Which File a Command Reads

Rogen picks a file the way Rojo does.

- **No argument** means the default of the current folder: `default.rogen.json`, or a plain `default.project.json` when no config is there. Nothing else is read, and Rogen does not search the folders above. In a folder with neither, the error says so and names the folder's other `.rogen.json` files if it has any. A subfolder of a project, or the root of a repository that holds only [places](/docs/v2/setups/places), gets the same "not found" error that `rojo serve` gives.
- **A folder** means its default: `rogen build places/lobby`.
- **A path** means that file: `rogen build dist.rogen.json`. A path to `dist.project.json` means the `dist.rogen.json` beside it, and when there is none, Rogen runs the plain project file as it is.
- **A bare name** such as `dist` means `dist.rogen.json` in the current folder, else a plain `dist.project.json`, unless a folder `dist` holds a default.
- **`serve`, `build`, `sourcemap` and `upload` take one project.** A second is a usage error, as in Rojo. To serve two places, use two terminals, the second with `--port`.

`rogen check <path>` and `rogen where <path>` are the exception: they take paths, and find each path's own config: the nearest default above it, else the named `.rogen.json` files at or above it whose source paths hold it. See [`check`](/docs/v2/cli#check-path).

A plain Rojo project runs under Rogen's commands as it is: `check`, `build`, `list`, `where`, `sourcemap`, `serve`, `upload` and `fmt-project` work on a folder with only a `default.project.json`, and Rogen writes nothing to the file. A `.project.jsonc` is read too, since Rojo reads it. Beside a `default.rogen.json`, the config wins.

A command writes **only the project file of the config it runs**. `rogen serve dist` writes `dist.project.json` and serves it, `rogen build release -o game.rbxl` writes `release.project.json` and builds from it, and nothing else is written. A file is rewritten only when its bytes differ. A config you didn't name can be broken without blocking you. The file Rogen writes is overwritten by every build, so edit the `X.rogen.json`; an `X.project.json` with no `X.rogen.json` beside it is a plain Rojo project and is left as it is.

## Fields

Rogen's keys, all inside the `rogen` block:

| Field | Default | What it does |
|---|---|---|
| `sourcePaths` | `["src"]` when `routes` exist | The folders to scan and watch. They merge into one tree, and the later one wins a clash. See [Several Source Paths](/docs/v2/core-concepts/project-layout#several-source-paths). Without `routes` it is an error. |
| `routes` | none | Route keys and their targets, like `"Service/Folder"`. Only declared keys route. Without it, nothing is routed and no source path is scanned. See [Routing](/docs/v2/core-concepts/routing). |
| `compiledPath` | none | The folder Rojo syncs from, usually your compiler's output. See [Compiled Path](/docs/v2/core-concepts/output#compiled-path). |

Rojo's keys, at the top level. Rogen passes each to the project file as it is, except `globIgnorePaths` and `syncRules`, which it also reads. [Rojo's project format](https://rojo.space/docs/v7/project-format/) documents all of them; this table says only what Rogen does with each:

| Field | What Rogen does with it |
|---|---|
| `$schema` | The published JSON schema, for editor validation and completion. It covers Rojo's keys and Rogen's, underlines a route key that isn't letters and digits and a route target that doesn't start with a service, and offers the common targets as completions. Rogen leaves it out of the project file. |
| `name` | The project's name. `default.project.json` carries it only when you set one here; Rojo names the project after its folder otherwise. Every other config must set one, since Rojo can't read its project file without ([`config.unnamedProjectFile`](/docs/v2/diagnostics#config-unnamedprojectfile)). |
| `tree` | The instance tree Rogen merges its generated nodes into. See [Tree](#tree). |
| `globIgnorePaths` | Globs, relative to the config, of files Rojo ignores. Rogen keeps them out of routing too. See [Ignoring Files](#ignoring-files). |
| `syncRules` | How a file name becomes an instance, in front of Rojo's own rules. Rogen reads files by them too. See [Sync Rules](#sync-rules). |
| `servePort`, `serveAddress`, `serveAllowedHosts` | Where `rojo serve` listens. See [`serve`](/docs/v2/cli#serve). |
| `servePlaceIds`, `blockedPlaceIds`, `placeId`, `gameId` | Which places may connect, and the ones a place file is published to. See [Studio](/docs/v2/studio#place-ids). |
| `emitLegacyScripts` | Whether Rojo makes `Script` and `LocalScript` instances for `.server` and `.client` files, rather than a run context. |
| `syncbackRules` | Rojo's syncback rules. |

A key on neither list is an error, since Rojo rejects a project file with a key it doesn't know ([`config.unknownField`](/docs/v2/diagnostics#config-unknownfield)); a Rogen key outside the block is an error that says where it goes ([`config.rogenKeyOutsideBlock`](/docs/v2/diagnostics#config-rogenkeyoutsideblock)). A wrong type is an error.

## Project Files Are as Fresh as Their Last Build

`default.project.json` is what the editor and your compiler read, and Rogen writes it only when a command builds that config. So it is as fresh as its last build. `rogen serve` and `rogen build` keep it current while they run. When you add a feature folder, or a file named with an `@` key, run `rogen build` before you open the editor or run the compiler; a file added to a folder that is already mounted whole needs nothing. A fresh clone runs `rogen build` before the editor or a compiler needs the file. `rogen check` reports a project file that differs from what a build would write.

Rogen writes these files, so `rogen init` adds `*.project.json` to the `.gitignore` it creates, beside `sourcemap.json`. The pattern covers a project file you wrote by hand as well; add `!name.project.json` below it to keep one tracked.

## More Files

A second output is a second complete file. `X.rogen.json` writes `X.project.json` beside it. Use one when the same code needs another project file: a Darklua build that Studio reads while your editor reads the source, a release without the dev packages, a test place. The file repeats `name`, `routes` and `tree` and changes what differs. Nothing is inherited:

```json title="default.rogen.json"
{
	"name": "Game",
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": { "DevPackages": { "$path": "DevPackages" } }
	},
	"rogen": {
		"sourcePaths": ["src", "dev"],
		"routes": { "server": "ServerScriptService", "*": "ReplicatedStorage" }
	}
}
```

```json title="dist.rogen.json"
{
	"name": "Game",
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": { "DevPackages": { "$path": "DevPackages" } }
	},
	"rogen": {
		"sourcePaths": ["src", "dev"],
		"routes": { "server": "ServerScriptService", "*": "ReplicatedStorage" },
		"compiledPath": "dist"
	}
}
```

```json title="release.rogen.json"
{
	"name": "Game",
	"globIgnorePaths": ["DevPackages/**", "**/*.spec.luau"],
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": { "DevPackages": { "$path": "DevPackages" } }
	},
	"rogen": {
		"sourcePaths": ["src"],
		"routes": { "server": "ServerScriptService", "*": "ReplicatedStorage" }
	}
}
```

- A file other than `default` must set `name`.
- `release` lists `"DevPackages/**"` in `globIgnorePaths`, which drops the `DevPackages` mount from `release.project.json`. See [Ignoring Files](#ignoring-files).
- A bare `rogen serve` serves `default.rogen.json`, even when `dist.rogen.json` sits beside it. With Darklua that is unprocessed source, as a bare `rojo serve` would serve: serve the processed code with `rogen serve dist`. `init` prints the run line that fits your setup.
- The files repeat each other and can drift. `rogen list` in the folder prints, for each file other than `default`, the keys in which it differs from `default`. It is information, not a warning: after you edit one file, run it to see which siblings to bring in step.
- A `test.project.json` you wrote by hand stays as it is. `rogen build test.project.json` runs it as a plain Rojo project when no `test.rogen.json` sits beside it.

**A test or subset file.** A second file is complete, so a smaller one is its own tree: give it its own `sourcePaths`, its mounts under `tree`, and `globIgnorePaths` for the mounts and specs it leaves out.

```json title="test.rogen.json"
{
	"name": "Game",
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": { "TestEZ": { "$path": "Packages/TestEZ" } }
	},
	"rogen": {
		"sourcePaths": ["src", "tests"],
		"routes": { "server": "ServerScriptService", "*": "ReplicatedStorage" }
	}
}
```

When you delete a `.rogen.json`, Rogen does not delete the `.project.json` it wrote, and Rojo still builds it. Delete the file with its config.

## Places

A repository with several places gives each place its own complete config, which lists its source paths in full and sets its own `name`: `lobby.rogen.json` at the root with `["src/common", "src/lobby"]` in Luau (what `init --places` writes), or a folder with its own `default.rogen.json` and `["../common/src", "src"]` for a place in `projects/`. Code the places share is a plain folder with no config of its own (`src/common`, `projects/common`). `servePort`, `servePlaceIds`, `blockedPlaceIds`, `placeId` and `gameId` are ordinary Rojo keys in each place's file, and Rogen writes no port. Name a place to run a command on it: `rogen serve lobby`, or `rogen serve projects/lobby`. The [Several Places guide](/docs/v2/setups/places) walks through it.

## Tree

`tree` is the same node tree as in any Rojo project file. Rogen merges the nodes it generates into it, so it holds what names can't express: the DataModel name, package mounts and `$properties`.

```json title="default.rogen.json"
{
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": {
			"Packages": { "$path": { "optional": "Packages" } }
		}
	},
	"rogen": { "routes": { "*": "ReplicatedStorage/Shared" } }
}
```

- If `tree` and the generated nodes define the same instance, `tree` wins and Rogen warns ([`tree.nodeClash`](/docs/v2/diagnostics#tree-nodeclash)). A `$path` below a service, like a package mount, owns that whole folder: a route into it puts files beside what the mount holds, and Rogen warns when a name is in both ([`tree.mountClash`](/docs/v2/diagnostics#tree-mountclash)).
- A `$path` that points inside a source path hands that path to Rojo. Rogen skips it, and `rogen where` reports it as `mounted`, which is how you sync a vendored library as it is. Mounting a source path itself or a folder above one is an error.
- With `routes`, the tree's root must be a `DataModel`, since a route target names a service. A root that isn't one, a bare `$path` included, is an error. Leave `tree` out and Rogen starts from an empty `DataModel`.
- Without `routes`, nothing is routed and no source path is scanned. Any root is valid and the project file is `tree` as you wrote it. Rogen warns when `src` holds files the tree doesn't mount.

## Ignoring Files

`globIgnorePaths` lists globs, relative to the config, for files that should stay out of the game. Rojo ignores them, and Rogen doesn't route them or warn about them. Rogen writes the list to the project file for Rojo.

```json
{ "globIgnorePaths": ["**/*.spec.luau", "**/*.story.luau"] }
```

A glob that covers all of a folder a `tree` `$path` mounts with `/**` (`"DevPackages/**"`) leaves the mount out of the project file, since Rojo would otherwise keep it as an empty `Folder`. That is the one place Rogen reads `globIgnorePaths` differently from Rojo. A glob that only names the folder or file (`"DevPackages"`, `"**/DevPackages"`) ignores nothing of the mount, in Rojo too, and so does a glob that ignores only some of its files (`**/*.spec.luau`): the mount stays, and Rojo ignores those files. See [Leaving Out Files](/docs/v2/core-concepts/project-layout#leaving-out-files).

A glob that starts with `!` brings back what an earlier glob ignored, as in a `.gitignore`: the last glob that matches a path decides. `["**/*.spec.luau", "!**/Keep.spec.luau"]` ignores every spec but `Keep.spec.luau`. A folder an earlier glob names is skipped whole, so nothing inside it can be brought back; write `"Vendor/**"`, not `"Vendor"`, to bring back one of its files. Write `\\!` for a name that starts with `!`. Rojo reads `!` from 7.7.0, and Rogen stops `serve` with [`rojo.negationUnsupported`](/docs/v2/diagnostics#rojo-negationunsupported) for an older one.

Rogen matches a glob the way Rojo does, so the two agree on what is ignored: `*` crosses folders (`*.tmp.luau` matches at any depth, and so does `src/*.luau`), and a glob that ends in `/` matches nothing. Rojo reads a glob that begins with `/` or `./` as matching nothing, so write the folder name first.

## Sync Rules

`syncRules` is Rojo's own key: a list of rules that turn a file name into an instance, tried before Rojo's built-in rules, the first match winning. Rogen reads files by them, so a custom extension is named, routed and given its meta file as Rojo will read it.

```json
{
	"syncRules": [
		{ "pattern": "*.module", "use": "moduleScript", "suffix": ".module" },
		{ "pattern": "*.hud", "use": "clientScript", "suffix": ".hud" },
		{ "pattern": "*.skip", "use": "ignore" }
	]
}
```

- `pattern` is a glob matched against the path from the config's folder, and `*` crosses folders. `exclude` is a glob of files the rule leaves to the next one.
- `use` is what the file becomes: `serverScript`, `clientScript`, `pluginScript`, `moduleScript`, `legacyClientScript`, `legacyServerScript`, `runContextServerScript`, `runContextClientScript`, `project`, `jsonModel`, `json`, `toml`, `csv`, `text`, `rbxm`, `rbxmx`, `yaml` or `ignore`. A file that `ignore` takes is left out of the tree.
- `suffix` is what Rojo cuts off the end of the file name to name the instance, extension included. Without it only the extension goes. A file whose name doesn't end with the suffix keeps its whole name, extension included, and Rogen warns ([`scan.syncRuleSuffix`](/docs/v2/diagnostics#scan-syncrulesuffix)). The meta file of `Combat.module` is `Combat.meta.json`, found by the cut name.
- Rules never apply to folders or `init` files, and a file a rule of yours doesn't take is read by Rojo's rules.

Rogen writes the rules to each project file, moved with the files they take: a pattern that begins with a folder follows that folder under a `compiledPath`, and a pattern that begins with a wildcard stays as it is. A pattern Rogen can't move becomes one rule per file it takes. Where the `tree` mounts a folder under the old place of a moved pattern, Rogen also keeps the pattern as you wrote it, so Rojo reads that folder by it too (the same goes for `globIgnorePaths`). See [`config.invalidSyncRule`](/docs/v2/diagnostics#config-invalidsyncrule) for a rule Rojo can't read.

With `emitLegacyScripts: false`, Rogen also writes a `legacyClientScript` rule for each `.client` script a route puts in `StarterPlayerScripts` or `StarterCharacterScripts`, after yours, so they stay LocalScripts. It can't for an `init.client` script, which Rojo reads without rules ([`tree.runContextTarget`](/docs/v2/diagnostics#tree-runcontexttarget)).

A project file with `syncRules` is for Rojo alone: Argon rejects it. Without `syncRules`, the files Rogen writes load in Argon too. That includes the file of a project that sets `emitLegacyScripts: false` with routes into those containers.

## Removed Keys

A config is one project file's description, so these keys are gone. Each is an error that names its replacement.

| Key | Replacement |
|---|---|
| `extends` | None: configs don't read each other. A second output is a [second complete file](#more-files). |
| `projects` | A second complete `<name>.rogen.json` for each entry. |
| `serveProject` | `rogen serve dist` serves the file you name; a bare `rogen serve` serves `default.rogen.json`. |
| `placePaths` | A [place](/docs/v2/setups/places) is a folder with its own `default.rogen.json`. Name it: `rogen serve places/lobby`. |
| `template` | Write the tree inline: move the template's `tree` and its other keys into `default.rogen.json`. |
| `outFile` | Rogen writes `default.project.json` beside `default.rogen.json`. |
| `exclude` | `globIgnorePaths`, which also leaves out a mount it ignores. |
| `rootDirs` | `sourcePaths`, inside the `rogen` block. |
| `syncDir`, `syncPath` | `compiledPath`, inside the `rogen` block. |
| `modes`, `mode` | A second complete file with the keys the mode set. |
| `variants`, `conflicts` | None. A file that replaces another goes in a later source path; sets that exclude each other are a file each. |
| `server` | None: `rogen serve` starts Rojo. |

`sourcePaths`, `routes` and `compiledPath` at the top level are an error as well, and the message says to move them into the `rogen` block. A file named `rogen.json` is not read: rename it `default.rogen.json` and move its Rogen keys into a `rogen` block. `-o` no longer names the project file, as it did with `outFile`: on `build` it names the place file Rojo builds. A `.rogen.json` with the keys of a Rogen 1 config, such as `source` or `aliases`, is an error that links to [Migrating from v1](/docs/v2/migrating-from-v1).

## Diagnostics

Every diagnostic points at the problem:

```
default.rogen.json:7:3 - error: "outDir" is not a Rojo key and not Rogen's, and Rojo rejects a project file with a key it doesn't know. (config.unknownField)
```

Errors stop the build. Warnings don't, and the build still exits with 0. You'll get warnings for:

- files that match no route,
- names that look like a route key but aren't,
- server code that ships to clients,
- scripts placed where they'll never run,
- an empty compiled path or a missing source path,
- instances that clash with the tree,
- a `default.project.json` that differs from what `build` would write, in `rogen check`.

[Diagnostics](/docs/v2/diagnostics) explains every code, with an example and the fix.
