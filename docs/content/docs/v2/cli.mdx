```bash
rogen [command] [project] [options]
```

The first word is always the command. A bare `rogen` opens [the command picker](#the-command-picker) in a terminal, and prints the root help and exits 2 anywhere else, as `rojo` does. Whatever follows names a project, as it does in Rojo, and `build`, `serve`, `sourcemap`, `upload` and `syncback` take one: a second is a usage error, exit 2. A project is named by:

- a folder, which means its `default.rogen.json` (`rogen build places/lobby`);
- the path to a `.rogen.json` file (`rogen serve places/lobby/dist.rogen.json`), or to a `*.project.json` file, which means the `.rogen.json` beside it, and when there is none, the plain Rojo project as it is;
- the name of a file in the current folder, so `rogen serve dist` is `dist.rogen.json` (else a plain `dist.project.json`), unless a folder `dist` holds a default, which wins.

With none, a command reads the `default.rogen.json` of the working directory, or its `default.project.json` when it has no config, and nothing else. It does not look in the folders above, as `rojo serve` does not. A bare command in a folder with neither is an error, "No default.rogen.json or default.project.json in this folder", which names the folder's other `.rogen.json` files when it has any. A repo of [places](/docs/v2/setups/places) has no config at its root, so name the place: `rogen serve places/lobby`. The text output says which config it read (`rogen build · my-game`). Paths stay relative to where you run. `--json` doesn't change, since its paths are absolute. `rogen lobby` is an error, not a shortcut, and Rogen will suggest `rogen build lobby`.

`list` and `fmt-project` take several projects, and `check` and `where` take paths, which [find their own config](#where-path).

## Commands

### `build [project]`

Writes the project file of the `default.rogen.json` here, or of the project you name, beside it: `rogen build dist` writes `dist.project.json`. That file is the only one it writes, as `rojo build` reads only the file you give it, so `default.project.json` is as fresh as the last build of the default. Run `rogen build` after you add a feature folder or an `@key` file, so the editor's `default.project.json` follows, and in a fresh clone before the editor or a compiler needs it. A project file whose bytes wouldn't change isn't written, so building again is cheap. A broken `.rogen.json` you didn't name doesn't stop the build. The `*.project.json` that Rogen writes is overwritten by every build that changes it, so edit the `.rogen.json`, not the project file. A `*.project.json` with no `.rogen.json` beside it is a plain Rojo project: it is built as it is, and Rogen writes nothing to it.

Each warning and error ends with its [code](/docs/v2/diagnostics), and the closing line counts the warnings: `Built 1 project with 4 warnings.`

#### `build -o` and `-p`

`rogen build -o game.rbxl` writes the project files, then runs Rojo's own `build` on the project and passes it `--output game.rbxl`: a place or model file, as `rojo build` makes. `-p Tool.rbxm` passes `--plugin`, which builds into Roblox's plugins folder. The Rojo that runs is the one your toolchain file pins, as for [`serve`](#serve). Rojo builds the project you name (`rogen build release -o game.rbxl`), the default one otherwise. In a repo of places, name the place (`rogen build places/lobby -o lobby.rbxl`). Nothing is built when the project files have errors, and a failed Rojo build exits 1 with what Rojo said ([`rojo.commandFailed`](/docs/v2/diagnostics#rojo-commandfailed)).

#### `build --watch`

Builds, then rebuilds whenever files or the config change. Without `-o` or `-p` only names matter, since the project file holds no contents, so editing inside a script triggers nothing. With `-o` or `-p`, Rojo's build runs again after each write and after each edit of a file under the source paths, so the file it built holds what you saved. Rogen runs Rojo's build itself each time and never passes `--watch` to it.

A config reloads when its `.rogen.json` changes, and CLI overrides carry over. If you save an invalid config, `build --watch` prints the error and keeps using the last valid version.

```
┌  rogen build --watch · my-game
│
◇  12:04:31 · 2 files changed
│  ✔ default.project.json · wrote
│
◇  12:05:02 · default.rogen.json changed · reloaded
│  ✔ default.project.json · unchanged
│
◇  12:06:10 · 1 file changed
│  ✔ default.project.json · wrote · 3 warnings as before
```

A block prints only the diagnostics the last one didn't have, so a standing warning isn't repeated. The result line counts what it left out (`3 warnings as before`), which tells you they are still there, and what went away since the last block (`1 warning fixed`).

It builds the one project it names, `default.rogen.json` when none is named. A `.rogen.json` you add beside it is not built until you name it.

With `--json`, `build --watch` prints one JSON object per line, as [`serve --json`](#serve---json) does, without the server lines: a `build` line each time it builds, a `notice` line when the config is removed, broken or recovered, and, with `-o` or `-p`, a `rojo` line after each Rojo build, shaped as [`rojo` in `build --json`](#build---json).

It's safe to run `build` while `build --watch` is running. Press Ctrl+C to stop.

### `sourcemap [project]`

Writes the project file, then runs Rojo's own `sourcemap` on the project and prints what it makes, as `rojo sourcemap` does, so `rogen sourcemap | jq` pipes. Like `build -o`, it runs the Rojo your toolchain file pins, on the default project unless you name another. A sourcemap for luau-lsp or Darklua has to come from the source tree, so a bare `rogen sourcemap` maps `default`, not a Darklua `dist`.

`-o <file>` writes the sourcemap there instead, and `--include-non-scripts` and `--absolute` are Rojo's flags, passed on. Nothing is written when the project files have errors, and a failed Rojo exits 1 with what it said ([`rojo.commandFailed`](/docs/v2/diagnostics#rojo-commandfailed)).

In a repo of [places](/docs/v2/setups/places), name the place or run it from the place's folder. Darklua and luau-lsp look for `sourcemap.json` beside the project, so a place that uses Darklua keeps it with `cd places/lobby && rogen sourcemap --watch -o sourcemap.json`.

`--watch` writes the project files again whenever names or the config change, and writes the sourcemap after each write, as [`build --watch`](#build---watch) does for `-o`. Every edit of a file under the source paths writes it again, a model or a meta file included, as `rojo sourcemap --watch` does. Without `-o` it prints each sourcemap on standard output, one document per change, and nothing else there; Rogen's own lines go to standard error. `--json` needs `-o`, since a sourcemap that is printed has no room beside the JSON lines.

### `upload [project]`

Writes the project file, then runs Rojo's own `upload` on the project, as `rojo upload` does: Rojo builds it and uploads it to Roblox. Like `build -o`, it runs the Rojo your toolchain file pins, on the default project unless you name another.

Rojo's flags are passed on, spelled as Rojo spells them: `--asset_id` names the place or model to upload to, and Rogen refuses to run without it. `--api_key` and `--universe_id` upload with Open Cloud, to a place only, and `--cookie` gives the cookie to upload with. Without a key or a cookie Rojo looks for a cookie on this machine. Rogen stores none of them and leaves them out of its own output, but a flag is visible to other programs on the machine while Rojo runs.

In a repo of places, name the place (`rogen upload places/lobby --asset_id 123`). Nothing is written or uploaded when the project file has errors, and a failed Rojo exits 1 with what it said ([`rojo.commandFailed`](/docs/v2/diagnostics#rojo-commandfailed)). `--json` prints [one document](#upload---json).

### `syncback [project] --input <file>` [#syncback]

Writes the project file, then brings the changes of a place or model file back into your source folders, as `rojo syncback` does for a project file: scripts edited in Studio, scripts added there, and scripts deleted. It is Rojo's own syncback, run once by Rogen on a mirror of your files: each file the build placed is copied to a folder laid out as the game is, named for its instance (`src/Inventory/Bag@server.luau` becomes `ServerScriptService/Inventory/Bag.luau`), and a project file made for the run mounts it. Rojo edits, adds and removes in the mirror as in any Rojo project, and Rogen writes each change back to the file it came from. So every layout behaves the same: routing folders, `@` names, `^` names, `(Group)` folders and markers. A folder the config's own `tree` mounts (`Packages`) is copied into the mirror too, so Rojo writes nothing outside it until you say yes, and its changes are written back where Rojo would write them. Two files whose instances differ only in letter case stop the run, as a case-blind file system can't hold both.

- **Edits and deletions reach the file the instance came from.** A changed script is written to its file, with the line endings the file had; a meta file Rojo changes or adds goes beside the file under the name the build pairs with it (`Bag@server.meta.json`); the files of an instance the place no longer holds are removed, its meta file with them. What Rojo itself skips is skipped: a class changed in Studio keeps its file, and a child added to a script that is not a folder is not written. A property or attribute set on a folder that no one folder of the project is (one a routing folder and an `@` name both feed) is listed as left out; set it on the folder's node in the `tree`. When an instance is gone, its files are removed, and its folder too once nothing else is left in it.
- **A new instance goes where routing would place a file for it, written like the nearest code.** Rogen takes the files already at its parent and writes the new one beside them, in their style: into the same routing folder, as `Mail@server.luau` beside `Save@server.luau`, or into the folder a marker routes. When they disagree, it follows most of them. With no file nearby, or as many in each style, it takes the style most files of the same route are written in, then the whole project's, then routing folders: in a repo of `@server` names, a new `ServerScriptService/Quest/Main` is `src/Quest/Main@server.luau`, and in one of routing folders `src/Quest/Server/Main.luau`, with the routing folder named as the config's routes name it. A script whose suffix already routes it gets no `@` name (`src/Boot.server.luau`). It is left out and listed ([`syncback.unplaced`](/docs/v2/diagnostics#syncback-unplaced)) only when nothing decides, such as two source paths with as many files beside it in each. After the run it asks where the files it placed land, and warns about one that lands elsewhere ([`syncback.misplaced`](/docs/v2/diagnostics#syncback-misplaced)).
- **It deletes.** The files of instances the place no longer holds are removed. A run in a terminal runs Rojo once, lists what it would do and asks; it then writes exactly that list, and nothing if one of the files it touches changed since. Without a terminal it needs `-y/--non-interactive`, or `--dry-run`. A file that cannot be written is listed as left out, and the rest is written. `--dry-run` plans and lists without writing; `--list` lists what a run writes. The list goes to stdout in Rojo's own form, `Writing <path>` and `Removing <path>` for each file and folder in the order Rojo lists them (the project file is your `.rogen.json`, where Rojo's own is the `.project.json`, and Rogen leaves out the colour codes Rojo adds), so a script that reads `rojo syncback --list` reads this. Rogen's other lines go to stderr. Without a terminal and without `-y`, Rojo asks, reads nothing, prints "Aborting due to user input!" and exits 0 having written nothing; Rogen exits 2 and says what to pass, since an agent should hear that nothing was written.
- **Changes to the nodes of your `tree` reach the `tree`.** What Rojo writes into the project file it ran on (`$properties`, `$attributes`, a node's value, a node it adds) is written into the `tree` of the `.rogen.json` you named, node for node, with its comments and formatting kept. A node routing made, such as a service the routes name, is not in the `tree`: its change is listed ([`syncback.unplaced`](/docs/v2/diagnostics#syncback-unplaced)); add a node for it to the `tree`.
- **Rojo's rules apply.** `syncbackRules` of the config pass through to the file Rojo reads, and the sync rules are written for the mirror's files. Nothing syncback writes may match `globIgnorePaths` or the `ignorePaths` of `syncbackRules`: an edit there is skipped, and a new instance that would land there is left out ([`syncback.unplaced`](/docs/v2/diagnostics#syncback-unplaced)). The `legacyClientScript` rule Rogen writes for `.client` files under `emitLegacyScripts: false` is left out of the run, since Rojo's syncback stops on it; a new LocalScript there is written as `Name.client.luau`. A project that syncs from a folder a tool writes into (a `compiledPath`, as with Darklua's `dist`) is written as Rojo writes it: into that folder, its files mirrored from there and new instances placed in the routing folders there, so the tool's next run replaces what syncback wrote. To bring Studio's changes into your sources, run it on the project that points at them, such as `default`. A plain project file with no `.rogen.json` beside it is given to Rojo as it is.

It runs on one project, as `upload` does: in a repo of places, name the place. Rojo older than 7.7.0 has no syncback ([`rojo.commandUnsupported`](/docs/v2/diagnostics#rojo-commandunsupported)). Nothing is written when the project file has errors or Rojo fails, and a failed Rojo exits 1 with what it said. Instances of services the project does not mention stay in the place: syncback skips them. `--json` prints [one document](#syncback---json).

### `plugin install` and `plugin uninstall`

Installs Rojo's Studio plugin into Studio's plugins folder, or removes it, with the Rojo your toolchain file pins in this folder or above, else the one on the PATH, so the plugin matches the server `rogen serve` starts. Installing again overwrites the plugin. It reads no project, so it runs in any folder. On a platform Rojo can't install a plugin on, Rojo's error is shown and the exit code is 1. `rogen plugin help` prints this command's help, as `rojo plugin help` does for Rojo's.

### `serve [project] [--port <port>] [--address <address>] [--allowed-hosts <host>…] [-- server args…]` [#serve]

Builds, starts Rojo on the project, and rebuilds it on changes as `build --watch` does. Run it instead of `build --watch` when you sync to Studio. It serves one project: the `default.rogen.json` here, or the one you name (`rogen serve dist`, `rogen serve places/lobby`).

```
rogen serve · my-game
12:04:31 · initial build
  default.project.json · unchanged
  Serving my-game with Rojo 7.7.1 at 127.0.0.1:34872.
12:05:10 · 1 file changed
  default.project.json · wrote
error: Rojo: Snapshot error: File is not a valid JSON model: src/Bad.model.json: JSONC parse error: Expected colon after the string or word in object property on line 2 column 1
```

A bare `rogen serve` serves `default.rogen.json` even when a `dist.rogen.json` sits beside it. With Darklua that is the unprocessed source, as a bare `rojo serve` would be, so `init` prints the line that fits your setup (`rogen serve dist`). In a repo of [places](/docs/v2/setups/places) there is no config at the root, so a bare `rogen serve` there is the "No default.rogen.json or default.project.json in this folder" error: name the place. Serving a second place at once is a second terminal with its own port, as with Rojo: `rogen serve places/lobby --port <port>`. Rogen writes no port and chooses none, and a second project on one command line is a usage error.

Servers start only after the first build succeeds. If it fails, nothing starts, the errors print and `serve` exits 1. A server that has not answered for its project after ten seconds is reported once, saying what else answers on its port if something does, and `serve` goes on waiting. Press Ctrl+C to stop: it reaches the server, and Rogen ends every process it started. Closing the terminal (SIGHUP) or sending SIGTERM does the same. A `serve` that is killed outright (SIGKILL, a crash) can't end its server, which then keeps serving the old project file; see the next section.

**As the config changes.** The server follows the config while `serve` runs, as the build does. A `servePort` or `serveAddress` change in the `.rogen.json` restarts the server there.

**Which Rojo.** Rogen runs the Rojo the project pins in `rokit.toml`, `aftman.toml` or `foreman.toml`, in the folder of the config or any folder above, so the pinned version runs. With none pinned, it uses the one on the PATH. With no Rojo at all, `serve` exits 1 with [`serve.noServer`](/docs/v2/diagnostics#serve-noserver). `serve` only starts Rojo: to serve with Argon, see [Studio](/docs/v2/studio#serve-with-argon). Rogen never bundles Rojo, since it has to match the Studio plugin you installed, and installs one only when `rogen init` is told to (a Yes in a terminal, or `--rojo`). With none, `serve` ends its error with `Run 'rogen init --rojo' to set Rojo up.`, and it also looks in Rokit's bin folder (`~/.rokit/bin`), so the terminal that installed Rokit needs no restart. It runs `rojo --version` first, so a broken install fails before the build. A Rojo before 7.5.0 does not read `syncRules`, so `serve` stops with [`rojo.syncRulesUnsupported`](/docs/v2/diagnostics#rojo-syncrulesunsupported) when a file it wrote has any. A Rojo before 7.7.0 reads no `globIgnorePaths` glob that starts with `!`, so `serve` stops with [`rojo.negationUnsupported`](/docs/v2/diagnostics#rojo-negationunsupported) when a file it wrote has one. Rojo 7.7.0 on Windows applies no sync rule or ignore glob whose pattern starts with `../`, so `serve` stops with [`rojo.windowsRules`](/docs/v2/diagnostics#rojo-windowsrules) when a file it wrote has one.

**Port.** `--port` and `--address` are Rojo's own flags:

| Port | Host |
|---|---|
| `--port`, else `servePort` in the `.rogen.json`, else 34872 | `--address`, else `serveAddress`, else `127.0.0.1` |

`--allowed-hosts`, which Rojo takes from 7.7.0, goes to the server; repeat it for several hosts. With an older Rojo it exits 2 before anything is built. A `servePort` in the `.rogen.json` is committed, so every teammate's plugin matches.

**Already running.** Before building, Rogen asks each port what serves there. A Rojo server only says the name of its project, and a server another `rogen serve` started is also known by its project file:

- **Another `rogen serve` serves the project file.** That serve keeps it built, so nothing starts for it: `serve` says so and exits 0 without building.
- **A `rogen serve` that ended left its server running.** The record of the server names the `rogen serve` process that started it. When that process no longer runs, the next `rogen serve` of the project file ends the server and what it started, says so (`Ended the Rojo (process 4301) that a rogen serve (process 4290) left running when it stopped without ending it.`), and starts its own, so it builds and watches as usual. When the process that leads the server is gone too, there is nothing to end, and the port counts as held by another process, as below. A record from an older Rogen, which names no process, still counts as served by another `rogen serve`. SIGHUP also overrides `nohup`: a `serve` you want to outlive its terminal must run under a process manager that doesn't hang it up.
- **A `rogen serve` started the server for another file,** in this folder or another, such as a second place on the same port. `serve` exits 1 with [`serve.portTaken`](/docs/v2/diagnostics#serve-porttaken), which names that file and says to stop it, set a `servePort`, or run the command with a free port.
- **Anything else holds the port,** such as a `rojo serve` you ran yourself, an Argon server, one an editor extension started, or a second checkout of the same project. `serve` exits 1 with [`serve.portTaken`](/docs/v2/diagnostics#serve-porttaken), as Rojo does for a port in use: the port is held by another process, and the message says to stop it or give this one another port with `--port` or `servePort`.

**After `--`.** Everything after `--` goes to the server untouched, after the flags above, and a `--port` or `--address` there counts as the flag. Rogen reads both, so the running check asks the port the server will use. A flag given both ways exits 2. Other commands take nothing after `--`: `rogen build -- x` exits 2.

**Studio.** When the Rojo is 7.7 or later, Rogen starts it with `RUST_LOG=info,librojo::web=debug`, which makes it log each plugin that connects and leaves (the `info` is your own `RUST_LOG`, if you set one), and says so: `Studio connected to my-game.`, `Studio connected to my-game (2 connected).`, `Studio disconnected from my-game, 1 still connected.`. A connection that drops without a goodbye, such as Studio crashing, counts as leaving. Rojo's log doesn't say what the client is, so any client of the server's websocket counts, not only the plugin. More than one connection is normal: a playtest server holds its own. A `RUST_LOG` you set stays: Rogen adds its directive after yours. An older Rojo logs differently, so for it no such line is printed; the `serving` line of `--json` says which case it is with `reportsConnections`. The count is also kept in the serve's record, so `rogen list` shows it from another terminal.

**Server output.** Rogen reads what the server prints and shows its warnings and errors as its own lines, each on one line, named after the server, with paths relative to the folder you ran `serve` in. The rest is dropped: the server's banner, since Rogen's `Serving` line says where it listens, its info logs, its debug detail, a message it repeats, and what Rogen's own port checks and project file writes make it say. A line Rogen doesn't recognise, such as a crash, is shown as it is, so nothing that explains a failure is lost. `--verbose` shows the dropped lines too, as debug lines.

**Exit code.** After Ctrl+C, SIGTERM or SIGHUP, `serve` stops its servers and exits with 128 plus the signal's number (130, 143 and 129), as the shell reports a `rojo serve` that the signal stopped. When a server stops on its own, `serve` stops too and exits with the server's code; a non-zero code also reports [`serve.serverExited`](/docs/v2/diagnostics#serve-serverexited).

`serve` accepts `--json`. See [`serve --json`](#serve---json) for its lines.

### `where [path…]`

Shows where each file lands in the game and why, without writing anything. When a project file on disk differs from what `rogen build` would write, it adds an [`output.differs`](/docs/v2/diagnostics#output-differs) warning after the answers, since Rojo and Studio would show a game other than the one it describes:

```
$ rogen where src/Net src/Combat/Server/Hit.luau
src/Net/Http.luau -> ReplicatedStorage/Shared/Net/Http · route * (fallback)
src/Net/Http.mock.luau -> ReplicatedStorage/Shared/Net/Http.mock · route * (fallback)
src/Net/Http.spec.luau -> ignored · matches **/*.spec.luau
src/Net/Remotes@server.luau -> ServerScriptService/Net/Remotes · route Server (suffix)
src/Net/Types.lua -> replaced by src/Net/Types.luau
  warning: becomes "ReplicatedStorage/Shared/Net/Types", as src/Net/Types.luau does, which takes its place. Rename one of them to keep both. (tree.instanceClash)
src/Net/Types.luau -> ReplicatedStorage/Shared/Net/Types · route * (fallback)
src/Combat/Server/Hit.luau -> ServerScriptService/Combat/Hit · route Server (folder)
  require(game:GetService("ServerScriptService").Combat.Hit)
```

A directory stands for the files inside it, and no path at all means every file of the default config here. Answers come in the order you gave the arguments, and a file already answered by an earlier argument isn't repeated. Since Rogen only reads names, the path doesn't have to exist yet, so you can check a file before you create it.

A placed file shows its instance path, the governing route, how it matched (`folder`, `marker`, `suffix` or `fallback`). Otherwise the line says why it isn't placed: `replaced by` another file, `displaced` by a `tree` node, `mounted` by a `tree` `$path`, `in a nested project` for a file in a folder that holds a `default.project.json`, `unrouted`, `ignored` (with the glob), `outside the source paths`, or `not placed` when the build of the config stops on an error. The error is either the file's own, which `where` prints under the line (for a directory, the line names the file inside it: `not placed · src/F/Bad@server.luau has an error (route.ignoredAt)`), or another file's, which the line names: `not placed · the build stops on src/F/Bad@server.luau (route.ignoredAt); run 'rogen check'`. A placed file that isn't there yet ends its line with `· the file does not exist yet`; `--json` has `exists: false`. A mounted file or folder (a package, a folder with an `init` file, any `$path` of a plain Rojo project) shows the instance Rojo makes of it, by Rojo's own rules: an `init` file is its folder, a `.meta.json` is the instance beside it, a `.model.json` or `.txt` is an instance named for its stem, and a file Rojo reads nothing from is `mounted` with no instance. A folder that holds mounts lists them. Asked by instance, `where ReplicatedStorage.Packages.Roact` finds the mounted file, and so does a Studio stack trace into a package through `rogen where -`. None of this needs `sourcePaths`, so it works on a folder with only a `default.project.json`. `where` still exits 0. That answer is per path. Paths named in one call are placed together, as if each of those that does not exist were created, so two of them that differ only in letter case (`Server/A.luau` and `server/B.luau`) each get a `scan.portableName` warning about the other; ask about alternatives in separate calls. Without a path, or asked about an instance, `where` has nothing it can place, so it prints the errors and exits 1, as `check` does.

With no path and nothing in the source paths, `where` says `No files in the source paths (src).` A path that doesn't exist and ends in a separator (`src/Combat/`) answers `does not exist · name a file in it to see where it would land`, since a file in it, such as `src/Combat/Hit.luau`, is placed as if it existed. Without the separator it answers `does not exist`, since `src/Module` may be a file missing its extension. A backslash is a separator on every platform, so `src\Combat\Hit.luau` answers as `src/Combat/Hit.luau` does.

Under the line of a file you name, `where` prints, dimmed, the `require` that reaches it, since "where does it land" is followed by "how do I reach it". It writes a name that isn't an identifier as an index. Where no path reaches the file, it says why instead: a module under `StarterPlayerScripts` (or `StarterCharacterScripts`, `StarterGui`, `StarterPack`) is cloned into each player, and a script isn't a module. A roblox-ts source is imported by path and gets no line. A directory and a bare `rogen where` are listings and stay as they are; `--verbose` adds each module's require to a listing.

```
$ rogen where src/Inventory/Types.luau src/Hud/Client/Hud.luau
src/Inventory/Types.luau -> ReplicatedStorage/Shared/Inventory/Types · route * (fallback)
  require(game:GetService("ReplicatedStorage").Shared.Inventory.Types)
src/Hud/Client/Hud.luau -> StarterPlayer/StarterPlayerScripts/Hud/Hud · route Client (folder)
  no require by this path: StarterPlayerScripts is cloned into each player
```

Under a path's line, `where` prints each warning or error a build would raise about it, with its code, so you see a stray `@` or a script that never runs before you build. Warnings about the compiled path are left out, since they are about your compiler's output and not a path. For a file you name, that includes the diagnostics about a folder it lies in, such as a misspelt route folder; a directory's listing leaves them to `check`. A path that doesn't exist yet gets the warnings it would get once created, and exit stays 0: `where` answers a question, it doesn't judge the project.

```
$ rogen where src/Inventory/Save@sever.luau
src/Inventory/Save@sever.luau -> ReplicatedStorage/shared/Inventory/Save@sever · route * (fallback)
  warning: did you mean "@Server"? (route.strayAt)
  require(game:GetService("ReplicatedStorage").shared.Inventory["Save@sever"])
```

A path can carry the `:line` or `:line:col` that linters and logs print after it, with or without a message (`src/Net/Http.luau:12:5: unexpected symbol`); Rogen reads it as the path, so you can paste such a line as it is.

`where` also works backwards. An argument that starts with a service is read as an instance, and you can paste an error line straight in:

```
$ rogen where "ServerScriptService.Combat.Hit:12: attempt to index nil"
src/Combat/Server/Hit.luau -> ServerScriptService/Combat/Hit · route Server (folder)
```

A line number names a script, so only the file that places that script is listed. A running game's copy of a player's scripts is read as the container it comes from: `Players.ldg.PlayerScripts.Chat.ChatController:4` is `StarterPlayer.StarterPlayerScripts.Chat.ChatController`, `Players.ldg.PlayerGui.Hud` is `StarterGui.Hud` and `Players.ldg.Backpack.Sword` is `StarterPack.Sword`. An instance with none, such as `ServerScriptService.Combat`, lists every file inside it.

When no file places the instance, `where` says where a new one goes, from the files placed beside it:

```
$ rogen where ServerScriptService.Inventory.Export
ServerScriptService.Inventory.Export -> no file places it · a new file goes in src/Inventory/Server/
```

With no files beside it, `where` still names the folder when a route and a source path make one: for the first server file of `src/Shop/`, `a new file goes in src/Shop/Server/`, checked by placing a file there as `build` does. When a file on disk would place the instance after a rename that a warning proposes, such as a typo in an `@` suffix, `where` says so:

```
$ rogen where "ServerScriptService.Shop.Buy:4: attempt to index nil"
ServerScriptService.Shop.Buy -> no file places it · src/Shop/Buy@sever.luau would, renamed to Buy@Server.luau (route.strayAt)
```

`rogen where -` turns a whole pasted log into links. It reads text on stdin and prints it back with every instance path that has a line number written as `file:line`, in both forms Studio prints: `ServerScriptService.Combat.Hit:12:` and `Script 'ServerScriptService.Combat.Hit', Line 12`. Other text passes through as it is, and an instance no file places stays as it was. It prints text, so `--json` with it is a usage error.

```
$ pbpaste | rogen where -
src/Combat/Server/Hit.luau:12: attempt to index nil
Stack Begin
src/Combat/Server/Hit.luau:12 - function strike
Stack End
```

An instance that one file places is rewritten. One that several files place is left as it is and listed once on stderr with the files, and the exit code stays 0. `-` takes no other path and no `--json`, and it needs a pipe, not a terminal. Text with nothing to rewrite needs no config. When a config can't answer, the text is printed as it is and `where` exits 1 with the errors.

`where` takes paths, not projects, and a path finds its own config. A file is answered by the `default.rogen.json` of the nearest folder at or above it (in one folder a `.rogen.json` comes before a plain `default.project.json`), so `rogen where places/lobby/src/Menu.luau` works from the repo root, where the agent hook runs. A `.rogen.json` path lists every file of that config. A path that no config covers, such as a file in the shared code of a roblox-ts project, is skipped with a warning on stderr that names the way, `rogen where projects/lobby`, and the exit code stays 0. When the paths belong to several configs, each answer starts with its config's name (`lobby: places/lobby/src/Menu.luau -> …`). With no path, and for an instance or `-`, `where` reads the default config of the working directory and nothing above it.

A config that doesn't load answers nothing: `where` prints its errors and exits 1.

`where --json` keeps the `outside` entries. `where` accepts `--json`.

### `check [path…]`

Prints the diagnostics about the paths you give it, and nothing else, and exits 1 when there are any. It builds as `build` does and writes nothing, so it fits a hook, `lint-staged` or `pre-commit`, which pass changed paths to a command and expect a non-zero exit. `where` answers a question and always exits 0; `check` is the judging counterpart. A path finds its own config as in [`where`](#where-path): the `default.rogen.json` of the nearest folder at or above it, so `rogen check places/lobby/src/Menu.luau` works from the repo root, and a `.rogen.json` path checks that config whole. A path that no config covers, such as a file in the shared code of a roblox-ts project, is skipped with a warning on stderr that names the way (`rogen check places/lobby`), and the exit code stays 0. A path in no source path is not an error, since a hook passes every changed file, but when its first folder is one edit from a source path (`scr/Inventory/Save.luau` beside `src`), `check` warns [`scan.outsideSourcePaths`](/docs/v2/diagnostics#scan-outsidesourcepaths).

```
$ rogen check src/Inventory/Save@sever.luau src/Inventory/Clean.luau
src/Inventory/Save@sever.luau - warning: did you mean "@Server"? (route.strayAt)
```

Each line is `file:line:col - severity: message (code)`, printed on stdout, so `rogen check > report.txt` and `rogen check | grep strayAt` work, and `--quiet` keeps them. A clean path prints nothing. A diagnostic about a group of files is cut down to the entry about your path. A path that doesn't exist yet is checked as if it did, and the compiled path's warnings are left out, as in `where`. A diagnostic is about a path when it names the path, something inside it, or a folder the path lies in: a misspelt folder (`route.folderTypo`) is reported for every file in it and for the folder above it. Whatever paths you give, a config that doesn't load fails the check, because it stops the build before any file is placed.

An error that stops the build because of another file does not fail the check of a path it isn't about. The check passes, and says how far it got: `Checked as far as the build gets: it stops on src/F/Bad@server.luau (route.ignoredAt). Run 'rogen check' to see everything.` On stderr, so a hook stays green for the files it was given; with `--json` the document gains `"stoppedBy"`, the same diagnostics as `"diagnostics"` has.

With no path, `check` reports every diagnostic of the default config of the working directory, the compiled path's included, and a warning when `default.project.json` on disk differs from what `build` would write ([`output.differs`](/docs/v2/diagnostics#output-differs)): what `build` would do, without the write, which a read-only checkout needs. Its lines have the same shape as with paths: a warning about several files prints one line per file, none left out, and one that isn't about a file (a missing source path, an empty compiled path) names the config or folder it is about.

`check --json` prints `{ "diagnostics": [...] }` with the entries described under [JSON output](#json-output). `check` accepts `--json`. It has no `--changed`: git stays outside Rogen, so whoever calls `check` passes the paths.

```bash
git diff --name-only --diff-filter=d HEAD | xargs -r rogen check
```

### `init [path]`

Writes a starting `default.rogen.json`, in the folder or in `path`, which `init` makes when it isn't there. Every command line of `rojo init` works: `--kind` and `--skip-git`, and a folder to start in, as `rojo init newproj` does. It detects the language, Darklua and your package manager, and writes what it found into the config. This is the only time Rogen detects anything; builds just do what the config says. The file is written as [`fmt-project`](#fmt-project-project) writes it, except for a tree lifted from a project file: each node of it that stays as it was keeps your numbers (`0`, not `0.0`), the order of your keys, and your comments, and only what Rogen changed is written afresh. `rogen fmt-project` formats the tree as Rojo does, but leaves a file that holds comments or trailing commas as it is.

In a terminal it asks only what it can't detect: the language in a folder with no code, `tsconfig.json` or `package.json`; `One place or several?` for a new project; and `Project file` when a hand-written `default.project.json` is there, since losing it is the one choice that can't be undone. Everything else is shown once as a summary of what it will write and run (one row per area with the detected or default value, then every file and command), and `Create this project?` takes Yes (Enter), Customise or Cancel. Customise asks every question, each with its answer preselected, and returns to the summary. A flag answers its row before the summary, so a flag is never asked again. The summary is the same shape for a change to a project that has a config (`Make these changes?`) and for a place (`Add this place?`). With `--non-interactive`, `--json`, or when it can't ask (see [Output](#output)), it takes the defaults, and a flag from [Choices as flags](#choices-as-flags) answers its question in either case.

When it finds a test runner, it also writes a `release.rogen.json` that ignores the specs (see [Testing](/docs/v2/testing)), and with Darklua a `dist.rogen.json` that sets the compiled path Studio syncs from (see [Darklua](/docs/v2/setups/darklua)). Each is a complete copy of `default.rogen.json` with the one key that differs, which `rogen list` shows. `init` builds only the default: `rogen serve dist` writes `dist.project.json` when you first serve it. With Darklua it also writes a `.darklua.json` where none exists, with the `convert_require` rule that turns path requires into instance requires (none for roblox-ts, whose compiler already did), lists the compiled path in the `.gitignore` it creates, and pins Darklua next to Rojo (see below). An existing `.darklua.json` or `.gitignore` is never edited: when the `.gitignore` doesn't list the compiled path, `init` prints `Add /dist to .gitignore so the processed code isn't committed.`

The `.gitignore` it creates also lists `sourcemap.json` and `*.project.json`, since Rogen writes the project files and they change with the tree. The pattern covers a project file you write by hand too: add `!name.project.json` to keep one tracked. A clone, and CI, run `rogen build` before the editor or a compiler needs the files. An existing `.gitignore` without the pattern gets an `Add *.project.json to .gitignore` line in the next steps.

`--kind place|model|plugin` says what the project is, as in `rojo init`. A place (the default) gets Rogen's starter, the routes and the Greeter sample, described below. A model or a plugin starts with Rojo's template of that kind (`src/init.luau` or `src/init.server.luau`, a `README.md` that names `rogen build`) and a `default.rogen.json` whose tree is the template's project, `$path: "src"`. A model or a plugin has no service to route to, so Rogen adds nothing to it yet, and `init` asks for no source paths. The files of Rojo's template are written where none exists, and the project file is built from `default.rogen.json`, so a model or a plugin builds to the same bytes as the one Rojo's template makes.

In a folder with no code, a new place also gets a sample that is Rogen's equivalent of Rojo's: three hello-world scripts in one feature folder, `src/Greeter/{Shared,Server,Client}`, where `Greeting.luau` is a module that both scripts require, a `README.md` that explains the layout, and the tree of `rojo init`'s sample game (a Baseplate, Lighting and SoundService) so the built place is playable. `rogen where src/Greeter/Shared/Greeting.luau` prints the `require` the scripts use. `--no-sample` writes an empty `src` and the bare tree. The sample is written only for a place that has no code folder, a new tree and the `server`, `client` and `shared` routes, and for roblox-ts only when `init` starts the project (see below), and `--sample` where it can't be written is a `usage` [error](#errors) that says why. For roblox-ts the folders are lowercase and the files TypeScript (`src/Greeter/shared/Greeting.ts`).

The starter's files are in the repository, one folder per variant: [`luau`](https://github.com/LDGerrits/rogen/tree/main/templates/luau) is the Greeter feature in `src/Greeter` for one place; [`luau-places`](https://github.com/LDGerrits/rogen/tree/main/templates/luau-places) puts the Greeter in `src/common` and a `Game` script in `src/game`; [`roblox-ts`](https://github.com/LDGerrits/rogen/tree/main/templates/roblox-ts) and [`roblox-ts-places`](https://github.com/LDGerrits/rogen/tree/main/templates/roblox-ts-places) are the same two layouts in TypeScript, with the places in `projects/`. `init` writes the config around them and fills in the project's name and the command that serves it.

In a folder with no code, `package.json` or `tsconfig.json`, `--language roblox-ts` first runs `npm create roblox-ts@latest -- game --dir . --yes --git=false --skipBuild`, replaces create-roblox-ts's sample and project file with Rogen's, sets the project's `name` (which roblox-ts requires), and lists `/node_modules`, `/out`, `/include` and `*.tsbuildinfo` in the `.gitignore` it creates. Its next steps are `npm run watch` and `rogen serve`. The command shows in `--dry-run` and in `--json` (`commands`), and runs before any file is written: if it fails (npm missing, no network), `init` writes none of its own files, and the `tool` [error](#errors) names the command to run by hand. What create-roblox-ts wrote before it failed stays, and `rogen init` over it sets Rogen up in that project, without the sample.

A new project also asks `One place or several?` (`--places`, `--no-places`). In Luau, several places put the code they share in `src/common` and the first place's own in `src/game`, and each place is a complete `<place>.rogen.json` at the root: `game.rogen.json` lists `src/common` and `src/game` in its `sourcePaths` and sets its own `name`. `init` also writes a `.vscode/settings.json` that makes luau-lsp keep `sourcemap.json` current for the first place (`rogen sourcemap game --watch -o sourcemap.json`; change the name to switch place), and `src/game/Game/Server/Game.server.luau` greets with the shared module. It writes no workspace file and no config for the shared code. Add a place with `rogen init <name>` (see [Adding a place](#adding-a-place)). In a new roblox-ts project each place is a folder of `projects/` with its own complete `default.rogen.json` and `tsconfig.json`, the shared code is `projects/common/src`, and the first place is `projects/game`; `projects/common/tsconfig.json` serves the editor. A `projects` folder here makes several the default of a roblox-ts run that can't ask, and more places are added with `rogen init projects/<name>`. `--places` works in Luau and in a new roblox-ts project, with or without Darklua (see [roblox-ts with Places](/docs/v2/setups/places#roblox-ts-with-places)), and with `--no-sample` the two source folders are empty. The next steps print `rogen serve game` (`rogen serve projects/game` in roblox-ts), and how to serve a second place from a second terminal with `--port`.

A new project also gets what `rojo init` gives it besides the project file: a `.gitignore` where there is none, and a `git init` where git is installed and no work tree holds the folder. `--skip-git` leaves both out. `init` writes a `.gitignore` of its own and never edits one that exists, and it starts no repository where a work tree holds the folder already. A run says what it did (`Initialised a git repository.`), and `--json` has `git: "initialised"`, `"wouldInitialise"` in a dry run, or `"failed"` when `git init` failed: that is a warning, and the project is written without a repository. A folder from which a `.git` is found upward is inside a work tree, and gets no new repository.

With a `path`, `init` starts a project there. When the project has places and the folder is a new one of them, it adds a place instead (see [Adding a place](#adding-a-place)). Either way `--dry-run` says which, and plans the same files.

Below a folder that has a config, `init` stops: that config builds the folder as part of its game, so a project in it would be built twice. In a terminal it asks first, with **No** as the answer Enter gives; without one it fails and names the folder to run `rogen init` from, or `--nested` to start the project there anyway.

`init` never overwrites a file it writes. If a hand-written `default.project.json` is in the way, it's lifted into `default.rogen.json` first: its `tree` and other keys move across, without the nodes that point into the source paths, which become routes that put each folder where the file had it (see [Coming from Rojo](/docs/v2/coming-from-rojo)). A `default.project.json` in a folder inside a source path is a nested project, which makes that folder one instance, as in Rojo ([Nested Projects](/docs/v2/core-concepts/project-layout#nested-projects)). Other project files in the folder (`test.project.json`) are left alone: Rojo runs a plain project file as it is, and Rogen writes only the project files its `.rogen.json` files name. Rogen writes `default.project.json` from then on, so the next steps print `git rm --cached default.project.json` to stop git tracking the lifted file.

Then `init` builds the default config it wrote, so `default.project.json` exists before you run anything: `rojo serve` and `rbxtsc --rojo` find it, and the tools that read the file have it. A hand-written project file in the way is replaced by that build, which is why it was lifted first. The build prints as `build` does, with its warnings and their codes, except the ones about the compiled path, since the compiler hasn't run yet. If it fails, the files stay, the errors print, and `init` exits 1: fix the config and run `rogen build`. With `--json`, the document has the build's entry under `built`, shaped as in [`build --json`](#build---json). When it's done, `init` prints what to run next.

A first `init` also adds Rogen's [rules for coding agents](/docs/v2/agents) to `AGENTS.md`, or to `CLAUDE.md` when that's the only one, or writes a new `AGENTS.md`. In a terminal it asks first. It appends after what's already there and never touches a file that already holds the rules: a later `init` says `AGENTS.md already has Rogen's rules.` and exits 0, and it reports the hook and the Rojo pin the same way. A later `init` offers them under **Agent instructions** until they are there.

**Rojo.** `init` runs `rojo --version`, as `serve` does. When Rojo runs, or a toolchain file there or above already pins it, it does nothing. Otherwise:

- **A toolchain manager is there** (Rokit, Aftman or Foreman, or the manager of the folder's `rokit.toml`, `aftman.toml` or `foreman.toml`): a terminal run asks `Pin Rojo 7.7.1 with Rokit?` (Yes by default), writes the manager's file where the folder has none, and runs `rokit add rojo-rbx/rojo@7.7.1` (`aftman add …`; for Foreman, the line is written and `foreman install` runs). A run that can't ask does the same, since it only touches the project and the manager you already have.
- **Nothing is there:** a terminal run says `Rojo isn't installed, and rogen serve needs it.` and asks `Install Rokit and Rojo now?`. A Yes runs Rokit's own installer for the OS (the one-liner from Rokit's README, shown in the question), then `rokit add`. A run that can't ask installs nothing on the machine: it prints that one-liner as the next step, and `decided` has `rojo: "not installed"`. `--rojo` installs.

After a pin or an install, it asks `Install Rojo's Studio plugin?` (Yes by default) and runs `rojo plugin install`; a run that can't ask prints `rogen plugin install` instead, and `--studio-plugin` runs it. A command that fails is a warning that names what to run by hand, and `init` still finishes. The commands are in `--dry-run` and `--json` (`commands`), where each has the outcome `ran`, `wouldRun`, `failed` or `skipped`. With Darklua, the same step pins `seaofvoices/darklua` (0.19.0) beside Rojo when no toolchain file pins it and `darklua --version` doesn't run, so the printed `darklua process src dist --watch` works as soon as it runs; the next steps list it with `rogen serve`, one command per terminal. A later `init` offers **Rojo** until Rojo is ready, and `rogen init --rojo` or `--studio-plugin` do it on a folder that has a config.

Where it finds a coding agent (Claude Code, Codex, Gemini CLI, Cursor or Copilot, each by a folder or file it leaves in the project), a terminal run also offers an [agent hook](/docs/v2/agents#check-changed-files-automatically) that reports Rogen warnings about the files a turn changed: it writes `.agents/hooks/rogen-check.sh` and registers it in each agent's hook file. A later `init` lists it under **Agent hook**. A run that can't ask adds it only with `--agent-hook`, and `jq` is the one tool it needs besides `bash` and `git`.

#### Choices as flags

Every question has a flag, so a program that can't answer prompts can still choose. A flag given skips its question in a terminal too. Without one, a run that can't ask takes the default, says so (`Took the defaults: --language luau, --no-darklua, …`), and `--json` lists each default it took under `decided`, with the flag that changes it.

| Flag | Answers |
|---|---|
| `--kind place\|model\|plugin` | What a new project is. A place by default. |
| `--skip-git` | Write no `.gitignore` and run no `git init`. |
| `--language <id>` | `luau` or `roblox-ts`; detected from the folder otherwise. |
| `--[no-]darklua` | Whether Darklua processes your code. Found from its config otherwise. The second file that serves the processed code, `dist.rogen.json`, is written by hand. |
| `--source-path <path>` | A folder with your scripts. Repeat for several; one for roblox-ts. |
| `--compiled-path <path>` | With Darklua: the folder it writes into, `dist` by default. |
| `--project-file lift\|new` | With a hand-written `default.project.json`: lift its tree (the default) or start a new one. |
| `--package <path>` | A package folder to mount as it is. Repeat for several, or `none`. |
| `--route <id>` | A starting route: `server`, `client`, `shared`, `replicatedFirst`, `serverStorage` or `starterGui`. Repeat for several, or `none`. When a lifted project file already mounts a folder under one of these names, `server` means that route, which is also called `mount:server`. |
| `--unmatched shared\|leave` | Where files that match no route go. |
| `--[no-]agent-rules` | Rogen's rules for coding agents. Added by default. |
| `--[no-]agent-hook` | The hook that reports warnings to the coding agents found. Not added by default. |
| `--[no-]rojo` | Whether to set Rojo up when it isn't ready: pin it with the manager found, or install Rokit first. A run that can't ask pins with a manager it finds, and installs Rokit only with this flag. |
| `--[no-]studio-plugin` | Whether to install Rojo's Studio plugin once Rojo is set up. Not installed by a run that can't ask. |
| `--[no-]sample` | The Greeter sample of a new place. Written by default in a folder with no code. |
| `--[no-]places` | Whether a new project is several places: `src/common` and `src/game` with a config per place at the root in Luau, `projects/common` and `projects/game` in roblox-ts. One place by default, several where a `projects` folder is for roblox-ts. A new project only. |
| `--nested` | Start a project below another `default.rogen.json`. |

A flag with a value that doesn't fit is a `usage` [error](#errors) whose `hint` lists the values, as is `--agent-hook` with no coding agent here.

#### A folder that has a config

`init` starts projects; it never changes a config that exists. In a folder that has a `default.rogen.json`, it only adds what is missing around it: the agent rules, the agent hook, Rojo's pin and the Studio plugin. In a terminal it prints what the project has and asks `What do you want to change?` as a multi-select of **Agents** and **Tools**, when either has something to add. `--agent-rules`, `--agent-hook`, `--rojo` and `--studio-plugin` ask for them without one, and `-y` with no flag makes the safe additions that are missing: Rojo's pin when a toolchain manager is installed, and the agent rules. An addition that is already there is not an error: the run adds nothing and succeeds, so a script can repeat it.

The flags that answer a question of a new project (`--language`, `--kind`, `--skip-git`, `--project-file`, `--sample`, `--route`, `--unmatched`, `--source-path`, `--compiled-path`, `--darklua` and `--package`) are a `usage` error beside a config. To change the routes, the source paths, the packages or Darklua, edit the `.rogen.json` in place, which keeps its comments, then run `rogen check`. A `dist.rogen.json` or `release.rogen.json` is yours to keep in step with it, and `rogen list` shows how each differs.

`--dry-run` (`-n`) plans without writing or building: it prints the files it would write, and with `--json` the document of a real run with `dryRun: true`, `changed: false`, no `built`, and `wouldWrite` for the `outcome` of each file. Run `rogen init --dry-run --json` to see what `init` would do and decide, then pass flags for what to answer.

#### Adding a place

`rogen init projects/lobby`, run in a `projects` folder that holds a place already, adds the folder as a place, whether or not it exists. It writes `projects/lobby/default.rogen.json` as a complete file of its own: the `routes`, `compiledPath` and `tree` of the first place under `projects` that has a `default.rogen.json` (not `common`), its own `name`, and `../common/src` before `src` in `sourcePaths` when `projects/common` exists. When that place has a `dist.rogen.json` or `release.rogen.json`, `tsconfig.json` or `.darklua.json`, the new place gets its own copies. It writes no port and no place ID: the new place is served by naming it, and the next steps print how to serve it from a second terminal with `--port` (`rogen serve projects/lobby --port <port>`). It creates `projects/lobby/src` and builds the place's `default.project.json`. In a Luau project with places, `rogen init lobby` adds a place the same way. It adds one when the folder has `src/common` and a root-level `*.rogen.json` that lists `src/common` in its `sourcePaths`, and the name is a new folder directly below it: a path such as `somewhere/else`, or a folder that exists, starts a project there as it does in Rojo. It writes `lobby.rogen.json`, a complete file of its own with the `routes` and `tree` of the first place's config, its own `name`, and `src/common` and `src/lobby` as `sourcePaths`; and `src/lobby` with a `Lobby` script that greets with the shared module, or an empty folder with `--no-sample` or when `src/common` has no Greeter. A Darklua project also gets `lobby.dist.rogen.json` (and `lobby.release.rogen.json` when the first place has one), and the next steps print the one `darklua process src/lobby dist/lobby --watch` the new place needs, since the shared code is processed already. The editor setting is left alone: the next steps give the `generatorCommand` that makes luau-lsp read the new place. A place name has letters, digits, `-` and `_`, and isn't `default`. A `lobby.rogen.json` or `src/lobby` that exists is an error ([`init.configExists`](/docs/v2/diagnostics#init-configexists), [`init.fileExists`](/docs/v2/diagnostics#init-fileexists)), and nothing is written.

A folder with no place to copy, or one that has a config already, goes through the ordinary flow instead.

### `list [project…]`

Lists every `.rogen.json` file of the working directory (a default is not required), or the folders and files you name. Each prints its source paths, its resolved routes (`Server -> ServerScriptService`, one per line), its compiled path and its project file. With a compiled path, each source path prints the folder it is read from (`src -> out/src`), which is where the compiler has to write. A file other than `default.rogen.json` also prints how it differs from it, as `differs from default.rogen.json: compiledPath`, naming the keys with another value. It is information, not a warning: after you edit one file, run `rogen list` to see which of its siblings to bring in step. A project file that a running `rogen serve` serves has a `serving:` line after it, such as `serving: Rojo at 127.0.0.1:34872, 1 Studio connected` (or `no Studio connected`, or nothing after the address when the server doesn't say). A file that sets `servePort` or `servePlaceIds` shows them after the project file (`port 34880, place IDs 1818, 2020`). Each file ends with the Rojo command that serves it (`rojo serve default.project.json`, with `--port` when it sets a port), to run yourself when you need Rojo directly. It's the quickest answer to "what does this folder build?". With `--json`, each config is printed fully resolved, with every default filled in and every path made absolute.

### `fmt-project [project…]`

Formats the `default.rogen.json` of the working directory, or the projects you name, the way `rojo fmt-project` formats a project file: two-space indentation, no trailing newline, Rojo's keys first in Rojo's order, then the `rogen` block with `sourcePaths`, `routes` and `compiledPath`, then any other key. The children of the `tree` are sorted. It prints `formatted <file>` for each file it changed. Numbers in `$properties` and `$attributes` are written as Rojo writes them: a bare number is a float (`65.0`), and a typed value follows its type (`Vector3` and `Color3` hold floats, `Int32`, `Enum` and `BrickColor` whole numbers, a `UDim` a float scale and a whole offset), a `Font` gets its `cachedFaceId`, and the keys of a sync rule come in Rojo's order. A config with no `name` is named for its folder, as Rojo names a project file. The project files `build` writes are formatted the same way.

A file with comments or trailing commas is left as it is, since the formatted text has none, and a `.rogen.jsonc` always is: [`format.commentsLost`](/docs/v2/diagnostics#format-commentslost). The project files Rogen writes are already in this format.

### `doc [topic]`

Opens the documentation in your browser, and prints its address. Without a terminal (an agent, CI, a pipe) it only prints the address.

`rogen doc <topic>` prints one section of the reference from the version you have installed, offline: `routing`, `config`, `layout` or `output`.

### `help [name]`

Prints usage, or a command's arguments, options and examples, in the layout Rojo's help uses: the command's name, its description, then `USAGE:`, `ARGS:`, `OPTIONS:` (the global options merged in, sorted by name), `SUBCOMMANDS:` where there are some, and `EXAMPLES:`. The root help lists each command with a one-line summary, and descriptions and prose are wrapped at 100 columns, as Rojo wraps its help. `rogen help build`, `rogen build --help` and `rogen build -h` print the same. `rogen --version` prints the installed version.

`rogen help codes` lists every [diagnostic](/docs/v2/diagnostics) code on a line with its severity and meaning. `rogen help <code>` explains one, such as `rogen help route.strayAt`. The code may be typed in any case, or without its prefix when one code ends in it: `rogen help strayat` prints `route.strayAt`.

With `--json`, `help` answers a program: see [`help --json`](#help---json).

## The command picker

A bare `rogen` in a terminal opens a picker instead of printing the help, so a newcomer doesn't have to read a wall of text and type the command again. The first line says the version and the project (`rogen 2.0.0 · my-game`, or `no default.rogen.json here`). Below it is every command with its one-line summary: type to filter by name or summary, move with the arrow keys, and press Enter to run the one under the cursor. With no config here `init` comes first. Beside one, `serve`, `build`, `where` and `check` come first, so Enter does the obvious thing. `doc` and `help` come last. Escape or Ctrl+C leaves without running anything.

A command that can't run bare asks for what it lacks, and nothing else: `plugin` asks `install` or `uninstall`, `syncback` offers the `.rbxl`, `.rbxlx`, `.rbxm` and `.rbxmx` files it finds in the project (or a path you type) for `--input`, `upload` asks for the `--asset_id`, and `doc` offers its topics or the site. Every other command runs as it does from the shell. Before it runs, the picker says the command line it composed (`› rogen plugin install`), so next time you can type it; it runs that line and exits with its exit code. There are no flags in the picker: add them on the command line.

Without a terminal (a pipe, CI, a coding agent: the same test `init` uses to decide whether it can ask) a bare `rogen` prints the root help and exits 2, so scripts see what they see from Rojo. `rogen --help`, `rogen -h` and `rogen help` print the help everywhere.

## Options

Anything you want every time belongs in the `.rogen.json`. `where`, `check` and `list` take only `--json`.

| Flag | Effect |
|---|---|
| `--color <auto\|always\|never>` | Whether to colour the output: `auto` (the default) draws in a terminal; `never` prints plain lines, as `NO_COLOR` does; `always` draws even when output is piped. `--json` is always plain. |
| `--json` | Prints one JSON document for `build`, `sourcemap`, `upload`, `where`, `check`, `list`, `init`, `fmt-project`, `doc` and `help`, and one JSON object per line for `serve`, `build --watch` and `sourcemap --watch`. On `init` it implies `--non-interactive`. |
| `-o, --output <file>` | `build`: also builds the project into this place or model file with Rojo. `sourcemap`: writes the sourcemap there instead of printing it. |
| `-p, --plugin <name>` | `build` only: also builds the project into Roblox's plugins folder with Rojo. |
| `--watch` | `build` and `sourcemap`: keeps the project files current, and runs Rojo after each write and each edit of a file when `-o` or `-p` (`build`) asks for it, or always for `sourcemap`. |
| `--include-non-scripts`, `--absolute` | `sourcemap` only: Rojo's flags of the same name. |
| `--asset_id`, `--api_key`, `--universe_id`, `--cookie` | `upload` only: Rojo's flags of the same name, with its underscores. |
| `--non-interactive` | `init` only: writes the defaults without asking. |
| `-n, --dry-run` | `init` only: prints what it would write and decide, and writes nothing. |
| `--language`, `--[no-]darklua`, `--source-path`, `--compiled-path`, `--project-file`, `--package`, `--route`, `--unmatched`, `--[no-]agent-rules`, `--[no-]agent-hook`, `--[no-]rojo`, `--[no-]studio-plugin`, `--[no-]sample`, `--[no-]places`, `--nested` | `init` only: answer a question. See [Choices as flags](#choices-as-flags). |
| `-h, --help` | Prints help. |
| `-V, --version` | Prints the version. |
| `-v, --verbose` | Prints debug output; `-vv` also prints trace output. Rojo gets `-v` or `-vv` too, so its debug lines come back with Rogen's. |
| `-q, --quiet` | Prints errors only, plus anything you explicitly asked for and anything that makes the run fail. |

## Exit codes

| Code | Meaning |
|---|---|
| `0` | The command did its job, warnings included. `serve` exits 0 when another `rogen serve` already serves the project; a `serve` that a signal stops exits 128 plus its number (Ctrl+C is 130). |
| `1` | The project is wrong: a project that can't be found (a path that isn't there, a folder with no project), an invalid config, build errors, a failed write, a cancelled `init`, or any diagnostic `check` prints. For `serve`, also no server to start or a taken port. |
| `2` | The command line is wrong: an unknown command, option or option value, a combination that isn't allowed (`--verbose` with `--quiet`, words after `--` on a command other than `serve`, a second `[PROJECT]` on a command that takes one), or a help topic that doesn't exist. A Rojo that refuses the arguments Rogen passes on (`upload --asset_id abc`) exits 2, as Rojo does. |

When a server stops on its own, `serve` exits with the server's code. `--json` keeps the same codes, so a script can tell "fix the call" from "fix the project" without reading the message.

## Continuous integration

Warnings exit 0 on a developer's machine, but some should stop a merge, such as `route.serverCodeShipped` (server code replicating to clients), `tree.deadScript`, or the ones that drop or misplace a file (`tree.instanceClash`, `route.folderTypo`, `scan.portableName`). They stay warnings so that a build still produces a project file while you fix them, and `rogen check` is the gate that fails on them. `rogen check` exits 1 on any diagnostic, warnings included, and writes nothing. Every warning has a fix that removes it (a rename, a marker such as `@Shared`, or a config edit; see [Diagnostics](/docs/v2/diagnostics)).

```bash
# compile first when the config sets a compiledPath, or output.nothingEmitted warns
rogen check
```

- Run the compiler or processor before `rogen check` when `compiledPath` is set.
- With [Darklua](/docs/v2/setups/darklua), a data file it turns into a module keeps `output.dataFileConverted` alive until the file is copied unchanged into the compiled path.
- `check` also fails when you commit project files and one is out of date ([`output.differs`](/docs/v2/diagnostics#output-differs)), so no `git diff` step is needed.
- `where` answers a question without judging the project, so it exits 0. To judge only some paths, such as the files a pull request changes, run `rogen check <paths>`, which exits 1 on any diagnostic about them.
- A place file comes from `rojo build` on the project file; see [Place Files](/docs/v2/core-concepts/output#place-files).
- A clone has no project files when `*.project.json` is gitignored, as `init` writes it: run `rogen build` (or `rogen build <project>`) before the editor, a compiler or Rojo needs them.
- Whether to [commit the project files](/docs/v2/core-concepts/output#ignore-or-commit-the-project-files) is yours to decide.

### Annotations on GitHub

When GitHub Actions runs `build` or `check` (`GITHUB_ACTIONS` is `true`), each diagnostic is also written as a workflow command on stderr, which GitHub shows on the changed file of the pull request:

```
::warning file=src/Save@sever.luau,title=route.strayAt::did you mean "@Server"?
```

`title` is the diagnostic's [code](/docs/v2/diagnostics), and `file`, `line` and `col` are there when the diagnostic has them, with the path relative to `GITHUB_WORKSPACE`. A warning about several files, such as `route.strayAt`, makes one annotation for each file it names, all of them, where the text lists ten. The text output is unchanged, `--json` never carries workflow commands, and a run that is not on GitHub Actions writes none. GitHub shows only a limited number of annotations per step, so the log still holds the full list. Nothing needs to be turned on:

```yaml
- run: rogen check
- run: git diff --name-only --diff-filter=d origin/main... | xargs -r rogen check
```

## JSON output

`--json` prints exactly one JSON document on stdout, on one line without indentation (`serve` and `build --watch` print one object per line, see [`serve --json`](#serve---json)), even when the command fails or crashes, or the command line itself is wrong. A crash prints an `internal` error (see [Errors](#errors)), exits 1 and writes its stack trace to stderr. The [exit code](#exit-codes) is the same as without it. File paths are absolute and use the OS separator; instance paths and globs always use `/`.

Diagnostics look like this. Match on `code`, since the wording of `message` can change. `line` and `column` are omitted when the problem is a whole file. `url` points at the code's section on the [Diagnostics](/docs/v2/diagnostics) page.

```json
{
	"file": "/repo/default.rogen.json",
	"line": 3,
	"column": 2,
	"severity": "error",
	"code": "config.unknownField",
	"message": "\"outDir\" is not a Rojo key and not Rogen's, and Rojo rejects a project file with a key it doesn't know.",
	"url": "https://rogen-playfully.vercel.app/docs/v2/diagnostics#config-unknownfield"
}
```

A warning whose fix is one rename also has `fixes`, a rename for every name it covers, including names the message leaves out. Rogen never applies them: after a rename, update the requires and imports that name the file.

```json
"fixes": [
	{ "rename": { "from": "/repo/src/Inventory/Save@sever.luau", "to": "/repo/src/Inventory/Save@Server.luau" } }
]
```

An unknown config key, and a route target that doesn't start with a service, have a `replace` fix when a name is close: the file, the `line` and `column` where the text starts, the JSON text found there (`from`, quotes included) and the text to put in its place (`to`). It is offered only for a close match. Rogen never applies it.

```json
"fixes": [
	{ "replace": { "file": "/repo/default.rogen.json", "line": 2, "column": 2, "from": "\"sourcePath\"", "to": "\"sourcePaths\"" } }
]
```

A `serve` error whose fix is a command has a `run` fix instead: the command, and the folder to run it in. Rogen never runs them.

```json
"fixes": [
	{ "run": { "command": "rogen serve --port 34873", "cwd": "/repo" } }
]
```

The commands that write files, `build`, `fmt-project` and `init`, say so the same way: a top-level `changed` comes first, `true` when the run wrote anything, and each file has an `outcome` of `wrote`, `unchanged`, `failed` or `notWritten`. A program asks the same question of all three.

Every document is an object, and every entry says which config it is about, the same way. An entry that is a config has `config` (its project name) and `file` (the absolute path of its `.rogen.json`). An entry that belongs to a config, such as a location, has `config`. Identity comes first and `diagnostics` last.

A warning about several files, such as `route.strayAt` or `tree.deadScript`, is filed under the config and lists every file it is about in `related`, each with what it says about that file. The list is complete, while the text output stops at ten lines.

```json
"related": [
	{ "file": "/repo/src/Inventory/Save@sever.luau", "message": "did you mean \"@Server\"?" }
]
```

A diagnostic is about a file when its `file` is that file or `related[].file` includes it. A program that wants every warning about the files it just changed filters on that, instead of reading `message`.

If a command fails before it has anything else to report, you get `{ "diagnostics": [...] }`, or `{ "error": {...} }` for anything that isn't a diagnostic, never both.

### Errors

A failure that isn't a list of diagnostics prints `{ "error": { "kind", "message", "hint"? } }`. Branch on `kind`; `message` says what happened, and `hint` is there only when one next step can be named: the closest valid name, the command to run, the flag that bypasses a refusal.

```json
{"error":{"kind":"usage","message":"Unknown command \"biuld\".","hint":"Did you mean 'rogen build'?"}}
```

| `kind` | Exit code | Meaning |
|---|---|---|
| `usage` | 2 | The command line is wrong: an unknown command, option, option value or name. |
| `project` | 1 | The project isn't in a state the command can run on: no `default.rogen.json` or `default.project.json` where one is needed, a path that is not there, an `init` inside another project. |
| `tool` | 1 | A program Rogen needs is missing or failed, with no diagnostic to say more. A missing or failing Rojo is a diagnostic with the command that fixes it. |
| `io` | 1 | A file or directory couldn't be read or written. |
| `cancelled` | 1 | The run was cancelled, such as an `init` the user declined. |
| `internal` | 1 | A bug in Rogen; `message` says where to report it. |

### `build --json`

```json
{
	"changed": true,
	"configs": [
		{
			"config": "my-game",
			"file": "/repo/default.rogen.json",
			"projectFile": "/repo/default.project.json",
			"outcome": "wrote",
			"diagnostics": []
		}
	]
}
```

`outcome` is `wrote`, `unchanged` or `notWritten`. If any config fails, nothing is written.

With `-o` or `-p`, the document also has `rojo`, the Rojo build that ran after the files were written:

```json
{
	"command": "build",
	"outcome": "built",
	"project": "/repo/default.project.json",
	"output": "/repo/game.rbxl",
	"messages": [{ "severity": "info", "text": "Built project to game.rbxl" }]
}
```

`outcome` is `built`, `failed` or `notRun`: Rojo isn't run when the project files have errors, and then `project` is `null`. `output` is the absolute path `-o` names, and `plugin` is the name `-p` gives (one of the two). `messages` is what Rojo said, with `severity` `error`, `warning` or `info`. A failed run has `diagnostics` with `rojo.commandFailed` (or what kept Rojo from starting), and the exit code is 1.

A config that doesn't load is an entry like the others: `projectFile` is `null`, `outcome` is `notWritten`, and its `diagnostics` say why.

### `sourcemap --json`

```json
{
	"changed": true,
	"configs": [
		{
			"config": "my-game",
			"file": "/repo/default.rogen.json",
			"projectFile": "/repo/default.project.json",
			"outcome": "unchanged",
			"diagnostics": []
		}
	],
	"sourcemaps": [
		{
			"command": "sourcemap",
			"outcome": "built",
			"project": "/repo/default.project.json",
			"output": "/repo/sourcemap.json",
			"messages": [
				{ "severity": "info", "text": "Created sourcemap at sourcemap.json" }
			]
		}
	]
}
```

`configs` is as in [`build --json`](#build---json). `sourcemaps` has an entry for the Rojo run, shaped as [`rojo` in `build --json`](#build---json) with `command` `sourcemap`, and `outcome` `built` when Rojo wrote the file. `changed` is true when a project file was written or a sourcemap was. With `--watch`, it prints one JSON object per line as [`build --watch --json`](#build---watch) does.

### `upload --json`

```json
{
	"changed": false,
	"configs": [
		{
			"config": "my-game",
			"file": "/repo/default.rogen.json",
			"projectFile": "/repo/default.project.json",
			"outcome": "unchanged",
			"diagnostics": []
		}
	],
	"rojo": {
		"command": "upload",
		"outcome": "built",
		"project": "/repo/default.project.json",
		"messages": []
	}
}
```

`configs` is as in [`build --json`](#build---json), and `rojo` is shaped as `rojo` in it, with `command` `upload`. `outcome` is `built` when Rojo exited without an error, `failed` when it did not, and `notRun` when the project files had errors. The flags you gave are not in it.

### `syncback --json`

```json
{
	"changed": true,
	"configs": [
		{
			"config": "my-game",
			"file": "/repo/default.rogen.json",
			"projectFile": "/repo/default.project.json",
			"outcome": "unchanged",
			"diagnostics": []
		}
	],
	"syncback": {
		"outcome": "written",
		"project": "my-game",
		"input": "game.rbxl",
		"changes": [
			{ "kind": "write", "file": "/repo/src/Quest/Server/Main.luau" },
			{ "kind": "remove", "file": "/repo/src/Combat/Server/Hit.luau" }
		],
		"unplaced": []
	}
}
```

`configs` is as in [`build --json`](#build---json). `syncback.outcome` is `written` when the run wrote, `planned` for `--dry-run`, `failed` when it did not, with `diagnostics` or `error` as a failed run prints, and `notRun` when the project files had errors. `changes` are the files written and removed, at the places the new ones were put; `unplaced` has the `instance` and the `reason` of each instance left out. A file placed where the build puts it elsewhere is a diagnostic in `syncback.diagnostics`.

### `fmt-project --json`

```json
{
	"changed": true,
	"files": [
		{ "file": "/repo/default.rogen.json", "outcome": "wrote", "diagnostics": [] }
	]
}
```

One entry per config file it looked at. `outcome` is `wrote`, `unchanged` or `failed`, and a failed file's `diagnostics` say why ([`format.commentsLost`](/docs/v2/diagnostics#format-commentslost) for a file with comments). The exit code is 1 when any file failed; the others are still formatted.

### `doc --json`

`rogen doc --json` prints `{ "url": "...", "topics": ["routing", "config", "layout", "output"] }` and opens nothing. `rogen doc <topic> --json` prints `{ "topic": "routing", "text": "..." }`, the text as `rogen doc routing` prints it. An unknown topic is a `usage` [error](#errors) and exit 2.

### `serve --json`

One JSON object per line on stdout, each keyed by what it reports, and nothing else: what the server says is an `output` line too.

```json
{"build": {"config": "my-game", "file": "/repo/default.rogen.json", "projectFile": "/repo/default.project.json", "outcome": "wrote", "diagnostics": []}}
{"serving": {"config": "my-game", "server": "rojo", "version": "7.7.1", "project": "my-game", "host": "127.0.0.1", "port": 34872, "session": "f7771777-…"}}
```

| Key | When | Fields |
|---|---|---|
| `build` | each config, on every build | the entry [`build --json`](#build---json) lists |
| `notice` | a config is added, removed, broken or recovered | `kind` (`added`, `removed`, `broken` or `recovered`), `file`; a broken config adds `keptLastValid` and `diagnostics` |
| `serving` | a server answers, so Studio can connect | `config`, `server`, `version`, `project`, `host`, `port`, `session` (Rojo only), `reportsConnections` (whether `connected` and `disconnected` lines follow from this process: false for `alreadyRunning`, which exits at once); `alreadyRunning: true` when it was already serving before `serve` started |
| `connected`, `disconnected` | a Studio plugin connected to a server this serve started, or left it | `config`, `server`, `project`, `port`, `clients`, how many are connected now. Only a server that reports them, which the `serving` line says with `reportsConnections` |
| `output` | a server prints a warning, an error or a line Rogen doesn't recognise | `config`, `server`, `severity` (`error`, `warning` or `info` for an unrecognised line), `message` |
| `refused` | a config to serve, added or edited while serving, can't be served because its port is taken. The others go on, and so does the server it already has, if any | `config`, `server`, `diagnostics` |
| `stopped` | a server stops | `config`, `server`, `reason`: `exited` when it stopped on its own, with its `code` and `signal`; `removed` or `moved` when its config was deleted, or moved to another address (a `serving` line follows for the new server); `shutdown` when `serve` was asked to stop, as the last lines of a clean run |
| `error` | an unexpected failure that `serve` survives | the message |

`project` is the name in the project file, not the config's. When a run fails, the last line is `{ "diagnostics": [...] }` or `{ "error": {...} }`, as for other commands. A server that stops with a non-zero code adds a `diagnostics` line with [`serve.serverExited`](/docs/v2/diagnostics#serve-serverexited).

### `check --json`

An object with a `diagnostics` array: the entries described above, one per diagnostic about the paths (or, with none, about the project), each once. The exit code is 1 when it isn't empty.

### `where --json`

An object with a `locations` array and a `diagnostics` array. `diagnostics` holds the errors of a config that didn't load (the exit code is then 1), then the `output.differs` warnings of project files that are out of date, and is empty otherwise. `locations` has one entry per path, each with `config`, `status` and `source`, plus:

| `status` | Fields |
|---|---|
| `placed` | `instancePath` (an array of names), `require`, `route`, `routeMatch`, and `hoisted: true` for a `^` name |
| `replaced` | `by`, the file that took its instance path |
| `displaced` | `instancePath`, the tree node's path |
| `mounted` | `mount`, the tree node whose `$path` mounts it, and `instancePath`, the instance Rojo makes of the file, when it makes one |
| `ignored` | `pattern`, the glob that matched |
| `unrouted`, `outside`, `notInstance`, `missing`, `empty`, `skipped` | none |
| `noFile` | `instance` instead of `source`: no file places an instance you asked about. `folders` lists where a new file for it goes, when files are placed beside it or a route and a source path make one. `fixes` lists the renames, in the shape diagnostics use, after which a file would place it |

Every entry with a `source` has `exists`, after `status`: `true` when the path is there now, `false` when `where` placed it as it would be once created, in a folder that exists or one that doesn't. A `noFile` entry has none.

Every entry also has `diagnostics`, last: the diagnostics about its path (the ones whose `file` is the path, or whose `related` lists it), empty for a clean path. A grouped diagnostic is narrowed to the path: its `message` is the `related` message about this path and `fixes` holds only the renames of this path. A `noFile` entry has none.

`require` is the Luau expression that reaches the module, such as `game:GetService("ReplicatedStorage").Shared.Inventory.Types`, with `["Foo Bar"]` for a name that isn't an identifier or is a reserved word. It is there only for a placed Luau module. A Script has none, nor does a roblox-ts source, which you import by relative path, nor anything under `StarterPlayerScripts`, `StarterCharacterScripts`, `StarterGui` or `StarterPack`, because Roblox clones those into the player at runtime and the edit-time path names the template. `rogen where <file> --verbose` prints it in text.

`routeMatch` is `folder`, `marker`, `suffix`, `fallback`, `init` (the route suffix of an init script in one of its folders) or `copy` (an init script placed where its folder's other files route it).

```json
}
```

`decided` lists each choice a run that couldn't ask took for itself, with the flag that changes it; it leaves out what a flag answered. `files` lists what was written, in order, and marks with `appended` the ones that existed and had something added: Rogen's agent rules at the end, the hook in an agent's hook file, or Rojo's pin in `rokit.toml`. `commands` lists what `init` ran after the files (`rokit add`, an installer, `rojo plugin install`), each with the outcome `ran`, `wouldRun`, `failed` (with the `error`) or `skipped` (an earlier one failed). `present` lists the additions the project has already (`agentRules`, `agentHook`, `rojo`), each with its file and `state: "present"`; it is left out when there are none. `directories` lists the source paths `init` created because they didn't exist; one that already existed is left alone and not listed. `built` has the entry of the config it wrote, as `build --json` does, without the compiled path's warnings; if one has errors, the exit code is 1. `notes` is what `init` said along the way, and `warnings` lists what it could not do as asked, each a [diagnostic](#errors) with a code (such as `init.settingsDropped`, for settings of a lifted node that the config has no place for); it is left out when there are none. In `nextSteps`, `setup` holds one-time edits, `run` the long-running commands (one terminal each), `darklua` the processing commands, and `edits` suggested changes to the new files. If a write fails, you get `{ "files": [...], "error": {...} }`.

### `help --json`

Offline, in two steps, so a program reads only what it asks for. Every document is generated from the table the text help comes from, and the text help is unchanged.

`rogen help --json` is the tree: `version`, `commands`, `globalOptions`, `exitCodes` and `errorKinds`. Each command has its `name`, `summary` (the line the root help lists), `args` (`name`, and `optional` or `variadic` when true), `options` (`name`, `short`, `type`, and `multiple` when true) and `effects`: what a run can do beyond printing, from `writesFiles`, `runsProcesses`, `opensBrowser` and `longRunning`. A command with none of them only reads.

`rogen help <command> --json` adds the `description`, the descriptions of the arguments and options, the `examples`, the `exitCodes` of the command (the general table, with what the command says differently: `check` exits 1 on a warning), and the shape of what the command prints with `--json` as `output` (`document` for one document, `lines` for a command that prints one line per event). `rogen <command> --help --json` prints the same, and `rogen --help --json` the tree. The shapes are written compactly: `{a:string,b?:int}` is an object whose `b` may be left out, `[T]` an array, `A|B` either shape, `{*:T}` an object of any keys, and a capitalised name such as `Diagnostic` a shape that `shapes` writes out once.

```json
{"name":"check","summary":"…","description":"…","args":[…],"options":[…],"effects":[],"examples":["rogen check src --json"],"output":{"document":"{diagnostics:[Diagnostic],stoppedBy?:[Diagnostic]}"},"shapes":{"Diagnostic":"{file:string,line?:int,…}"}}
```

`rogen help <code> --json` prints `{ "code", "text", "url" }`: the text `rogen help <code>` prints, and the link to its section of the [Diagnostics](/docs/v2/diagnostics) page. `rogen help codes --json` prints `{ "codes": [...] }`, every code at once with its `severity`, the first sentence of what it `summary` means and its `url`, so a program can look codes up without the network; the text form prints one code per line. That is about 23 KB for all of them, so `rogen help codes route --json` lists only the codes that start with `route`. A name that is neither a command nor a code is a `usage` [error](#errors) whose `hint` names the closest one.

### `list --json`

An object with a `configs` array, one entry per `.rogen.json` file. Every entry has `config`, `file`, `status` (`valid` or `broken`) and `diagnostics`, and a file other than `default.rogen.json` has `differsFromDefault`, the keys whose value differs from the default's. A config that resolved also has `projectName` (the name Rojo shows), `sourcePaths`, `commonRoot`, `routes`, `globIgnorePaths`, `compiledPath`, `compiledLayout` (each source path and the compiled folder it is read from; empty without a compiled path), `projectFile` and `serving` (the `server`, `host` and `port` of the server a running `rogen serve` serves its project file with, and `clients`, how many Studio plugins are connected, `null` when the server doesn't say), with `null` for anything unset. `port` and `placeIds` are there when the file sets `servePort` or `servePlaceIds`, and `rojo` is the command that serves it, as a list of arguments with the project file's absolute path and `--port` when it has one. A broken config has only the first four. If a config has errors, the exit code is 1. `diagnostics` of a valid config holds [`scan.missingSourcePath`](/docs/v2/diagnostics#scan-missingsourcepath) for each source path that is no folder now: an error each when none is, since `build` would fail, else a warning each, and [`output.differs`](/docs/v2/diagnostics#output-differs) for the project file on disk when it differs from what `build` would write. `list` only reports them and exits 0.

## Output

In a terminal, Rogen draws a framed layout. It prints plain lines instead in pipes and redirects, with `NO_COLOR` or `TERM=dumb`, and when CI or a coding agent runs it.

Only `init` asks questions, and only when stdin and stdout are both terminals and nothing says a program is on the other end. A run that can't ask takes the defaults, as `--non-interactive` does, unless a flag answers the question. Rogen treats the run as CI or an agent when `CI`, `AGENT` or `AI_AGENT` is set (`0` and `false` don't count), or when an agent's harness sets its own variable for the commands it runs: `CLAUDECODE` (Claude Code), `CODEX_SANDBOX` or `CODEX_THREAD_ID` (Codex), `CURSOR_AGENT` (Cursor), `GEMINI_CLI` (Gemini CLI), `COPILOT_AGENT` (GitHub Copilot), `OPENCODE` (OpenCode) or `CLINE_ACTIVE` (Cline). What a command prints doesn't change otherwise.

In the commands that run Rojo (`build -o`, `sourcemap`, `upload`, `syncback`, `plugin`, `serve`), stdout carries what Rojo's stdout carries, line for line and without a prefix (`Building project 'Game'`, `Created sourcemap at sourcemap.json`, the `syncback --list` lines, `serve`'s "Rojo server listening" block). Rogen's own lines (the frame, `default.project.json · wrote`, `Built 1 project.`, `Serving Game…`) go to stderr when stdout isn't a terminal, and `--json` prints its one document on stdout as before.

Short options take their value after a space or after `=`: `-o game.rbxl` and `-o=game.rbxl` are the same.

Diagnostics use the familiar `file:line:col - severity: message` shape, so editors and CI can parse them. A warning about several files is one block in `build`, `build --watch` and `serve`, and its first line names the config. For one line per file, which is what an editor task or a CI annotation should read, use [`rogen check`](#check-path) or `--json`.

## Update notice

When a newer stable release is out, Rogen prints one line on stderr after a command in a terminal, naming the fix for how you installed it: the pin to change in `rokit.toml`, `aftman.toml` or `foreman.toml` and the install command to run after, the `npm i` command (`npm i -g` for a global install), or a link to the release.

```text
Rogen 2.0.3 is out (you have 2.0.0). Update the pin in rokit.toml: rogen = "ldgerrits/rogen@2.0.3". Then run rokit install.
```

`build --watch` and `serve` print it once, before the first build. A prerelease hears about later prereleases as well. It says nothing under CI or an agent (the run [described above](#output) as automated), in a pipe, with `--json`, with `--quiet`, or for `--version` and `help`, and it names each version once a day.

This is the one time Rogen goes on the network unasked. It reads GitHub's list of Rogen releases, in the background and at most once a day, and keeps the answer in a file in your cache folder (`$XDG_CACHE_HOME`, else `~/Library/Caches` on macOS, `%LOCALAPPDATA%` on Windows or `~/.cache`). The line comes from what the last check found, so no command waits for the network to print; a command that ends before a check does stays open for it, two seconds at most. An offline machine, a rate limit or a bad reply print nothing. Set `ROGEN_NO_UPDATE_CHECK=1` or `NO_UPDATE_NOTIFIER=1` to stop both the request and the line.
