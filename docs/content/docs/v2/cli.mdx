```bash
rogen [command] [name…] [options]
```

The first word is always a **command**, and a bare `rogen` runs `build`. Everything after the command is a config name, so `rogen build lobby` builds `lobby.rogen.json`. That keeps command names and config names from ever clashing.

<Callout type="info">
	`rogen lobby` isn't a shortcut. It's an error, and Rogen suggests `rogen build lobby` instead.
</Callout>

## Commands

### `build [name…]`

Writes the project file for each named config. It's the default command. You can build several configs at once, as long as no two of them write the same file.

If the working directory has other `*.rogen.json` files, `build` lists the ones you didn't ask for. That matters most in a Darklua setup, where one config feeds Studio and the other feeds Darklua and forgetting either one is easy. `rogen build --all` builds every config in the folder.

### `watch [name…]`

Builds, then rebuilds whenever your files or configs change. Only names matter, so editing the inside of a script never triggers a rebuild.

A config is reloaded when it changes, when anything in its `extends` chain changes, or when its template does, and CLI overrides carry over. If you save an invalid config, `watch` prints the error and keeps using the last valid version, so a broken `prod.rogen.json` won't hold up `default.rogen.json`.

Each rebuild prints a block that starts with the time and what triggered it:

```
┌  rogen watch · default, lobby
│
◇  12:04:31 · 2 files changed
│  ✔ default.project.json · wrote
│  ■ lobby.project.json · not written
│  ■ /repo/lobby.project.json - error: …
│
◇  12:05:02 · default.rogen.json changed · reloaded
│  ✔ default.project.json · unchanged
```

It's safe to run `build` while `watch` is going. Press Ctrl+C to stop.

### `where [path…]`

Shows where each file lands in the game and why, without writing anything. You get one line per file, sorted if you don't pass a path:

```
$ rogen where src/Net src/Combat/Server/Hit.luau
src/Net/Http.luau -> ReplicatedStorage/Shared/Net/Http · route * (fallback)
src/Net/Http.mock.luau -> pruned · variant mock is off (suffix)
src/Net/Remotes@server.luau -> ServerScriptService/Net/Remotes · route Server (suffix)
src/Net/Types.lua -> replaced by src/Net/Types.luau
src/Combat/Server/Hit.luau -> ServerScriptService/Combat/Hit · route Server (folder)
```

`where` maps files, not folders. Passing a directory is shorthand for every file inside it, and the directory itself doesn't get a line (unless the template mounts it, in which case it gets a single `mounted` line). With no path at all, `where` maps every file in the tree.

It also works backwards. If an argument starts with a service, it's read as an instance, written either the way Studio prints it or with slashes, and `where` prints the files placed at or inside it. You can paste the start of an error message straight in, because a leading `game.` and everything from the line number on are ignored:

```
$ rogen where "ServerScriptService.Combat.Hit:12: attempt to index nil"
src/Combat/Server/Hit.luau -> ServerScriptService/Combat/Hit · route Server (folder)
```

If nothing places the instance, `where` says `no file places it`. (If the working directory happens to have a folder named after the service, the argument is read as that path instead.)

For a placed file, the line shows its instance path, the governing route, how it matched (`folder`, `marker`, `suffix` or `fallback`) and any active variants. For a file that isn't placed, it tells you why:

- `pruned` by a dormant variant,
- `replaced by` the file that took its name,
- `displaced` by a template node,
- `mounted` by a template `$path`, which Rojo reads as it is,
- `unrouted`,
- `excluded`, with the glob that matched,
- `outside the root dirs`.

Because Rogen only looks at names, `where` can place a path that doesn't exist yet, so you can check before you create a file.

Unlike other commands, `where` takes paths rather than config names. It reads the default config; pick others with `-c` or `--all`, and switch variants with `--variant` and `--no-variant`. When several configs agree on a line it's printed once, and otherwise once per config under its name. Add `--json` to get the answer as data (see [JSON output](#json-output)).

### `init [name]`

Writes a starting `<name>.rogen.json`, or `default.rogen.json` if you don't give a name. It detects the language (roblox-ts if there's a `tsconfig.json`, Luau otherwise), Darklua and your package manager, and writes what it found into the config. This is the only time Rogen detects anything; builds just do what the config says.

In a terminal, `init` asks a few questions, and pressing Enter at each one gives you the defaults. On a first run it asks whether you're setting up one place or several (several if `places/` has folders in it). If `default.rogen.json` already exists, it asks whether to add a **place**, a config that **extends** default, or a separate config.

Without a terminal, or with `--json`, it takes the defaults without asking. Next to an existing `default.rogen.json`, that means `rogen init lobby` adds a place with its code in `places/lobby`, and a bare `rogen init` fails because a place needs a name.

`init` never overwrites a file or touches `.gitignore` and editor settings. If a hand-written project file like `default.project.json` is in the way, it's copied to `template.project.json` first so nothing is lost. When it's done, `init` prints what to run next.

### `list [name…]`

Lists every `*.rogen.json` in the working directory, with its root directories, sync directory, project file and active variants. Since every combination is its own config file, this answers the question "what can this repo build?".

Name configs to list just those, or use `-c`, `--all`, `--variant` and `--no-variant` to pick configs and switch variants first. With `--json`, each config is printed fully resolved, with every default filled in and every path absolute, which is the easiest way to see the common root or follow an `extends` chain.

### `help [command]`

Prints usage, or the details of one command.

### `version`

Prints the installed version.

## Options

An **override** replaces a config value for a single run; anything you want every time belongs in the file. `build` and `watch` accept all of the flags below. `where` and `list` only take the ones that pick configs and switch variants: `--all`, `-c`, `--variant` and `--no-variant`.

### `--all`

Uses every `*.rogen.json` in the working directory, as if you'd named each one. It can't be combined with names or `-c`, and like naming several configs, it rules out `-o`, `-s` and `--template`.

### `-c, --config <path>`

Points at a config file directly, for configs the naming rule can't reach. Repeatable.

### `-o, --out-file <path>`

Overrides `outFile`.

### `-s, --sync-dir <path>`

Overrides `syncDir`.

### `--template <path>`

Overrides `template`. It has no short flag.

### `--variant <name>`

Turns a variant on. Repeatable.

### `--no-variant <name>`

Turns a variant off. Repeatable.

<Callout type="info">
	`-o`, `-s` and `--template` change a single config, so they can't be used when building several. A variant flag applies to every config being built that declares the variant, and is only an error if none of them do.
</Callout>

### `--json`

For `build`, `where`, `list` and `init`. Prints a single JSON document on stdout instead of text, for other programs to read. See [JSON output](#json-output).

### Global options

| Flag | Description |
|---|---|
| `-h, --help` | Prints help. |
| `-v, --version` | Prints the version. |
| `--verbose` | Prints debug output. Can't be combined with `--quiet`. |
| `-q, --quiet` | Prints errors only. Can't be combined with `--verbose`. |
| `--no-input` | Never asks questions, and prints plain lines. |

`--quiet` never hides output you asked for explicitly, like help, the version or a `--json` document.

## JSON output

`--json` replaces a command's text with a single JSON document on stdout. The exit code stays the same, and failures print a document too, so a program can always parse stdout. Nothing else is written there, and `--quiet` and `--verbose` have no effect. Even a mistake on the command line itself, like an unknown flag, prints `{ "error": "..." }`, because `--json` is read before the rest of the line.

File paths are absolute and use the operating system's separator, so they contain backslashes on Windows. Instance paths and glob patterns aren't file paths, so they keep `/`. Each diagnostic is an object; match on its `code`, because the wording of `message` may change:

```json
{
	"file": "/repo/default.rogen.json",
	"line": 3,
	"column": 2,
	"severity": "error",
	"code": "config.unknownField",
	"message": "unknown field \"outDir\"."
}
```

`line` and `column` are left out when a diagnostic is about a whole file or folder. If a command fails before it has anything to report (say, because a config is invalid or missing), the document is `{ "diagnostics": [...] }`, or `{ "error": "..." }` for problems that aren't diagnostics.

### `build --json`

```json
{
	"configs": [
		{
			"file": "/repo/default.rogen.json",
			"outFile": "/repo/default.project.json",
			"outcome": "wrote",
			"diagnostics": []
		}
	],
	"notBuilding": ["/repo/lobby.rogen.json"]
}
```

`outcome` is `wrote`, `unchanged` or `notWritten`. If any config fails, nothing is written, and every config comes back `notWritten` with its own diagnostics. `notBuilding` lists the configs in the folder that this run wasn't asked to build.

### `where --json`

An array with one entry per config and path, in the same order as the text output but with nothing folded together. Every entry has `config`, `status` and a `source` path, plus fields that depend on the status:

| `status` | Fields |
|---|---|
| `placed` | `instancePath` (an array of names), `route`, `routeMatch`, `variants` |
| `pruned` | `variants`, the dormant ones |
| `replaced` | `by`, the file that took its instance path |
| `displaced` | `node`, the template node's path |
| `mounted` | `node`, the template node whose `$path` mounts it |
| `excluded` | `pattern`, the glob that matched |
| `unrouted`, `outside`, `ignored`, `missing`, `empty`, `skipped` | none |
| `noFile` | `instance` instead of `source`: no file places an instance you asked about |

`routeMatch` is `folder`, `marker`, `suffix` or `fallback`. Each entry in `variants` looks like `{ "variant": "mock", "form": "suffix" }`, where `form` is `folder`, `marker` or `suffix`.

### `init --json`

```json
{
	"files": ["/repo/lobby.rogen.json", "/repo/tsconfig.lobby.json"],
	"notes": [],
	"nextSteps": {
		"setup": ["Add \"include\": [\"src\"] to tsconfig.json, so its own build leaves out the place folders."],
		"run": ["rbxtsc -w -p tsconfig.lobby.json --rojo lobby.project.json", "rogen watch lobby", "rojo serve lobby.project.json"],
		"darklua": [],
		"edits": ["Declare variants under \"variants\" in lobby.rogen.json to swap in files like Analytics.mock.ts."]
	}
}
```

`files` lists what was written, in order. `notes` holds what `init` said before writing, such as keeping a hand-written project file as the template. `nextSteps` groups what to do next:

- `setup`: one-time edits to make before anything runs,
- `run`: the long-running commands, each needing its own terminal,
- `darklua`: the commands that process code into the sync directory,
- `edits`: what to change in the files that were written.

If a write fails, the document is `{ "files": [...], "error": "..." }`, listing whatever was written before the failure.

### `list --json`

An object keyed by each config file's absolute path. Every value has `extends` (the parents, nearest first) and `diagnostics`. A config that resolved also has `name`, `rootDirs`, `commonRoot`, `routes`, `variants`, `exclude`, `template`, `syncDir` and `outFile`, with `null` for an unset `template`, `syncDir` or `commonRoot`. A config with errors only has `extends` and `diagnostics`; the others still print, and the exit code is 1.

## Output

In a terminal, Rogen draws a framed layout with symbols. Anywhere else (CI, pipes, redirects) it prints plain lines with no gutter or color, so anything that greps the output keeps working.

It also switches to plain lines and stops asking questions when the `CI` environment variable is set to anything other than empty, `0` or `false`, when `TERM` is `dumb`, or when you pass `--no-input`. That last one is useful when a tool runs Rogen in a pseudo-terminal, where `init` would otherwise sit waiting for answers.

A build result line reads `<file> · wrote`, `<file> · unchanged` or `<file> · not written`. Diagnostics follow on their own lines in the usual `file:line:col - severity: message` shape, so editors and CI can parse them, with the file relative to the working directory. A warning about a source file points at that file, one line each. A command that fails prints the error inside the frame and exits with 1.
