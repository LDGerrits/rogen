```bash
rogen [command] [name…] [options]
```

The first positional is always a **command**, and a bare `rogen` runs `build`. Everything after it is a config name: `rogen build lobby` builds `lobby.rogen.json`. Because of that, a command name can never clash with a config name.

<Callout type="info">
	`rogen lobby` is an error, not a shortcut. Rogen suggests `rogen build lobby` instead.
</Callout>

## Commands

### `build [name…]`

Writes the project file for each named config. This is the default command. You can build several configs in one go, but two configs writing the same file is an error.

If the working directory has other `*.rogen.json` files, `build` lists the ones you didn't ask for. In a Darklua setup one config feeds Studio and the other feeds Darklua, so forgetting either should be obvious. `rogen build --all` builds every config there is.

### `watch [name…]`

Builds, then rebuilds whenever sources or configs change. Only file names and folders matter, so editing what's inside a script never triggers a rebuild.

`watch` reloads a config when it changes, when anything in its `extends` chain changes, or when its template does. CLI overrides survive a reload. If you save an invalid config, `watch` prints the error and keeps building that config with its last valid version, so a broken `prod.rogen.json` doesn't stop `default.rogen.json`.

Each rebuild prints a block that starts with the time and what triggered it:

```
┌  rogen watch · default, lobby
│
◇  12:04:31 · 2 files changed
│  ✔ default.project.json · wrote
│  ■ lobby.project.json · not written
│  ■ /repo/lobby.project.json - error: …
│
◇  12:05:02 · default.rogen.json changed · reloaded
│  ✔ default.project.json · unchanged
```

It's safe to run `build` while `watch` is going; see [Building While Watching](/docs/v2/core-concepts/output#building-while-watching). Press Ctrl+C to stop.

### `where [path…]`

Shows where each file lands in the game and why, without writing anything. It prints one line per file, sorted when you don't pass a path:

```
$ rogen where src/Net src/Combat/Server/Hit.luau
src/Net/Http.luau -> ReplicatedStorage/Shared/Net/Http · route * (fallback)
src/Net/Http.mock.luau -> pruned · variant mock is off (suffix)
src/Net/Remotes@server.luau -> ServerScriptService/Net/Remotes · route Server (suffix)
src/Net/Types.lua -> replaced by src/Net/Types.luau
src/Combat/Server/Hit.luau -> ServerScriptService/Combat/Hit · route Server (folder)
```

`where` maps files, not folders. A directory is shorthand for the files inside it and never gets a line of its own, except a folder the template mounts, which gets one `mounted` line. With no path, it maps every file in the tree.

It also works backwards. An argument that starts with a service is read as an instance, written the way Studio prints it or with slashes, and `where` prints the files placed at it or inside it. You can paste the start of an error line as it is, since a leading `game.` and everything from the line number on are dropped:

```
$ rogen where "ServerScriptService.Combat.Hit:12: attempt to index nil"
src/Combat/Server/Hit.luau -> ServerScriptService/Combat/Hit · route Server (folder)
```

If no file places an instance, `where` says `no file places it`. That includes the template's own nodes, such as package mounts. If the working directory has a folder named after the service, the argument is read as that path instead.

For a placed file, the line shows its instance path, the governing route, how it matched (`folder`, `marker`, `suffix` or `fallback`), and any active variants. For a file that isn't placed, it says why:

- `pruned` by a dormant variant,
- `replaced by` the file that took its name,
- `displaced` by a template node,
- `mounted` by a template `$path`, which Rojo reads as it is,
- `unrouted`,
- `excluded`, with the glob that matched,
- `outside the root dirs`.

Since Rogen only reads names, `where` can place a path that doesn't exist yet, so you can check before you create a file.

An init folder is one instance: its init script gets the folder's line, and every other script below it is a child.

Here, positionals are paths, not config names. `where` reads the default config; pick others with `-c` or `--all`, and switch variants with `--variant` and `--no-variant`. With several configs, a line is printed once if they all agree, and otherwise once per config under its name. Add `--json` to get the answer as data (see [JSON output](#json-output)).

### `init [name]`

Writes a starting `<name>.rogen.json`, or `default.rogen.json` with no name. It detects the language (roblox-ts if there's a `tsconfig.json`, Luau otherwise), Darklua and packages once, and writes what it found as plain fields. Builds never guess.

In a terminal, `init` asks a few questions first, and pressing Enter at each one gives you the same files a non-interactive `init` would write. On a first run, it asks whether you're setting up one place or several. If there are folders in `places/`, it defaults to several and writes one config per place that extends `default`. When `default.rogen.json` already exists, it asks what to add: a **place**, a config that **extends** default, or a separate config.

Without a terminal, it takes those same defaults. So next to an existing `default.rogen.json`, `rogen init lobby` adds a place called `lobby` with its code in `places/lobby`, and a bare `rogen init` fails, because a place needs a name. A config that only extends default is a single line you can write yourself: `{ "extends": "./default.rogen.json" }`. With `--json`, `init` never asks either, and prints what it wrote and the next steps as data (see [JSON output](#init---json)).

`init` checks your answers as you type them: root directories can't nest or repeat, and a roblox-ts project takes only one. It never overwrites a file, and never touches `.gitignore` or editor settings. If there's a hand-written project file, like `default.project.json`, that a build would replace, `init` first copies it to `template.project.json` so its name, properties and packages carry over.

It finishes with the next steps:

- the long-running commands to run side by side (the compiler watcher, `rogen watch`, `rojo serve`),
- with Darklua, one `darklua process` per root directory,
- where to add routes and variants.

### `list [name…]`

Lists every `*.rogen.json` in the working directory, with its root directories, sync directory, project file and active variants. Since every combination is its own config file, this is how you answer "what can this repo build?".

Name configs to list only those, and use `-c`, `--all`, `--variant` and `--no-variant` to pick configs and switch variants first. With `--json`, it prints each config fully resolved, with every default filled in and every path absolute. That's the way to see the common root or follow an `extends` chain.

### `help [command]`

Prints usage, or the details of one command.

### `version`

Prints the installed version.

## Options

`build` and `watch` take the override flags. `where` and `list` take the ones that pick configs and switch variants: `--all`, `-c`, `--variant` and `--no-variant`. An **override** replaces a config value for a single run. Anything you want every time belongs in the file.

### `--all`

Every `*.rogen.json` in the working directory, as if you'd named each one. It can't be combined with names or `-c`, and like several names, it rejects `-o`, `-s` and `--template`.

### `-c, --config <path>`

An explicit config path, for configs the name rule can't reach. Repeatable.

### `-o, --out-file <path>`

Overrides `outFile`.

### `-s, --sync-dir <path>`

Overrides `syncDir`.

### `--template <path>`

Overrides `template`. It has no short flag.

### `--variant <name>`

Turns a variant on. Repeatable.

### `--no-variant <name>`

Turns a variant off. Repeatable.

<Callout type="info">
	`-o`, `-s` and `--template` change one config, so you can't use them with several names. A variant flag applies to every built config that declares that variant, and is only an error if none does.
</Callout>

### `--json`

For `build`, `where`, `list` and `init`. Prints a single JSON document on stdout instead of text, for another program to read. See [JSON output](#json-output).

### Global options

| Flag | Description |
|---|---|
| `-h, --help` | Prints help. |
| `-v, --version` | Prints the version. |
| `--verbose` | Prints debug output. Can't be combined with `--quiet`. |
| `-q, --quiet` | Prints errors only. Can't be combined with `--verbose`. |
| `--no-input` | Never asks questions, and prints plain lines. |

Anything you explicitly asked for, like help, the version or a `--json` document, still prints with `--quiet`.

## JSON output

`--json` replaces a command's text with one JSON document on stdout. The exit code is the same as the text version's, and failures print a document too, so a program can always read stdout. Nothing else goes to stdout, `--quiet` and `--verbose` don't affect it, and it never draws a frame. Even a mistake on the command line itself, like an unknown flag, prints `{ "error": "..." }`, because `--json` is read before the rest of the line.

Paths are absolute and use the operating system's separator, so on Windows they have backslashes. Instance paths and glob patterns aren't file paths, so they keep `/`. Each diagnostic is an object. Match on its `code`, since the wording of `message` can change:

```json
{
	"file": "/repo/default.rogen.json",
	"line": 3,
	"column": 2,
	"severity": "error",
	"code": "config.unknownField",
	"message": "unknown field \"outDir\"."
}
```

`line` and `column` are left out when a diagnostic is about a whole file or folder. If a command fails before it has anything to report, for example because a config is invalid or missing, the document is `{ "diagnostics": [...] }`, or `{ "error": "..." }` for anything that isn't a diagnostic.

### `build --json`

```json
{
	"configs": [
		{
			"file": "/repo/default.rogen.json",
			"outFile": "/repo/default.project.json",
			"outcome": "wrote",
			"diagnostics": []
		}
	],
	"notBuilding": ["/repo/lobby.rogen.json"]
}
```

`outcome` is `wrote`, `unchanged` or `notWritten`. If any config fails, none is written, and every config is `notWritten` with its own diagnostics. `notBuilding` lists the configs in the folder that this run wasn't asked to build.

### `where --json`

An array with one entry per config and path, in the same order as the text, but with no lines folded together. Every entry has `config`, `status` and a `source` path, plus whatever its status carries:

| `status` | Fields |
|---|---|
| `placed` | `instancePath` (an array of names), `route`, `routeMatch`, `variants` |
| `pruned` | `variants`, the dormant ones |
| `replaced` | `by`, the file that took its instance path |
| `displaced` | `node`, the template node's path |
| `mounted` | `node`, the template node whose `$path` mounts it |
| `excluded` | `pattern`, the glob that matched |
| `unrouted`, `outside`, `ignored`, `missing`, `empty`, `skipped` | none |
| `noFile` | `instance` instead of `source`: no file places an instance you asked about |

`routeMatch` is `folder`, `marker`, `suffix` or `fallback`. Each entry in `variants` looks like `{ "variant": "mock", "form": "suffix" }`, where `form` is `folder`, `marker` or `suffix`.

### `init --json`

```json
{
	"files": ["/repo/lobby.rogen.json", "/repo/tsconfig.lobby.json"],
	"notes": [],
	"nextSteps": {
		"setup": ["Add \"include\": [\"src\"] to tsconfig.json, so its own build leaves out the place folders."],
		"run": ["rbxtsc -w -p tsconfig.lobby.json --rojo lobby.project.json", "rogen watch lobby", "rojo serve lobby.project.json"],
		"darklua": [],
		"edits": ["Declare variants under \"variants\" in lobby.rogen.json to swap in files like Analytics.mock.ts."]
	}
}
```

`files` lists what was written, in order. `notes` is what `init` said before writing, such as keeping a hand-written project file as the template. `nextSteps` groups what to do next:

- `setup`: one-time edits to make before anything runs,
- `run`: the long-running commands, each needing its own terminal,
- `darklua`: the commands that process code into the sync directory,
- `edits`: what to change in the files that were written.

If a write fails, the document is `{ "files": [...], "error": "..." }`, listing the files written before it.

### `list --json`

An object keyed by each config file's absolute path. Every value has `extends` (the parents, nearest first) and `diagnostics`. A config that resolved also has `name`, `rootDirs`, `commonRoot`, `routes`, `variants`, `exclude`, `template`, `syncDir` and `outFile`, with `null` for an unset `template`, `syncDir` or `commonRoot`. A config with errors has only `extends` and `diagnostics`. The other configs still print, and the exit code is 1.

## Output

Every command prints through the same logger. In a terminal, it draws a framed layout with symbols. Without one (CI, pipes, redirects), it prints plain lines with no gutter or color, so anything that greps the output keeps working.

Rogen also prints plain lines, and never asks a question, when the `CI` environment variable is set to anything other than empty, `0` or `false`, when `TERM` is `dumb`, or with `--no-input`. Use `--no-input` when a tool runs Rogen in a pseudo-terminal, where `init` would otherwise sit waiting for answers.

A build result line reads `<file> · wrote`, `<file> · unchanged` or `<file> · not written`. Diagnostics go on their own lines below it in the usual `file:line:col - severity: message` shape, so editors and CI can parse them. The file is relative to the working directory, and a warning about a source file points at that file, one line per file. A command that fails prints the error inside the frame and exits with 1.
