```bash
rogen [command] [name…] [options]
```

The first word is always the command, and a bare `rogen` prints usage. Whatever follows names configs: `rogen build lobby` builds `lobby.rogen.json`, and a name with a `/` or ending in `.json` is a path, as in `rogen build places/lobby.rogen.json`. With no names, a command reads every `*.rogen.json` in the folder. Run from a folder with none, `build`, `watch`, `serve`, `list` and `where` use the configs of the nearest folder above that has any, and the text output says which (`rogen build · default, lobby · in ../..`). Config names resolve in that folder; paths (config paths, `where` paths, `-o`) stay relative to where you run. `--json` doesn't change, since its paths are absolute. `rogen lobby` is an error, not a shortcut, and Rogen will suggest `rogen build lobby`.

## Commands

### `build [config…]`

Writes the project file of every config in the folder, or of the ones you name. A config that declares [modes](/docs/v2/core-concepts/modes) builds in the mode its `mode` field names, or in the one `--mode` picks. You can build several configs at once, as long as no two write the same file. Configs that share a root directory share one scan, and a project file whose bytes wouldn't change isn't written, so building everything is cheap.

Each warning and error ends with its [code](/docs/v2/diagnostics), and the closing line counts the warnings: `Built 1 config with 4 warnings.`

### `watch [config…]`

Builds, then rebuilds whenever files or configs change. Only names matter, so editing inside a script never triggers a rebuild.

A config reloads when it, its `extends` chain or its template changes, and CLI overrides carry over. If you save an invalid config, `watch` prints the error and keeps using the last valid version, so a broken `prod.rogen.json` doesn't hold up `default.rogen.json`.

```
┌  rogen watch · default, lobby
│
◇  12:04:31 · 2 files changed
│  ✔ default.project.json · wrote
│  ■ lobby.project.json · not written
│  ■ /repo/lobby.project.json - error: … (config.unknownField)
│
◇  12:05:02 · default.rogen.json changed · reloaded
│  ✔ default.project.json · unchanged
│
◇  12:06:10 · 1 file changed
│  ✔ default.project.json · wrote · 3 warnings as before
```

A block prints only the diagnostics the last one didn't have, so a standing warning isn't repeated. The result line counts what it left out (`3 warnings as before`), which tells you they are still there, and what went away since the last block (`1 warning fixed`). Configs that share a root dir find the same warnings, which one block prints once: the next config's line ends `same warnings as default`.

With no config names, `watch` follows the folder: a `*.rogen.json` you add is built from then on, and one you delete is dropped, each with a line saying so. A config you named is the only one it watches.

It's safe to run `build` while `watch` is running. Press Ctrl+C to stop.

### `serve [config…] [-- server args…]` [#serve]

Builds, starts a sync server on the project files, and rebuilds on changes as `watch` does. Run it instead of `watch` when you sync to Studio.

```
rogen serve · default
12:04:31 · initial build
  default.project.json · unchanged
  Serving default with Rojo 7.7.1 at 127.0.0.1:34872.
12:05:10 · 1 file changed
  default.project.json · wrote
error: Rojo: Snapshot error: File is not a valid JSON model: src/Bad.model.json: JSONC parse error: Expected colon after the string or word in object property on line 2 column 1
```

Every config in the folder is built and watched, so no project file goes stale. A server starts only for the configs no other config extends: `sync` over `default` with [Darklua](/docs/v2/setups/darklua), and each place, not the shared `default`, in a [multi-place](/docs/v2/setups/multi-place) repo. Names pick which configs are served: `rogen serve lobby` builds everything and serves only `lobby`. A named config from another folder is watched on its own.

Servers start only after the first build succeeds. If it fails, nothing starts, the errors print and `serve` exits 1. Press Ctrl+C to stop: it reaches the server, and Rogen ends every process it started.

**As configs change.** The servers follow the configs while `serve` runs, as the build does. A config added that is to be served gets its own server once it builds, after the same port checks as at the start; one that can't be served, as its port is taken, is reported and the rest go on. A served config that is deleted, or that a new config comes to extend (adding `sync.rogen.json` over `default`), has its server stopped, and the new config is served instead. A template that moves a config to another port or address restarts its server there. With config names, only those configs are served, whatever is added.

**Which server.** Rojo or Argon. Rogen runs the one the project pins in `rokit.toml`, `aftman.toml` or `foreman.toml`, in the folder of the configs or any folder above, so the pinned version runs. With none pinned, it uses the one on the PATH. `--tool rojo` or `--tool argon` picks. When both are pinned, Rojo serves and Rogen says so: `Both rojo and argon are pinned; serving with rojo (--tool argon to switch).` Rogen never installs or bundles a server, since it has to match the Studio plugin you installed. It runs `<tool> --version` first, so a broken install fails before the build.

**Port.** There is no Rogen flag. The port is the server's own:

| Server | Port | Host |
|---|---|---|
| Rojo | `--port` after `--`, else the template's `servePort`, else 34872 | `--address`, else `serveAddress`, else `127.0.0.1` |
| Argon | `--port` or `-P` after `--`, else `servePort`, else `port` in `argon.toml` beside the project file, else in `~/.argon/config.toml`, else 8000 | `--host` or `-H`, else `serveAddress`, else `host` in those files, else `localhost` |

Two served configs on one port exit 2, with the fix: give each its own `servePort` in its template, or serve one at a time (`rogen serve lobby`). Places that set no `servePort` share the default port, which is why `init` prints `rogen serve lobby` for a place. A `servePort` in the template is committed, so every teammate's plugin matches.

**Already running.** Before building, Rogen asks each port what serves there. When the same project is already served, that config isn't started. Rogen knows a project by the name in its project file, so when two served configs share a name, a server on their port counts as something else. A server another `rogen serve` started is also known by its project file, so a second checkout of the same project, such as a git worktree, is told the port is taken by the first one's folder rather than that it is already served. When every served config is already served, `serve` says so and exits 0 without building. When something else holds the port, `serve` exits 1 with [`serve.portTaken`](/docs/v2/diagnostics#serve-porttaken), which names what holds it and a free port to use instead.

**After `--`.** Everything after `--` goes to the server untouched, such as `rogen serve -- --port 34873` or Argon's `--sourcemap`. Rogen reads the port and host flags from it, so the running check asks the port the server will use. Rogen never passes Argon's `--ts`; run `rbxtsc -w` yourself. Other commands take nothing after `--`: `rogen build -- x` exits 2.

**Server output.** Rogen reads what the server prints and shows its warnings and errors as its own lines, each on one line, named after the server, with paths relative to the folder you ran `serve` in. The rest is dropped: the server's banner, since Rogen's `Serving` line says where it listens, its info logs, its debug detail, a message it repeats, and what Rogen's own port checks and project file writes make it say. A line Rogen doesn't recognise, such as a crash, is shown as it is, so nothing that explains a failure is lost. `--verbose` shows the dropped lines too, as debug lines.

**Exit code.** 0 after Ctrl+C. When a server stops on its own, `serve` stops too and exits with the server's code; a non-zero code also reports [`serve.serverExited`](/docs/v2/diagnostics#serve-serverexited).

`serve` accepts `-o`, `--mode`, `--variant`, `--no-variant`, `--tool` and `--json`. See [`serve --json`](#serve---json) for its lines.

### `where [path…]`

Shows where each file lands in the game and why, without writing anything:

```
$ rogen where src/Net src/Combat/Server/Hit.luau
src/Net/Http.luau -> ReplicatedStorage/Shared/Net/Http · route * (fallback)
src/Net/Http.mock.luau -> pruned · variant mock is off (suffix)
src/Net/Remotes@server.luau -> ServerScriptService/Net/Remotes · route Server (suffix)
src/Net/Types.lua -> replaced by src/Net/Types.luau
src/Combat/Server/Hit.luau -> ServerScriptService/Combat/Hit · route Server (folder)
```

A directory stands for the files inside it, and no path at all means every file in the tree. Since Rogen only reads names, the path doesn't have to exist yet, so you can check a file before you create it.

A placed file shows its instance path, the governing route, how it matched (`folder`, `marker`, `suffix` or `fallback`) and any active variants and modes. Otherwise the line says why it isn't placed: `pruned` (with the variant that is off, or `mode is dev, not prod`), `replaced by` another file, `displaced` by a template node, `mounted` by a template `$path`, `unrouted`, `excluded` (with the glob), or `outside the root dirs`.

With no path and nothing in the root dirs, `where` says `No files in the root dirs (src).` A path that doesn't exist and ends in a separator (`src/Combat/`) answers `does not exist · name a file in it to see where it would land`, since a file in it, such as `src/Combat/Hit.luau`, is placed as if it existed. Without the separator it answers `does not exist`, since `src/Module` may be a file missing its extension. A backslash is a separator on every platform, so `src\Combat\Hit.luau` answers as `src/Combat/Hit.luau` does.

Under the line of a file you name, `where` prints, dimmed, the `require` that reaches it, since "where does it land" is followed by "how do I reach it". It writes a name that isn't an identifier as an index. Where no path reaches the file, it says why instead: a module under `StarterPlayerScripts` (or `StarterCharacterScripts`, `StarterGui`, `StarterPack`) is cloned into each player, and a script isn't a module. A roblox-ts source is imported by path and gets no line. A directory and a bare `rogen where` are listings and stay as they are; `--verbose` adds each module's require to a listing.

```
$ rogen where src/Inventory/Types.luau src/Hud/Client/Hud.luau
src/Inventory/Types.luau -> ReplicatedStorage/Shared/Inventory/Types · route * (fallback)
  require(game:GetService("ReplicatedStorage").Shared.Inventory.Types)
src/Hud/Client/Hud.luau -> StarterPlayer/StarterPlayerScripts/Hud/Hud · route Client (folder)
  no require by this path: StarterPlayerScripts is cloned into each player
```

Under a path's line, `where` prints each warning or error a build would raise about it, with its code, so you see a stray `@` or a script that never runs before you build. Warnings about the sync dir are left out, since they are about your compiler's output and not a path. A path that doesn't exist yet gets the warnings it would get once created, and exit stays 0: `where` answers a question, it doesn't judge the project.

```
$ rogen where src/Inventory/Save@sever.luau
src/Inventory/Save@sever.luau -> ReplicatedStorage/shared/Inventory/Save@sever · route * (fallback)
  warning: did you mean "@server"? (route.strayAt)
```

A path can carry the `:line` or `:line:col` that linters and logs print after it, with or without a message (`src/Net/Http.luau:12:5: unexpected symbol`); Rogen reads it as the path, so you can paste such a line as it is.

`where` also works backwards. An argument that starts with a service is read as an instance, and you can paste an error line straight in:

```
$ rogen where "ServerScriptService.Combat.Hit:12: attempt to index nil"
src/Combat/Server/Hit.luau -> ServerScriptService/Combat/Hit · route Server (folder)
```

When no file places the instance, `where` says where a new one goes, from the files placed beside it:

```
$ rogen where ServerScriptService.Inventory.Export
ServerScriptService.Inventory.Export -> no file places it · a new file goes in src/Inventory/Server/
```

With no files beside it, `where` still names the folder when a route and a root dir make one: for the first server file of `src/Shop/`, `a new file goes in src/Shop/Server/`, checked by placing a file there as `build` does. When a file on disk would place the instance after a rename that a warning proposes, such as a typo in an `@` suffix, `where` says so:

```
$ rogen where "ServerScriptService.Shop.Buy:4: attempt to index nil"
ServerScriptService.Shop.Buy -> no file places it · src/Shop/Buy@sever.luau would, renamed to Buy@Server.luau (route.strayAt)
```

Unlike other commands, `where` takes paths, not config names, so it reads every config in the folder. A file every config places the same way prints one line. Otherwise each config's line starts with its name, and `outside the root dirs` is left out when another config places the file, so a place's file prints only the place's line:

```
$ rogen where places/lobby/Lobby/Server/Queue.luau
lobby: places/lobby/Lobby/Server/Queue.luau -> ServerScriptService/Lobby/Queue · route Server (folder)
```

A config that doesn't load answers nothing: `where` prints the answers of the configs that do, then the broken config's errors, and exits 1.

`where --json` keeps every config's entry, `outside` included. `where` accepts `--mode`, `--variant`, `--no-variant` and `--json`.

### `check [path…]`

Prints the diagnostics about the paths you give it, and nothing else, and exits 1 when there are any. It builds as `build` does and writes nothing, so it fits a hook, `lint-staged` or `pre-commit`, which pass changed paths to a command and expect a non-zero exit. `where` answers a question and always exits 0; `check` is the judging counterpart, as `--deny-warnings` is for `build`.

```
$ rogen check src/Inventory/Save@sever.luau src/Inventory/Clean.luau
src/Inventory/Save@sever.luau - warning: did you mean "@Server"? (route.strayAt)
```

Each line is `file:line:col - severity: message (code)`, printed on stdout, so `rogen check > report.txt` and `rogen check | grep strayAt` work, and `--quiet` keeps them. A clean path prints nothing. A diagnostic that several configs share prints once, and one about a group of files is cut down to the entry about your path. A path that doesn't exist yet is checked as if it did, and the sync dir's warnings are left out, as in `where`. Whatever paths you give, what stops `build` fails the check: a config that doesn't load, one without routes, or two that write the same file.

With no path, `check` reports every diagnostic of every config, the sync dir's included: `build --deny-warnings` without the write, which a read-only checkout needs. Its lines have the same shape as with paths: a warning about several files prints one line per file, none left out, and one that isn't about a file (a missing root dir, an empty sync dir) names the config or folder it is about.

`check --json` prints `{ "diagnostics": [...] }` with the entries described under [JSON output](#json-output). `check` accepts `--mode`, `--variant`, `--no-variant` and `--json`. It has no `--changed`: git stays outside Rogen, so whoever calls `check` passes the paths.

```bash
git diff --name-only --diff-filter=d HEAD | xargs -r rogen check
```

### `init [name]`

Writes a starting `<name>.rogen.json` (or `default.rogen.json`). It detects the language, Darklua and your package manager, and writes what it found into the config. This is the only time Rogen detects anything; builds just do what the config says.

In a terminal it asks a few questions, and Enter gives you the default each time. With an existing `default.rogen.json`, it offers to add a place, a config that extends default, or a separate config, and with other configs but no default, a separate config. Either way it also offers Rogen's rules for coding agents and the agent hook, when they aren't there yet. With `-y`, `--json`, or when it can't ask (see [Output](#output)), it takes the defaults, so `rogen init lobby -y` adds a place in `places/lobby`.

Below a folder that has a config, `init` stops: that config builds the folder as part of its game, so a project in it would be built twice. In a terminal it asks first, with **No** as the answer Enter gives; without one it fails and names the folder to run `rogen init` from.

`init` never overwrites a file it writes. If a hand-written project file is in the way, it's copied to `template.project.json` first, without the nodes that point into the root dirs, which become routes that put each folder where the file had it (see [Coming from Rojo](/docs/v2/coming-from-rojo)).

Then `init` builds the configs it wrote, so the project files exist before you run anything: `rojo serve` and `rbxtsc --rojo` find theirs, and the file is ready to commit. A hand-written project file in the way is replaced by that build, which is why it was copied first. The build prints as `build` does, with its warnings and their codes, except the ones about the sync dir, since the compiler hasn't run yet. If it fails, the files stay, the errors print, and `init` exits 1: fix the config and run `rogen build`. With `--json`, the document has the build's entries under `built`, shaped as in [`build --json`](#build---json). When it's done, `init` prints what to run next.

A first `init` also adds Rogen's [rules for coding agents](/docs/v2/agents) to `AGENTS.md`, or to `CLAUDE.md` when that's the only one, or writes a new `AGENTS.md`. In a terminal it asks first. It appends after what's already there and never touches a file that already holds the rules. A later `init` offers them under **Agent instructions**.

Where it finds a coding agent (Claude Code, Codex, Gemini CLI, Cursor or Copilot, each by a folder or file it leaves in the project), a terminal run also offers an [agent hook](/docs/v2/agents#check-changed-files-automatically) that reports Rogen warnings about the files a turn changed: it writes `.agents/hooks/rogen-check.sh` and registers it in each agent's hook file. A later `init` lists it under **Agent hook**. A run that can't ask never adds it, and `jq` is the one tool it needs besides `bash` and `git`.

### `list [config…]`

Lists every config in the folder, or the ones you name, with its root directories, its resolved routes (`Server -> ServerScriptService`, one per line, or `routes: same as default` when an earlier config in the list has the same), sync directory, project file, every variant it declares, on or off (`variants: debug on, mock off`), its conflict groups (`conflicts: halloween | christmas`), the mode it builds in and every mode it declares (`mode: dev`, `modes: dev, qa, prod`). It's the quickest answer to "what can this repo build?". With `--json`, each config is printed fully resolved, which is handy for following an `extends` chain.

### `help [name]`

Prints usage, or a command's arguments, options and examples. `rogen --version` prints the installed version.

`rogen help <topic>` prints one section of the reference from the version you have installed, offline: `routing`, `variants`, `modes`, `config`, `layout` or `output`. `rogen help <code>` explains a [diagnostic](/docs/v2/diagnostics) code, such as `rogen help route.strayAt`. The code may be typed in any case, or without its prefix when one code ends in it: `rogen help strayat` prints `route.strayAt`.

## Options

An override changes a config value for one run. Anything you want every time belongs in the file, and a different sync directory or template is a different config. `where`, `check` and `list` only take `--mode`, `--variant` and `--no-variant`.

| Flag | Effect |
|---|---|
| `-o, --out-file <path>` | Overrides `outFile`. |
| `--mode <name>` | Picks the mode every config that declares modes builds in. Strict: a config that declares modes without this one is an error. |
| `--variant <name>` | Turns a variant on, beyond those the mode lists. Repeatable. |
| `--no-variant <name>` | Turns a variant off, whatever turned it on. Applies last. Repeatable. |
| `--deny-warnings` | `build` only: exits 1 when any config has a warning. Files are written and diagnostics keep their severity, so only the exit code changes. |
| `--json` | Prints one JSON document for `build`, `where`, `check`, `list` and `init`, and one JSON object per line for `serve`. On `init` it implies `--yes`. |
| `--tool <rojo\|argon>` | `serve` only: the sync server to start. Without it, the one the project pins, Rojo before Argon. |
| `-y, --yes` | `init` only: writes the defaults without asking. |
| `-h, --help` | Prints help. |
| `-V, --version` | Prints the version. |
| `-v, --verbose` | Prints debug output. |
| `-q, --quiet` | Prints errors only, plus anything you explicitly asked for. |

`-o` changes a single config, so with several configs in the folder you have to name one. A variant flag applies to every config that declares the variant, and is only an error if none do. `--mode` applies to every config that declares modes, ignores the ones that don't, and is an error if none declare any. Naming a mode with `--variant` is an error that points at `--mode`. `--variant` never turns another variant off: for two variants of a [conflict group](/docs/v2/core-concepts/variants#conflicts), turn the first off with `--no-variant`.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | The command did its job, warnings included (unless `build --deny-warnings` is given). `serve` exits 0 after Ctrl+C, or when every config is already served. |
| `1` | The project is wrong: an invalid config, build errors, a failed write, a cancelled `init`, any warning under `build --deny-warnings`, or any diagnostic `check` prints. For `serve`, also no server to start or a taken port. |
| `2` | The command line is wrong: an unknown command, option or option value, a combination that isn't allowed (`-o` with several configs, `--verbose` with `--quiet`, words after `--` on a command other than `serve`, two served configs on one port), or a name that doesn't exist (a config, a variant or a help topic). |

When a server stops on its own, `serve` exits with the server's code. `--json` keeps the same codes, so a script can tell "fix the call" from "fix the project" without reading the message.

## Continuous integration

Warnings exit 0 on a developer's machine, but some should stop a merge, such as `route.serverCodeShipped` (server code replicating to clients) or `tree.deadScript`. `build --deny-warnings` exits 1 when any config has a warning, with the summary line `Built 2 configs with 3 warnings; --deny-warnings fails the run.`. It changes the verdict only: files are written as without the flag, and with `--json` the document is the same. Every warning has a fix that removes it (a rename, a marker such as `@Shared`, or a config edit; see [Diagnostics](/docs/v2/diagnostics)).

```bash
# compile first when a config has a syncDir, or output.nothingEmitted warns
rogen build --mode prod --deny-warnings
# only if you commit project files: fail when they're out of date
git diff --exit-code -- '*.project.json'
```

- Every build checks every mode, so a `--mode prod` build also fails on `mode.missingInstance` for another mode. That's the point of the check.
- Run the compiler or processor before `rogen build` when `syncDir` is set.
- With [Darklua](/docs/v2/setups/darklua), a data file it turns into a module keeps `output.dataFileConverted` alive until the file is copied unchanged into the sync dir.
- `watch` is interactive and has no such flag, and `where` answers a question without judging the project, so it exits 0. To judge only some paths, such as the files a pull request changes, run `rogen check <paths>`, which exits 1 on any diagnostic about them.
- Whether to [commit the project file](/docs/v2/core-concepts/output#commit-the-project-file) is yours to decide, and committing it is what the last line of the snippet needs.
- No `--check` flag is needed: `git diff --exit-code` covers committed project files, because `build` leaves a file untouched when its bytes wouldn't change.

## JSON output

`--json` prints exactly one JSON document on stdout (`serve` prints one per line, see [`serve --json`](#serve---json)), even when the command fails or crashes, or the command line itself is wrong. A crash prints `{ "error": "<message>" }`, exits 1 and writes its stack trace to stderr. The [exit code](#exit-codes) is the same as without it. File paths are absolute and use the OS separator; instance paths and globs always use `/`.

Diagnostics look like this. Match on `code`, since the wording of `message` can change. `line` and `column` are omitted when the problem is a whole file. `url` points at the code's section on the [Diagnostics](/docs/v2/diagnostics) page.

```json
{
	"file": "/repo/default.rogen.json",
	"line": 3,
	"column": 2,
	"severity": "error",
	"code": "config.unknownField",
	"message": "unknown field \"outDir\".",
	"url": "https://rogen-playfully.vercel.app/docs/v2/diagnostics#config-unknownfield"
}
```

A warning whose fix is one rename also has `fixes`, a rename for every name it covers, including names the message leaves out. Rogen never applies them: after a rename, update the requires and imports that name the file.

```json
"fixes": [
	{ "rename": { "from": "/repo/src/Inventory/Save@sever.luau", "to": "/repo/src/Inventory/Save@server.luau" } }
]
```

A `serve` error whose fix is a command has a `run` fix instead: the command, and the folder to run it in. Rogen never runs them.

```json
"fixes": [
	{ "run": { "command": "rogen serve default -- --port 34873", "cwd": "/repo" } }
]
```

Every document is an object, and every entry says which config it is about, the same way. An entry that is a config has `config` (the name every command takes: `lobby` for `lobby.rogen.json`) and `file` (its absolute path). An entry that belongs to a config, such as a location, has `config`. Identity comes first and `diagnostics` last.

A warning about several files, such as `route.strayAt` or `tree.deadScript`, is filed under the config and lists every file it is about in `related`, each with what it says about that file. The list is complete, while the text output stops at ten lines.

```json
"related": [
	{ "file": "/repo/src/Inventory/Save@sever.luau", "message": "did you mean \"@server\"?" }
]
```

A diagnostic is about a file when its `file` is that file or `related[].file` includes it. A program that wants every warning about the files it just changed filters on that, instead of reading `message`.

If a command fails before it has anything else to report, you get `{ "diagnostics": [...] }`, or `{ "error": "..." }` for anything that isn't a diagnostic.

### `build --json`

```json
{
	"configs": [
		{
			"config": "default",
			"file": "/repo/default.rogen.json",
			"outFile": "/repo/default.project.json",
			"outcome": "wrote",
			"diagnostics": []
		}
	]
}
```

`outcome` is `wrote`, `unchanged` or `notWritten`. A config that declares modes also has `mode`, the one it built in. If any config fails, nothing is written. Each entry's `diagnostics` is complete on its own: a warning that several configs share appears under each of them, while the text output prints it once and `--deny-warnings` counts it once.

A config that doesn't load is an entry like the others: `outFile` is `null`, `outcome` is `notWritten`, and its `diagnostics` say why. Every config that wasn't written because others failed or didn't load has `blockedBy`, the names of those configs, so a program can tell "this config is wrong" from "this config is fine, fix the other one". In text, the broken config's line says `not loaded` and the others say `not written · broken failed`.

### `serve --json`

One JSON object per line on stdout, each keyed by what it reports, and nothing else: what the server says is an `output` line too.

```json
{"build": {"config": "default", "file": "/repo/default.rogen.json", "outFile": "/repo/default.project.json", "outcome": "wrote", "diagnostics": []}}
{"serving": {"config": "default", "tool": "rojo", "version": "7.7.1", "project": "Game", "host": "127.0.0.1", "port": 34872, "session": "f7771777-…"}}
```

| Key | When | Fields |
|---|---|---|
| `build` | each config, on every build | the entry [`build --json`](#build---json) lists |
| `notice` | a config is added, removed, broken or recovered | `kind` (`added`, `removed`, `broken` or `recovered`), `file`; a broken config adds `keptLastValid` and `diagnostics` |
| `serving` | a server answers, so Studio can connect | `config`, `tool`, `version`, `project`, `host`, `port`, `session` (Rojo only); `alreadyRunning: true` when it was already serving before `serve` started |
| `output` | a server prints a warning, an error or a line Rogen doesn't recognise | `config`, `tool`, `severity` (`error`, `warning` or `info` for an unrecognised line), `message` |
| `refused` | a config to serve, added while serving, can't be served; the others go on | `config`, `tool`, `diagnostics` |
| `stopped` | a server stops | `config`, `tool`, `reason`: `exited` when it stopped on its own, with its `code` and `signal`; `removed`, `extended` or `moved` when its config was deleted, came to be extended by another, or moved to another address (a `serving` line follows for the new server); `shutdown` when `serve` was asked to stop, as the last line of a clean run |
| `error` | an unexpected failure that `serve` survives | the message |

`project` is the name in the project file, not the config's. When a run fails, the last line is `{ "diagnostics": [...] }` or `{ "error": "..." }`, as for other commands. A server that stops with a non-zero code adds a `diagnostics` line with [`serve.serverExited`](/docs/v2/diagnostics#serve-serverexited).

### `check --json`

An object with a `diagnostics` array: the entries described above, one per diagnostic about the paths (or, with none, about the project), each once. The exit code is 1 when it isn't empty.

### `where --json`

An object with a `locations` array and a `diagnostics` array. `diagnostics` holds the errors of any config that didn't load (the exit code is then 1) and is empty otherwise. `locations` has one entry per config that loaded and path, each with `config`, `status` and `source`, plus:

| `status` | Fields |
|---|---|
| `placed` | `instancePath` (an array of names), `require`, `route`, `routeMatch`, `variants`, and `hoisted: true` for a `^` name |
| `pruned` | `variants`, the dormant ones, a mode's name among them when another mode is active |
| `replaced` | `by`, the file that took its instance path |
| `displaced` | `node`, the template node's path |
| `mounted` | `node`, the template node whose `$path` mounts it |
| `excluded` | `pattern`, the glob that matched |
| `unrouted`, `outside`, `ignored`, `missing`, `empty`, `skipped` | none |
| `noFile` | `instance` instead of `source`: no file places an instance you asked about. `folders` lists where a new file for it goes, when files are placed beside it or a route and a root dir make one. `fixes` lists the renames, in the shape diagnostics use, after which a file would place it |

A config that declares modes adds `mode`, the active one, after `config`. Every entry with a `source` has `exists`, after `status`: `true` when the path is there now, `false` when `where` placed it as it would be once created, in a folder that exists or one that doesn't. A `noFile` entry has none.

Every entry also has `diagnostics`, last: the diagnostics about its path (the ones whose `file` is the path, or whose `related` lists it), empty for a clean path. A grouped diagnostic is narrowed to the path: its `message` is the `related` message about this path and `fixes` holds only the renames of this path. A `noFile` entry has none.

`require` is the Luau expression that reaches the module, such as `game:GetService("ReplicatedStorage").Shared.Inventory.Types`, with `["Foo Bar"]` for a name that isn't an identifier or is a reserved word. It is there only for a placed Luau module. A Script has none, nor does a roblox-ts source, which you import by relative path, nor anything under `StarterPlayerScripts`, `StarterCharacterScripts`, `StarterGui` or `StarterPack`, because Roblox clones those into the player at runtime and the edit-time path names the template. `rogen where <file> --verbose` prints it in text.

`routeMatch` is `folder`, `marker`, `suffix` or `fallback`. Each `variants` entry looks like `{ "variant": "mock", "form": "suffix" }`.

### `init --json`

```json
{
	"files": ["/repo/lobby.rogen.json", "/repo/tsconfig.lobby.json"],
	"appended": [],
	"directories": ["/repo/places/lobby"],
	"built": [
		{
			"config": "lobby",
			"file": "/repo/lobby.rogen.json",
			"outFile": "/repo/lobby.project.json",
			"outcome": "wrote",
			"diagnostics": []
		}
	],
	"notes": [],
	"nextSteps": {
		"setup": ["Add \"include\": [\"src\"] to tsconfig.json, so its own build leaves out the place folders."],
		"run": ["rbxtsc -w -p tsconfig.lobby.json --rojo lobby.project.json", "rogen serve lobby"],
		"darklua": [],
		"edits": ["Declare variants under \"variants\" in lobby.rogen.json to swap in files like Analytics.mock.ts, and turn them on in a mode or with --variant."]
	}
}
```

`files` lists what was written, in order, and `appended` the ones among them that existed and had something added: Rogen's agent rules at the end, or the hook in an agent's hook file. `directories` lists the root dirs `init` created because they didn't exist (a place's folder, or the root dirs of a new project); one that already existed is left alone and not listed. `built` has an entry per config it wrote, as `build --json` does, without the sync dir's warnings; if one has errors, the exit code is 1. `notes` is what `init` said along the way. In `nextSteps`, `setup` holds one-time edits, `run` the long-running commands (one terminal each), `darklua` the processing commands, and `edits` suggested changes to the new files. If a write fails, you get `{ "files": [...], "error": "..." }`.

### `list --json`

An object with a `configs` array, one entry per config in the order they were read. Every entry has `config`, `file`, `status` (`valid` or `broken`), `extends` (nearest parent first) and `diagnostics`. A config that resolved also has `projectName` (the name Rojo shows, which is not the config's name), `rootDirs`, `commonRoot`, `routes`, `variants` (each declared variant and whether it is on), `conflicts`, `mode` (the active one), `modes` (every name declared, in order), `exclude`, `template`, `syncDir` and `outFile`, with `null` for anything unset. `variants` and `exclude` are those of the active mode with the command line applied. A broken config has only the five. If any config has errors, the exit code is 1.

## Output

In a terminal, Rogen draws a framed layout. It prints plain lines instead in pipes and redirects, with `NO_COLOR` or `TERM=dumb`, and when CI or a coding agent runs it.

Only `init` asks questions, and only when stdin and stdout are both terminals and nothing says a program is on the other end. A run that can't ask takes the defaults, as `-y` does. Rogen treats the run as CI or an agent when `CI`, `AGENT` or `AI_AGENT` is set (`0` and `false` don't count), or when an agent's harness sets its own variable for the commands it runs: `CLAUDECODE` (Claude Code), `CODEX_SANDBOX` or `CODEX_THREAD_ID` (Codex), `CURSOR_AGENT` (Cursor), `GEMINI_CLI` (Gemini CLI), `COPILOT_AGENT` (GitHub Copilot), `OPENCODE` (OpenCode) or `CLINE_ACTIVE` (Cline). What a command prints doesn't change otherwise.

Diagnostics use the familiar `file:line:col - severity: message` shape, so editors and CI can parse them.
