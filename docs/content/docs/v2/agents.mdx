## Why

Coding agents work best when the context they need is in one place and their changes are easy to check. A Rogen layout gives you both.

1. **One folder, one feature.** Point the agent at `Shop/` and it has everything about the shop.
2. **A small blast radius.** If features don't require each other, a diff that stays inside `Shop/` can only break the shop, and the file list tells you that before you read any code.
3. **Boundaries a linter can check.** Rules like "features don't require each other" are rules about paths, so a linter can catch a crossed boundary before you review. See [Enforcing the Rules](/docs/v2/architectures#enforcing-the-rules).
4. **Placement is declared.** Where a file ends up comes from a short `routes` map, not from conventions the agent has to infer.
5. **No generated file to break.** Rogen rewrites the project file on every build, so there's nothing hand-maintained for an agent to corrupt.
6. **It checks its own work.** `rogen where` shows where a file lands and why, and `rogen check` reports what is misplaced, with a non-zero exit.

Left to itself, an agent assumes the path on disk is the instance path. It edits the generated project file, requires server code from shared code, or puts a `Server/` folder inside `Shared/` and ships it to every client. A short block of instructions prevents all of that.

## Set it up

Run [`rogen init`](/docs/v2/cli#init-name). A first `init` adds the block below to your `AGENTS.md`, or to `CLAUDE.md` when that's the only one, and creates `AGENTS.md` when there's neither. In a terminal it asks first. Every agent that reads the file gets the rules, with nothing to install.

## Add it to an existing repo

Paste the block into `AGENTS.md`, or run `rogen init` again and pick **Agent instructions**:

````md title="AGENTS.md"
## Rogen

Rogen writes the Rojo project file from the folders and names under each `*.rogen.json`'s `rootDirs`. Folders decide where code runs, so the disk path is not the instance path.

- Never edit a `*.project.json` that Rogen writes: change the config or its `template`.
- Put a new file where the repo keeps files like it. Server-only code never goes under a shared route.
- Run `rogen where <path>` to see where a file lands, before or after it exists.
- After adding, moving or renaming files, run `rogen check <paths>` and fix what it prints.
- A config with `modes` builds in one at a time: run `rogen build --mode <name>` for another, and `rogen list` to see them.
- Leave `rogen watch` to the user: it never exits.
- To sync to Studio, start `rogen serve --json` in the background. It exits 0 at once if a server already serves the project, or non-zero with diagnostics if it can't serve; otherwise it prints a `serving` line once Studio can connect, and keeps running.
- Before placing files or writing requires, read `rogen help routing`. `rogen help` lists every command and topic; read a command's help before guessing a flag.
````

## Check changed files automatically

The block asks an agent to run `rogen check <paths>` after it adds, moves or renames files. That depends on the agent remembering, and a clean result still costs a tool call.

[`rogen check`](/docs/v2/cli#check-path) prints the diagnostics about the paths it is given, and nothing else, and exits 1 when there are any. A hook that runs when the agent is about to end its turn can use that to report only what the agent's own changes caused. The script below collects the changed files from git (modified, renamed and untracked, but not deleted), runs `rogen check` on them, and reports each line it hasn't reported earlier in the session. The agent gets the report as its next prompt and continues its turn.

It is one script for every agent that has a hook for the end of a turn. They agree on the payload (a JSON object on stdin with the session id and the working directory) and on the reply (`{"decision": "block", "reason": …}` on stdout, which becomes the next prompt). Only Cursor differs, and takes `cursor` as the script's first argument to reply with `followup_message`.

`Stop` and not `PostToolUse`, because `PostToolUse` only sees `Write` and `Edit`, so a move done with `mv` or `git mv` in Bash is invisible, and it would report half-finished states, such as `dev/Service.luau` written before its `prod/` partner. A turn's end checks the end state once.

```bash title=".agents/hooks/rogen-check.sh"
#!/usr/bin/env bash
# Agent Stop hook: report new Rogen diagnostics about changed files before the agent ends its turn.
# Pass "cursor" as the first argument for Cursor, which replies with followup_message.
command -v jq >/dev/null || { echo "rogen-check.sh needs jq." >&2; exit 1; }
payload=$(cat)
session=$(jq -r '.session_id // .sessionId // .conversation_id // "agent"' <<<"$payload")
cd "${CLAUDE_PROJECT_DIR:-$(jq -r '.cwd // "."' <<<"$payload")}" || exit 0

changed=()
while IFS= read -r -d '' file; do changed+=("$file"); done < <(
	git diff -z --name-only --relative --diff-filter=d HEAD 2>/dev/null
	git ls-files -z --others --exclude-standard 2>/dev/null
)
((${#changed[@]})) || exit 0

seen="$(git rev-parse --git-dir)/rogen-hook-$session"
touch "$seen"
report=$(rogen check "${changed[@]}" 2>/dev/null | grep -vxF -f "$seen")
[[ -z $report ]] && exit 0
message=$(printf 'Rogen warns about files you changed. Fix each, or tell the user why it stays:\n%s' "$report")
reply='{decision: "block", reason: $message}'
[[ ${1:-} == cursor ]] && reply='{followup_message: $message}'
reply=$(jq -n --arg message "$message" "$reply") || exit 1
printf '%s\n' "$report" >>"$seen"
printf '%s\n' "$reply"
```

Where it finds an agent, `rogen init` can write the script and register it: a terminal run asks whether to add the hook to the agents it names, and a later `init` lists it under **Agent hook**. An agent is found by a sign in the project, and its hook file is created, or has the entry added to the event's list when it exists. It runs the script through `bash`, so it needs no executable bit. A run without a terminal never adds it, and `init` leaves alone an agent that names the script already, and a file that isn't plain JSON, which it says when it writes the hook for other agents.

| Agent | Found by | Hook file | Event | Entry |
|---|---|---|---|---|
| Claude Code | `.claude`, `CLAUDE.md` | `.claude/settings.json` | `Stop` | `bash "$CLAUDE_PROJECT_DIR"/.agents/hooks/rogen-check.sh` |
| Codex | `.codex` | `.codex/hooks.json` | `Stop` | `bash "$(git rev-parse --show-toplevel)"/.agents/hooks/rogen-check.sh` |
| Gemini CLI | `.gemini`, `GEMINI.md` | `.gemini/settings.json` | `AfterAgent` | `bash "$GEMINI_PROJECT_DIR"/.agents/hooks/rogen-check.sh` |
| Cursor | `.cursor` | `.cursor/hooks.json` | `stop` | `bash .agents/hooks/rogen-check.sh cursor` |
| Copilot | `.github/copilot-instructions.md`, `.github/hooks` | `.github/hooks/rogen.json` | `agentStop` | `bash "$(git rev-parse --show-toplevel)"/.agents/hooks/rogen-check.sh` |

To do it by hand, put the script at `.agents/hooks/rogen-check.sh` and add the entry in the agent's own format. Claude Code, Codex and Gemini CLI take a group of command hooks; Cursor and Copilot take the command itself, in a file that starts with `"version": 1`:

```json title=".claude/settings.json"
{
	"hooks": {
		"Stop": [
			{ "hooks": [{ "type": "command", "command": "bash \"$CLAUDE_PROJECT_DIR\"/.agents/hooks/rogen-check.sh" }] }
		]
	}
}
```

```json title=".cursor/hooks.json"
{
	"version": 1,
	"hooks": { "stop": [{ "command": "bash .agents/hooks/rogen-check.sh cursor" }] }
}
```

Codex runs a project hook only once you trust it: open `/hooks` in Codex to review it.

Tried on a project with two configs and one warning already there (`Old@sevre.luau`):

| Turn | The agent sees |
|---|---|
| Adds a clean file | nothing |
| Adds `Buy@sever.luau`, and `git mv`s `Save.luau` to `Save.client.luau` | `route.strayAt` and `tree.deadScript`, one line each |
| Stops again, same state | nothing, it was already reported |
| Fixes the typo, adds `Tax.shared.luau` | only `route.dotRoute` |

The warning that was there before never shows up, and the two configs' copies of each diagnostic collapse to one line.

With the hook in place, the "run `rogen check` …" rule in the block is optional, so a repo that uses the hook may drop it.

### Limits

- **Your own changes count too.** The hook can't tell the agent's changes from your uncommitted ones, so a warning in a file you're editing is reported once per session.
- **It needs bash, git and jq.** On Windows, Claude Code runs hooks in Git Bash, which has bash and git but not jq (`winget install jqlang.jq`). The script runs on bash 3.2, the one macOS ships.
- **An agent with no hook for the end of a turn** can still run `rogen check <paths>` and read its exit code, as `lint-staged` does: `"*": "rogen check"`.
- **Cursor and Copilot have caps and quirks.** Cursor limits automatic follow-ups (`loop_limit`, 5 by default), and its `stop` hook has been reported not to fire in the CLI or to ignore its reply on Windows. Copilot ends the turn after 8 blocks in a row. The script reports each line once, so neither limit is reached by it.
- **It runs from the folder the agent started in.** `rogen` finds the config there or in the nearest folder above, and the changed files are those below it, so an agent started in a subfolder is checked on that subfolder.

## Install the skill

For a repo that doesn't use `init`, the same text ships as a skill in [`skills/rogen`](https://github.com/LDGerrits/rogen), in the open [Agent Skills](https://agentskills.io) format that most coding agents understand. Install it with the [`skills`](https://github.com/vercel-labs/skills) CLI:

```bash
npx skills add LDGerrits/rogen
```

## What an agent reads

The block is loaded in every session, so it holds only what an agent gets wrong without being told, and the commands that answer the rest:

1. **The block**, about 150 tokens: the rules and the commands that check them.
2. **`rogen help <topic>`**, about 300 tokens a topic, read when needed: `routing`, `variants`, `modes`, `config`, `layout` and `output`. It matches the installed version and works offline.
3. **[`--json`](/docs/v2/cli#json-output) diagnostics**, when something's wrong: each has a stable code, the renames or commands that fix it, and a link to its [explanation](/docs/v2/diagnostics). `rogen help <code>` prints the same explanation.
