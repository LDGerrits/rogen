A coding agent places code and writes requires well on its own. It doesn't know that Rogen generates the Rojo project file, so after it adds a file, Rojo and the editor can miss the file until someone runs `rogen write`. Rogen adds a short block of rules to `AGENTS.md` that tells the agent to check its changes, and which commands answer the rest.

## Add the Rules

`rogen init` adds the block below to `AGENTS.md`, and creates the file when there is none. In a terminal it asks first, and `--no-agent-rules` leaves the block out. Where a project has only a `CLAUDE.md`, the block goes there.

Claude Code reads `AGENTS.md` only when the project has no `CLAUDE.md`, and Gemini CLI reads only `GEMINI.md`. So `init` appends an `@AGENTS.md` import to each `CLAUDE.md` and `GEMINI.md` that has neither the import nor the block. Where the project has an agent's folder (`.claude` or `.gemini`) but not its file, `init` writes the file with only the import.

To add the rules to a project that already has a config, run `rogen init --agent-rules` in the folder of the `*.rogen.json`. It writes the agent files and changes no config. You can also paste the block into `AGENTS.md` yourself. Keep the marker lines, because Rogen updates only a block between them:

````md title="AGENTS.md"
<!-- rogen -->
## Rogen

This repo uses Rogen. Each `*.rogen.json` generates the Rojo project file beside it (`game.rogen.json` → `game.project.json`) from folder and file names, so a file's path on disk is not its path in the game, and adding, moving or deleting a file can leave the project file out of date.

After you add, move, rename or delete files, or edit a `*.rogen.json`, run `rogen check <paths>` from the repo root. Fix each line it prints, or tell the user why it stays. When it says to run `rogen write`, run it.

### Placing code

- Name new files like their neighbours: same folders, `@` suffixes and casing. Run `rogen where <path>` to see where a file lands and how to require it.
- A folder or `@` suffix named after a key in `routes` routes its contents: `Shop/Server/`, `Save@Server.luau`.
- The outermost route wins, so `Shared/Server/Save.luau` ships to clients. Keep server-only code under a server route.
- In roblox-ts, import by relative path.

### Changing the setup

- Edit the `*.rogen.json`, never the generated `*.project.json`.
- Configs share nothing: apply a change to `routes`, `sourcePaths` or `tree` to every `*.rogen.json` it concerns.
- Read `rogen doc routing` before adding a route or a new naming pattern.

### Commands

- In roblox-ts, check `projects/common` through a place that uses it: `rogen check projects/game`.
- Run other commands in the folder of the `*.rogen.json`, or name it: `rogen write projects/game`.
- To sync to Studio, run `rogen serve --json` in the background and leave it running. `rogen help serve` explains its output.
- `rogen doc <topic>` covers `routing`, `config`, `layout` and `output`; `rogen help <command> --json` lists a command's flags and JSON output.
<!-- /rogen -->
````

## Keep the Rules Current

Rogen owns the text between the `<!-- rogen -->` and `<!-- /rogen -->` markers. When `rogen write` or `rogen serve` finds a block that differs from the installed version's, it replaces the block and prints a line saying so. It looks in the `AGENTS.md`, `CLAUDE.md` and `GEMINI.md` of the folder it runs in, and of each folder above it up to the repository root. Your text around the block is kept byte for byte, and an edit inside the block is overwritten.

Pin one Rogen version for the whole team, in `rokit.toml` or `package.json` as [Installation](/docs/v2/installation) does. Otherwise each person's `rogen write` rewrites the block to match their own version.

## Stop the Updates

Rogen never changes a file that has no markers. To keep the rules and edit them yourself, delete the two marker lines. To remove the rules, delete the block with its markers.

## Check Changed Files Automatically

The block asks an agent to run `rogen check <paths>` after it changes files. An agent can forget, and a clean result still costs it a tool call. A hook can run the check for it when the agent is about to end its turn.

The script below collects the files changed in git (modified, renamed and untracked, but not deleted) and runs `rogen check` on them, which prints only the diagnostics about those paths. The script sends each line it hasn't reported earlier in the session back to the agent as its next prompt, and the agent continues its turn. A warning in a file the agent didn't touch never shows up.

It is a Node script with no dependencies, so it runs wherever Rogen does, Windows included. It runs the Rogen in the project's `node_modules/.bin`, else the one on the `PATH`. Every agent with a hook for the end of a turn sends the same payload (a JSON object on stdin with the session id and the working directory) and reads the same reply (`{"decision": "block", "reason": …}` on stdout). Only Cursor differs: pass `cursor` as the first argument, and the script replies with `followup_message`.

The hook runs once, at the end of the turn, so it sees the end state. A hook after each edit would miss a move done with `git mv` in the shell, and would report half-finished states, such as one file of a pair written before the other.

```js title=".agents/hooks/rogen-check.mjs"
// Agent Stop hook: report new Rogen diagnostics about changed files before the agent ends its turn.
// Pass "cursor" as the first argument for Cursor, which replies with followup_message.
import { spawnSync } from "node:child_process";
import fs from "node:fs";
import path from "node:path";

const git = (...args) => {
	const run = spawnSync("git", args, { encoding: "utf8" });
	return run.status === 0 ? run.stdout : "";
};

let payload = {};
try {
	payload = JSON.parse(fs.readFileSync(0, "utf8"));
} catch {}
const session = String(
	payload.session_id ??
		payload.sessionId ??
		payload.conversation_id ??
		"agent",
).replace(/[^\w.-]/g, "_");
try {
	process.chdir(process.env.CLAUDE_PROJECT_DIR || payload.cwd || ".");
} catch {
	process.exit(0);
}

const changed = [
	...git(
		"diff",
		"-z",
		"--name-only",
		"--relative",
		"--diff-filter=d",
		"HEAD",
	).split("\0"),
	...git("ls-files", "-z", "--others", "--exclude-standard").split("\0"),
].filter(Boolean);
if (!changed.length) process.exit(0);

const seenFile = path.resolve(
	git("rev-parse", "--git-dir").trim(),
	`rogen-hook-${session}`,
);
const seen = fs.existsSync(seenFile)
	? fs.readFileSync(seenFile, "utf8").split("\n")
	: [];

const windows = process.platform === "win32";
const names = windows ? ["rogen.cmd", "rogen.exe"] : ["rogen"];
const locate = (dirs) =>
	dirs
		.flatMap((dir) => names.map((name) => path.join(dir, name)))
		.find((file) => fs.existsSync(file));
const rogen = locate([
	path.resolve("node_modules/.bin"),
	path.join(git("rev-parse", "--show-toplevel").trim(), "node_modules/.bin"),
	...(process.env.PATH ?? "").split(path.delimiter).filter(Boolean),
]);
if (!rogen) {
	const NONE = "# found no rogen";
	if (!seen.includes(NONE)) {
		console.error(
			"Rogen's hook found no rogen; install it in the project or globally",
		);
		fs.appendFileSync(seenFile, `${NONE}\n`);
	}
	process.exit(0);
}

const run = (command, args) =>
	windows && command.endsWith(".cmd")
		? spawnSync([command, ...args].map((part) => `"${part}"`).join(" "), {
				encoding: "utf8",
				stdio: ["ignore", "pipe", "ignore"],
				shell: true,
			})
		: spawnSync(command, args, {
				encoding: "utf8",
				stdio: ["ignore", "pipe", "ignore"],
			});
const check = run(rogen, ["check", ...changed]);
const report = (check.stdout ?? "")
	.split(/\r?\n/)
	.filter((line) => line && !seen.includes(line));
if (!report.length) process.exit(0);

const message = `Rogen warns about files you changed. Fix each, or tell the user why it stays:\n${report.join("\n")}`;
fs.appendFileSync(seenFile, `${report.join("\n")}\n`);
console.log(
	JSON.stringify(
		process.argv[2] === "cursor"
			? { followup_message: message }
			: { decision: "block", reason: message },
	),
);
```

In a terminal, `rogen init` asks whether to add the hook for the agents it finds in the project. Without a terminal, it adds the hook only with `--agent-hook`. It writes the script and adds an entry for the event to each agent's hook file, creating the file when needed. The entry runs the script through `node`, so the script needs no executable bit. `init` skips an agent whose hook file already names the script. It also skips a hook file that isn't plain JSON, and tells you to register the script by hand.

| Agent | Found by | Hook file | Event | Entry |
|---|---|---|---|---|
| Claude Code | `.claude`, `CLAUDE.md` | `.claude/settings.json` | `Stop` | `node "$CLAUDE_PROJECT_DIR"/.agents/hooks/rogen-check.mjs` |
| Codex | `.codex` | `.codex/hooks.json` | `Stop` | `node "$(git rev-parse --show-toplevel)"/.agents/hooks/rogen-check.mjs` |
| Gemini CLI | `.gemini`, `GEMINI.md` | `.gemini/settings.json` | `AfterAgent` | `node "$GEMINI_PROJECT_DIR"/.agents/hooks/rogen-check.mjs` |
| Cursor | `.cursor` | `.cursor/hooks.json` | `stop` | `node .agents/hooks/rogen-check.mjs cursor` |
| Copilot | `.github/copilot-instructions.md`, `.github/hooks` | `.github/hooks/rogen.json` | `agentStop` | `node "$(git rev-parse --show-toplevel)"/.agents/hooks/rogen-check.mjs` |

To register it by hand, put the script at `.agents/hooks/rogen-check.mjs` and add the entry in the agent's own format. Claude Code, Codex and Gemini CLI take a group of command hooks. Cursor and Copilot take the command itself, in a file that starts with `"version": 1`:

```json title=".claude/settings.json"
{
	"hooks": {
		"Stop": [
			{ "hooks": [{ "type": "command", "command": "node \"$CLAUDE_PROJECT_DIR\"/.agents/hooks/rogen-check.mjs" }] }
		]
	}
}
```

```json title=".cursor/hooks.json"
{
	"version": 1,
	"hooks": { "stop": [{ "command": "node .agents/hooks/rogen-check.mjs cursor" }] }
}
```

Codex runs a project hook only after you trust it. Open `/hooks` in Codex to review it.

### Limits

- **Your own changes count too.** The hook can't tell the agent's changes from your uncommitted ones, so it reports a warning in a file you're editing once per session.
- **It needs Node, git and Rogen.** Without a `rogen` in `node_modules/.bin` or on the `PATH`, the hook prints `Rogen's hook found no rogen; install it in the project or globally` on stderr once per session, and lets the turn end.
- **It checks only below the folder the agent started in.** It skips a file that no build reads, such as a `README.md`.
- **Cursor and Copilot have caps.** Cursor limits automatic follow-ups (`loop_limit`, 5 by default), and its `stop` hook has been reported not to fire in the CLI, or to ignore its reply on Windows. Copilot ends the turn after 8 blocks in a row. The script reports each line once, so a warning the agent leaves alone doesn't count against either cap.
- **An agent with no hook for the end of a turn** relies on the block's rule. To check before each commit too, add `rogen check` to `lint-staged`: `"*": "rogen check"`.

## Install the Skill

The `rogen` skill in [`skills/rogen`](https://github.com/LDGerrits/rogen) sets a repo up for Rogen. It runs `rogen init` to start a project or to move a Rojo project onto Rogen, and can reorganise a Rojo layout into feature folders. In a repo that has Rogen but not the block, it adds the block. It uses the open [Agent Skills](https://agentskills.io) format that most coding agents read. Install it with the [`skills`](https://github.com/vercel-labs/skills) CLI:

```bash
npx skills add LDGerrits/rogen
```

The rules stay in `AGENTS.md`, where every session reads them, because an agent loads a skill only when a task looks like it needs one. Adding a Luau file doesn't look like a Rogen task, and that is when the agent needs the rules.
