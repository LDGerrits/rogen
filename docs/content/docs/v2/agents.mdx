## Why

Coding agents work best when the context they need is in one place and their changes are easy to check. A Rogen layout gives you both.

1. **One folder, one feature.** Point the agent at `Shop/` and it has everything about the shop.
2. **A small blast radius.** If features don't require each other, a diff that stays inside `Shop/` can only break the shop, and the file list tells you that before you read any code.
3. **Boundaries a linter can check.** Rules like "features don't require each other" are rules about paths, so a linter can catch a crossed boundary before you review. See [Enforcing the Rules](/docs/v2/architectures#enforcing-the-rules).
4. **Placement is declared.** Where a file ends up comes from a short `routes` map, not from conventions the agent has to infer.
5. **No generated file to break.** Rogen rewrites the project file on every write, so there's nothing hand-maintained for an agent to corrupt.
6. **It checks its own work.** `rogen where` shows where a file lands and why, and `rogen check` reports what is misplaced, with a non-zero exit.

Left to itself, an agent assumes the path on disk is the instance path. It edits the generated project file, requires server code from shared code, or puts a `Server/` folder inside `Shared/` and ships it to every client. A short block of instructions prevents all of that.

## Set it up

Run [`rogen init`](/docs/v2/cli#init-path). A first `init` adds the block below to your `AGENTS.md`, or to `CLAUDE.md` when that's the only one, and creates `AGENTS.md` when there's neither. In a terminal it asks first. Every agent that reads the file gets the rules, with nothing to install.

An agent that runs `init` itself can't answer prompts: `rogen init --dry-run --json` shows what it would write and which choices it would take, and a flag answers each question (see [Choices as flags](/docs/v2/cli#choices-as-flags)).

## Add it to an existing repo

`rogen init` only starts projects, and never changes a folder that has a config. To add the rules to a project that has one, paste the block into `AGENTS.md` (or `CLAUDE.md`):

````md title="AGENTS.md"
## Rogen

This repo uses Rogen. Each `*.rogen.json` generates the Rojo project file beside it (`game.rogen.json` → `game.project.json`) and places code by its folder and file names. A file's path on disk is not its path in the game.

### Placing code

- Route keys are the names in a config's `rogen.routes`, such as `Server`, `Client` and `Shared`. A folder named after a key (`Shop/Server/`) sends everything in it to that route's target; a name ending in `@` and a key (`Save@Server.luau`) sends that file or folder.
- The outermost route wins: `Shared/Server/Save.luau` still ships to clients. Put server-only code under a server route.
- Put a new file next to similar files, then run `rogen where <path>` to see where it lands and the `require` that reaches it. It works before the file exists.
- roblox-ts code imports by relative path.

### Changing the setup

- Edit the `*.rogen.json`, never the generated `*.project.json`.
- Configs share nothing. A change to `routes`, `sourcePaths` or `tree` goes into every `*.rogen.json` it applies to.
- Read `rogen doc routing` before you add a route or use a naming pattern the repo doesn't use yet.

### Checking

- After you add, move or rename files or edit a `*.rogen.json`, run `rogen check <paths>` from the repo root and fix what it prints. In roblox-ts, check `projects/common` through a place that uses it: `rogen check projects/game`.
- Other commands read the `*.rogen.json` files of the current folder; run them there, or name the config: `rogen write projects/game`.
- roblox-ts: run `rogen write` before `rbxtsc`, which reads the project file.
- To sync to Studio, run `rogen serve --json` in the background and keep it running; it rewrites on every change. `rogen help serve` explains its lines.
- `rogen help <command> --json` lists a command's flags and the shape of its `--json` output.
````

## Check changed files automatically

The block asks an agent to run `rogen check <paths>` after it adds, moves or renames files. That depends on the agent remembering, and a clean result still costs a tool call.

[`rogen check`](/docs/v2/cli#check-path) prints the diagnostics about the paths it is given, and nothing else, and exits 1 when there are any. A hook that runs when the agent is about to end its turn can use that to report only what the agent's own changes caused.

The script below collects the changed files from git (modified, renamed and untracked, but not deleted), runs `rogen check` on them, and reports each line it hasn't reported earlier in the session. It is a Node script with no dependencies, so it runs wherever Rogen does, Windows included. It runs the Rogen in the project's `node_modules/.bin`, else the one on the `PATH`. The agent gets the report as its next prompt and continues its turn.

It is one script for every agent that has a hook for the end of a turn. They agree on the payload (a JSON object on stdin with the session id and the working directory) and on the reply (`{"decision": "block", "reason": …}` on stdout, which becomes the next prompt). Only Cursor differs, and takes `cursor` as the script's first argument to reply with `followup_message`.

`Stop` and not `PostToolUse`, because `PostToolUse` only sees `Write` and `Edit`, so a move done with `mv` or `git mv` in Bash is invisible, and it would report half-finished states, such as `dev/Service.luau` written before its `prod/` partner. A turn's end checks the end state once.

```js title=".agents/hooks/rogen-check.mjs"
// Agent Stop hook: report new Rogen diagnostics about changed files before the agent ends its turn.
// Pass "cursor" as the first argument for Cursor, which replies with followup_message.
import { spawnSync } from "node:child_process";
import fs from "node:fs";
import path from "node:path";

const git = (...args) => {
	const run = spawnSync("git", args, { encoding: "utf8" });
	return run.status === 0 ? run.stdout : "";
};

let payload = {};
try {
	payload = JSON.parse(fs.readFileSync(0, "utf8"));
} catch {}
const session = String(
	payload.session_id ??
		payload.sessionId ??
		payload.conversation_id ??
		"agent",
).replace(/[^\w.-]/g, "_");
try {
	process.chdir(process.env.CLAUDE_PROJECT_DIR || payload.cwd || ".");
} catch {
	process.exit(0);
}

const changed = [
	...git(
		"diff",
		"-z",
		"--name-only",
		"--relative",
		"--diff-filter=d",
		"HEAD",
	).split("\0"),
	...git("ls-files", "-z", "--others", "--exclude-standard").split("\0"),
].filter(Boolean);
if (!changed.length) process.exit(0);

const seenFile = path.resolve(
	git("rev-parse", "--git-dir").trim(),
	`rogen-hook-${session}`,
);
const seen = fs.existsSync(seenFile)
	? fs.readFileSync(seenFile, "utf8").split("\n")
	: [];

const windows = process.platform === "win32";
const names = windows ? ["rogen.cmd", "rogen.exe"] : ["rogen"];
const locate = (dirs) =>
	dirs
		.flatMap((dir) => names.map((name) => path.join(dir, name)))
		.find((file) => fs.existsSync(file));
const rogen = locate([
	path.resolve("node_modules/.bin"),
	path.join(git("rev-parse", "--show-toplevel").trim(), "node_modules/.bin"),
	...(process.env.PATH ?? "").split(path.delimiter).filter(Boolean),
]);
if (!rogen) {
	const NONE = "# found no rogen";
	if (!seen.includes(NONE)) {
		console.error(
			"Rogen's hook found no rogen; install it in the project or globally",
		);
		fs.appendFileSync(seenFile, `${NONE}\n`);
	}
	process.exit(0);
}

const run = (command, args) =>
	windows && command.endsWith(".cmd")
		? spawnSync([command, ...args].map((part) => `"${part}"`).join(" "), {
				encoding: "utf8",
				stdio: ["ignore", "pipe", "ignore"],
				shell: true,
			})
		: spawnSync(command, args, {
				encoding: "utf8",
				stdio: ["ignore", "pipe", "ignore"],
			});
const check = run(rogen, ["check", ...changed]);
const report = (check.stdout ?? "")
	.split(/\r?\n/)
	.filter((line) => line && !seen.includes(line));
if (!report.length) process.exit(0);

const message = `Rogen warns about files you changed. Fix each, or tell the user why it stays:\n${report.join("\n")}`;
fs.appendFileSync(seenFile, `${report.join("\n")}\n`);
console.log(
	JSON.stringify(
		process.argv[2] === "cursor"
			? { followup_message: message }
			: { decision: "block", reason: message },
	),
);
```

Where it finds an agent, `rogen init` can write the script and register it: a terminal run asks whether to add the hook to the agents it names. An agent is found by a sign in the project, and its hook file is created, or has the entry added to the event's list when it exists. It runs the script through `node`, so it needs no executable bit. A run without a terminal adds it only with `--agent-hook`, and `init` leaves alone an agent that names the script already, and a file that isn't plain JSON, which it says when it writes the hook for other agents.

| Agent | Found by | Hook file | Event | Entry |
|---|---|---|---|---|
| Claude Code | `.claude`, `CLAUDE.md` | `.claude/settings.json` | `Stop` | `node "$CLAUDE_PROJECT_DIR"/.agents/hooks/rogen-check.mjs` |
| Codex | `.codex` | `.codex/hooks.json` | `Stop` | `node "$(git rev-parse --show-toplevel)"/.agents/hooks/rogen-check.mjs` |
| Gemini CLI | `.gemini`, `GEMINI.md` | `.gemini/settings.json` | `AfterAgent` | `node "$GEMINI_PROJECT_DIR"/.agents/hooks/rogen-check.mjs` |
| Cursor | `.cursor` | `.cursor/hooks.json` | `stop` | `node .agents/hooks/rogen-check.mjs cursor` |
| Copilot | `.github/copilot-instructions.md`, `.github/hooks` | `.github/hooks/rogen.json` | `agentStop` | `node "$(git rev-parse --show-toplevel)"/.agents/hooks/rogen-check.mjs` |

To do it by hand, put the script at `.agents/hooks/rogen-check.mjs` and add the entry in the agent's own format. Claude Code, Codex and Gemini CLI take a group of command hooks; Cursor and Copilot take the command itself, in a file that starts with `"version": 1`:

```json title=".claude/settings.json"
{
	"hooks": {
		"Stop": [
			{ "hooks": [{ "type": "command", "command": "node \"$CLAUDE_PROJECT_DIR\"/.agents/hooks/rogen-check.mjs" }] }
		]
	}
}
```

```json title=".cursor/hooks.json"
{
	"version": 1,
	"hooks": { "stop": [{ "command": "node .agents/hooks/rogen-check.mjs cursor" }] }
}
```

Codex runs a project hook only once you trust it: open `/hooks` in Codex to review it.

Tried on a project with one warning already there (`Old@sevre.luau`):

| Turn | The agent sees |
|---|---|
| Adds a clean file | nothing |
| Adds `Buy@sever.luau`, and `git mv`s `Save.luau` to `Save.client.luau` | `route.strayAt` and `tree.deadScript`, one line each |
| Stops again, same state | nothing, it was already reported |
| Fixes the typo, adds `Tax.shared.luau` | only `route.dotRoute` |

The warning that was there before never shows up.

With the hook in place, the "run `rogen check` …" rule in the block is optional, so a repo that uses the hook may drop it.

### Limits

- **Your own changes count too.** The hook can't tell the agent's changes from your uncommitted ones, so a warning in a file you're editing is reported once per session.
- **It needs Node, git and a Rogen.** Node is there wherever Rogen is. With no `rogen` in `node_modules/.bin` or on the `PATH`, the hook prints `Rogen's hook found no rogen; install it in the project or globally` on stderr once per session and lets the turn end, so it never blocks the agent. Install Rogen in the project (`npm i -D @ldgerrits/rogen`) and the next turn is checked.
- **An agent with no hook for the end of a turn** can still run `rogen check <paths>` and read its exit code, as `lint-staged` does: `"*": "rogen check"`.
- **Cursor and Copilot have caps and quirks.** Cursor limits automatic follow-ups (`loop_limit`, 5 by default), and its `stop` hook has been reported not to fire in the CLI or to ignore its reply on Windows. Copilot ends the turn after 8 blocks in a row. The script reports each line once, so neither limit is reached by it.
- **It checks from the folder the agent started in.** The changed files are those below it. `rogen check` finds each file's nearest `default.rogen.json` or `default.project.json`, so a place's file is checked from the repo root. Where there is none, as in root-level places, it takes the named `.rogen.json` files whose source paths hold the file, so a file in `src/common` is checked against every place and reported once. A file no build reads, such as the shared code of a roblox-ts project or a `README.md`, is skipped, and the hook hides the note.

## Install the skill

For a repo that doesn't use `init`, the same text ships as a skill in [`skills/rogen`](https://github.com/LDGerrits/rogen), in the open [Agent Skills](https://agentskills.io) format that most coding agents understand. Install it with the [`skills`](https://github.com/vercel-labs/skills) CLI:

```bash
npx skills add LDGerrits/rogen
```

## What an agent reads

The block is loaded in every session, so it holds only what an agent gets wrong without being told, and the commands that answer the rest:

1. **The block**, about 600 tokens: the rules and the commands that check them.
2. **`rogen doc <topic>`**, between 400 and 2,400 tokens a topic, read when needed: `routing`, `config`, `layout` and `output`. It matches the installed version and works offline.
3. **[`--json`](/docs/v2/cli#json-output) diagnostics**, when something's wrong: each has a stable code, the renames or commands that fix it, and a link to its [explanation](/docs/v2/diagnostics). `rogen help <code>` prints the same explanation.

## Exit codes

Every command ends with `0` (done, warnings included), `1` (the project has a problem, or Rojo failed; `rogen check` also exits 1 on any warning) or `2` (the command line is wrong, or a terminal is needed and there is none), with the same meaning under `--json`. A command that Ctrl+C or SIGTERM ends exits 130 or 143, as the shell reports it. [The table](/docs/v2/cli#exit-codes) is in the reference.

## When a terminal counts as an agent's

Rogen asks nothing when it thinks a program is on the other end: with `CI`, `AGENT` or `AI_AGENT` set, or a variable an agent's harness sets for its commands (`CLAUDECODE` for Claude Code, `CODEX_SANDBOX` for Codex, `CURSOR_AGENT`, `GEMINI_CLI`, …), a real terminal counts as non-interactive. `init` takes its defaults, and `syncback` writes nothing without `-y` (or lists what it would do with `--dry-run`) and exits 2, so an agent that runs it by hand in a terminal needs the flag too. The full list of variables is under [Output](/docs/v2/cli#output).
