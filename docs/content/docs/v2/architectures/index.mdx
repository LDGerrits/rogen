[Core Concepts](/docs/v2/core-concepts/routing) explains how Rogen reads a tree. These pages help you decide which tree to write. Each one describes a layout that works well for a Roblox game, where the idea comes from, and what it costs you.

## Two Axes

A Roblox codebase can be split along two axes:

- **Where code runs:** server, client or both. Roblox requires this split at runtime.
- **What code is about:** inventory, combat, trading.

Rojo maps folders one-to-one onto instances, so without Rogen the first axis has to be your top-level split. Rogen flips that around: every layout here puts features (or layers, then features) at the top, with `Server/`, `Client/` and `Shared/` inside them.

## Comparison

| | [Feature folders](/docs/v2/architectures/feature-folders) | [Layered](/docs/v2/architectures/layered) | [ECS by feature](/docs/v2/architectures/ecs) |
|---|---|---|---|
| **Top level** | One folder per feature | `base`, `platform`, `core`, `features`, `app` | One folder per feature |
| **Inside it** | `Server/`, `Client/`, `Shared/` | Features, each with `Server/`, `Client/`, `Shared/` | Components in `Shared/`, systems per side |
| **Dependency rule** | Features stay independent | Layers only require layers below | Systems read components, not each other |
| **Extra config** | None | Optional invisible layer folders | None |
| **Costs** | Shared code needs a home | More folders, a decision per module | A new model to learn |

## Pick This If…

- **Feature folders** if you're just starting out or moving away from `server/client/shared`. It's the smallest change to how you already write code, and the other two build on it.
- **Layered** if your codebase has grown to the point where utilities, infrastructure and gameplay start to blur together, and you want a clear rule for which module may require which.
- **ECS by feature** if you already use Jecs or Matter, or your game has lots of entities that share behavior, like mobs, projectiles and vehicles.

The layouts also mix well. A layered codebase has feature folders in `core/` and `features/`, and ECS can live inside `features/`.

## Enforcing the Rules

Every rule on these pages is a rule about paths: `platform` doesn't require `features`, one feature doesn't require another, `Shared` doesn't require `Server`. Feature folders put the layer, the feature and the side in every file's path, so a linter can check each rule just by comparing two paths.

With technical grouping, you can't even write these rules down. `InventoryController` sits in `client/Controllers/` next to every other controller, and nothing in its path says it belongs to the inventory, so there's no way to express "the inventory doesn't require trading", let alone check it.

Rogen only routes files; it doesn't read your `require` calls, so checking them is up to your tools. Roblox does enforce one rule for you: `ServerScriptService` isn't replicated, so a client can't require server code at all. But a shared module that requires server code only fails once a client loads it, and a feature that reaches into another's internals works fine right up until someone changes them.

### roblox-ts

ESLint's [`import/no-restricted-paths`](https://github.com/import-js/eslint-plugin-import/blob/main/docs/rules/no-restricted-paths.md) checks imports against folders. This config enforces the [layered](/docs/v2/architectures/layered) rules, using one zone per feature to stop sideways imports:

```js title="eslint.config.js"
import { readdirSync } from "node:fs";
import importPlugin from "eslint-plugin-import";

const features = readdirSync("src/features");

export default [
	{
		files: ["src/**/*.ts"],
		plugins: { import: importPlugin },
		settings: { "import/resolver": { typescript: true } },
		rules: {
			"import/no-restricted-paths": ["error", {
				zones: [
					// Layers only import the layers below them.
					{ target: "./src/base", from: ["./src/platform", "./src/core", "./src/features", "./src/app"] },
					{ target: "./src/platform", from: ["./src/core", "./src/features", "./src/app"] },
					{ target: "./src/core", from: ["./src/features", "./src/app"] },
					{ target: "./src/features", from: "./src/app" },
					// Features don't import each other.
					...features.map((name) => ({
						target: `./src/features/${name}`,
						from: "./src/features",
						except: [`./${name}`],
					})),
					// Shared code runs on both sides.
					{ target: "./src/**/shared/**", from: ["./src/**/server/**", "./src/**/client/**"] },
					{ target: "./src/**/server/**", from: "./src/**/client/**" },
					{ target: "./src/**/client/**", from: "./src/**/server/**" },
				],
			}],
		},
	},
];
```

The resolver setting needs `eslint-import-resolver-typescript`. For [feature folders](/docs/v2/architectures/feature-folders), the side zones work unchanged. Features in that layout are allowed to import the helper features that hold shared code, so give each feature a zone whose `except` lists the helpers it may use.

### Luau

Luau doesn't have a common linter for requires yet, but the check is the same comparison: the path of the requiring file against the path it requires. A short script in CI can handle it. Until you have one, write the rules down in your `AGENTS.md` and hold the line in review.

### Why It Pays Off

- **A smaller blast radius.** When features can't require each other, a change inside `features/Shop` can only break the shop, and a pull request's file list tells you what it can affect.
- **Safe deletes.** Nothing outside a feature requires it, so removing its folder can't break anything else.
- **Teams can work in parallel.** Two people on two features touch different folders, and a crossed boundary fails in CI instead of turning up in review weeks later.
- **Agents stay inside the lines.** An agent can run the linter, see which boundary it crossed, and fix it before you review. See [Working with agents](/docs/v2/agents).
- **The architecture holds up.** Rules that only live in people's heads get broken one shortcut at a time. Rules in a lint config don't.

<Callout type="info" title="About the examples">
	The trees use the routes `rogen init` writes for Luau. In a roblox-ts project, the routing folders are lowercase (`server/`, `client/`, `shared/`) and the files end in `.ts`. Client modules go to `StarterPlayerScripts` because that's where `init` sends them; point the `Client` route at a folder in `ReplicatedStorage` if you'd rather keep them there.
