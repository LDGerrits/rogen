This is feature folders, stacked in layers. Each layer can only require the layers below it, so you can tell which way a dependency points just by looking at the path.

## The Rule

The top level has five layers, and each holds modules or feature folders with `Server/`, `Client/` and `Shared/` inside:

| Layer | Holds | May require |
|---|---|---|
| `base` | Pure utilities that know nothing about the game: `Signal`, `Promise` | `base` |
| `platform` | Wrappers around Roblox and infrastructure: networking, data stores | `base`, `platform` |
| `core` | Game rules most features build on: combat, characters | `base`, `platform`, `core` |
| `features` | Gameplay features: inventory, trading, quests | `base`, `platform`, `core` |
| `app` | The entry points: one `Script` and one `LocalScript` | everything |

Features don't require each other; when two features need the same thing, it moves down into `core`. Inside each feature, the sides follow one more rule:

- `Shared` requires only `Shared`.
- `Server` and `Client` require `Shared`, never each other.

## Where It Comes From

- **VS Code.** Its [source code organization](https://github.com/microsoft/vscode/wiki/Source-Code-Organization) splits the code into layers (`base`, `platform`, `editor`, `workbench`, and `code` as the entry point that "stitches everything together"), each depending only on the layers below it. "Inside each layer the code is organised by the target runtime environment", and workbench features live in `contrib/<feature>/`, which nothing outside `contrib` depends on. VS Code checks its runtime rules with its own ESLint rule, `code-layering`.
- **Game engines.** Jason Gregory's _Game Engine Architecture_ ([CRC Press](https://www.gameenginebook.com/)) describes a runtime engine as a stack of layers, from platform independence up through core systems to gameplay foundations and game-specific code. On Roblox, the engine layers _are_ Roblox, so what's left for your game is the top of that stack: this page's `platform`, `core` and `features`.
- **Unreal's Lyra.** Epic's [Lyra sample](https://dev.epicgames.com/documentation/en-us/unreal-engine/lyra-sample-game-in-unreal-engine) keeps a small, generic core and ships gameplay as [Game Feature plugins](https://dev.epicgames.com/documentation/en-us/unreal-engine/game-features-and-modular-gameplay-in-unreal-engine), "fully encapsulated within the plugin". That's the `core` and `features` split.
- **Roblox.** [Script locations](https://create.roblox.com/docs/scripting/locations) recommends "a single entry point on the client and server sides". That's `app`.

`base/` has no routing folder because everything in it runs on both sides, and `app/` holds nothing but the two entry points.

## The Config

The routes `rogen init` writes are enough:

```json title="default.rogen.json"
{
	"$schema": "https://ldgerrits.github.io/rogen/schema/2/rogen.json",
	"rootDirs": ["src"],
	"routes": {
		"Server": "ServerScriptService",
		"Client": "StarterPlayer/StarterPlayerScripts",
		"Shared": "ReplicatedStorage/Shared",
		"*": "ReplicatedStorage/Shared"
	}
}
```

`base/` matches no route, so the `*` route sends it to `ReplicatedStorage/Shared`, which is the Roblox version of VS Code's rule that `base` code runs everywhere.

### Dropping a Layer From Studio

By default the layers show up in Studio, as in `ServerScriptService/features/Inventory`. To keep a layer on disk only, make it an [invisible folder](/docs/v2/core-concepts/project-layout#invisible-folders). With every layer invisible, you get:

```
src/(base)/Signal.luau                                 ->  ReplicatedStorage/Shared/Signal
src/(features)/Inventory/Server/InventoryService.luau  ->  ServerScriptService/Inventory/InventoryService
src/(app)/Server/main.server.luau                      ->  ServerScriptService/main
```

<Callout type="warn" title="Invisible layers share one namespace">
	With invisible layers, two layers can produce the same instance. A `Combat` folder in both `(core)` and `(features)` turns into a single `Combat` folder in Studio, and a module with the same name in both is a clash (Rogen warns, and the last one wins). Keep the layers visible if feature names repeat across them.
</Callout>

`app/Server/main.server.luau` becomes a `Script` named `main`, and `app/Client/main.client.luau` a `LocalScript`. The routing folder governs here, so `.server` and `.client` only set the class.

## Why It Fits a Game

- **Server and client is VS Code's problem too.** VS Code splits by runtime so code for one environment never calls another's APIs, the same rule you want between `Server` and `Client`.
- **It scales with the team.** No feature requires another, so work in `features/Trading` can't break the rest of the game.
- **One entry point per side.** Scripts only start in `app/`, as Roblox recommends, so everything else is a module you can require, test or disable.
- **Live games keep changing.** New modes and events are new folders in `features/`, on a core that changes less often.

## Trade-offs

- **More folders.** Small games don't need five layers; start with [feature folders](/docs/v2/architectures/feature-folders) and add layers as things pile up.
- **Every module needs a layer.** `core` or `features`? `platform` or `base`? Write down what each layer means for your game.
- **The rules need a linter.** ESLint can enforce them in roblox-ts; Luau has no common tool yet. See [Enforcing the Rules](/docs/v2/architectures#enforcing-the-rules).
- **Longer paths in Studio,** unless you make the layers invisible and accept possible name clashes.

## Feature-Sliced Design

[Feature-Sliced Design](https://fsd.how/docs/get-started/overview) is the same idea as it caught on in frontend development, plus one extra rule. Its [layers](https://fsd.how/docs/reference/layers) are `app`, `pages`, `widgets`, `features`, `entities` and `shared`, each split into **slices**, and:

- "A module (file) in a slice can only import other slices when they are located on layers strictly below."
- "Slices cannot use other slices on the same layer."

That second rule is what makes it stricter. The layout above lets a module require others in its own layer (`core` requires `core`), but FSD never allows a sideways require, except in `app` and `shared`, which don't have slices. In a game, `pages` becomes screens or modes, `widgets` holds HUD pieces, and each slice gets routing folders:

<Callout type="warn" title="shared is a route key">
	FSD's `shared` layer has the same name as the `Shared` route, so it acts as a routing folder and its modules land directly in `ReplicatedStorage/Shared`. Because the outer route governs, a `Server/` folder inside it is just an ordinary folder, and any server code there goes to every client (Rogen warns when that happens). Keep `shared/` for code both sides run, or give the layer another name.
</Callout>

Go with FSD if your team wants the stricter rule, or already knows it from the web.
