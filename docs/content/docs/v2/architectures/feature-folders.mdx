This is the baseline layout, and the reason Rogen exists. You may also know it as **package by feature** or **vertical slices**.

## The Rule

Everything one feature needs goes in one folder, and nothing else goes there. Inside it, a routing folder per side says where each piece runs:

- `Server/` for code only the server runs,
- `Client/` for code only clients run,
- `Shared/` for code both sides require: types, config, remote definitions.

Features stay independent of each other. When several features need the same code, it becomes a feature of its own, named after what it does.

## Where It Comes From

- **Package by feature.** John O'Hanley's [_Package by feature, not layer_](http://www.javapractices.com/topic/TopicAction.do?Id=205) argues that grouping by feature gives "packages with high cohesion and high modularity, and with minimal coupling between packages". His test for modularity is deletion: "an item has maximum modularity only if it can be deleted in a single operation".
- **Vertical slices.** Jimmy Bogard's [vertical slice architecture](https://www.jimmybogard.com/vertical-slice-architecture/) says the same for backends: "Minimize coupling between slices, and maximize coupling in a slice". A feature folder is a vertical slice.
- **Domain-driven design.** Eric Evans' [_DDD Reference_](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) asks for modules that "tell the story of the system", named in the language of the domain. On Roblox, that means `Trading/` and `Quests/`, not `Services/`.
- **Game engines.** Godot's [project organization](https://docs.godotengine.org/en/stable/tutorials/best_practices/project_organization.html) advice is to "group assets as close to scenes as possible", because it keeps a growing project maintainable.
- **Roblox.** [Nevermore](https://github.com/Quenty/NevermoreEngine) puts `Client/`, `Server/` and `Shared/` inside every package, the same shape as a Rogen feature folder.

`Inventory` is the simple case: a service on the server, a controller on the client and the types both sides share. The other two show how common game patterns fit inside a feature folder.

### A Component: `Door`

The [component pattern](https://gameprogrammingpatterns.com/component.html) exists to "allow a single entity to span multiple domains without coupling the domains to each other". On Roblox, a component is usually bound to every instance with a given [tag](https://create.roblox.com/docs/studio/properties#instance-tags), and since tags replicate from the server to the client, both sides find the same doors.

- `DoorServer` owns the state: it checks who can open a door, and opens it.
- `DoorClient` animates the door and plays its sound.
- `DoorConfig` holds the tag name and timings both sides read.


### UI With a View Model: `Shop`

In [MVVM](https://learn.microsoft.com/en-us/archive/blogs/johngossman/introduction-to-modelviewviewmodel-pattern-for-building-wpf-apps), a view model holds the state of a view and the view just draws it. That split lines up nicely with the sides of a game:

- **Model:** `ShopCatalog` (the items and prices, shared) and `ShopService` (the purchase, which only the server gets to decide).
- **View model:** `ShopState`, the client-side state of the window: whether it's open, which item is selected.
- **View:** `ShopWindow` and `ShopItemCard`, written with a UI library such as [Fusion](https://elttob.uk/Fusion/0.3/) or [react-lua](https://github.com/jsdotlua/react-lua).

`(Ui)` is an [invisible folder](/docs/v2/core-concepts/project-layout#invisible-folders). It groups the views on disk and disappears in Studio.

## The Config

The routes `rogen init` writes are all this layout needs, and the invisible folder doesn't need any config at all.

```json title="default.rogen.json"
{
	"$schema": "https://ldgerrits.github.io/rogen/schema/2/rogen.json",
	"rootDirs": ["src"],
	"routes": {
		"Server": "ServerScriptService",
		"Client": "StarterPlayer/StarterPlayerScripts",
		"Shared": "ReplicatedStorage/Shared",
		"*": "ReplicatedStorage/Shared"
	}
}
```

## Why It Fits a Game

- **Gameplay features span every side.** Input on the client, validation on the server, types in between. A feature folder keeps all three together, so a change to the shop is a change to `Shop/`.
- **Removing a feature is one delete.** Delete `Shop/` and every script it placed in Studio goes with it, which is exactly O'Hanley's test for modularity.
- **Server code stays on the server.** `Server/` routes to `ServerScriptService`, which isn't replicated, so exploiters can't read it. And because the split happens inside each feature, you can see it in every folder, not just at the root.
- **The tree tells you what the game is.** The top level reads `Door`, `Inventory`, `Shop` instead of `server`, `client`, `shared`.

## Trade-offs

- **Code used everywhere needs a home.** A `Signal` class or a remote wrapper doesn't belong to any one feature, so give it a feature folder of its own, named after what it does. Once you have a lot of these, the [layered](/docs/v2/architectures/layered) layout gives them a proper place.
- **Nothing stops one feature from reaching into another.** Rogen doesn't read requires, but because the feature is in every path, a linter can. See [Enforcing the Rules](/docs/v2/architectures#enforcing-the-rules).
- **Paths get one level deeper.** Requires read `ReplicatedStorage.Shared.Shop.ShopCatalog` instead of `ReplicatedStorage.Shared.ShopCatalog`.
- **Big features need subfolders.** A feature can have folders of its own, with routing folders at any depth inside them. Just don't nest one routing folder inside another, because only the outer one counts.

<Callout type="info">
	Routing folders are the recommended way to route in this layout, but for a feature with only a file or two, `Door@server.luau` works too and keeps things flat. See [The `@` Sign](/docs/v2/core-concepts/routing#the--sign).
</Callout>
