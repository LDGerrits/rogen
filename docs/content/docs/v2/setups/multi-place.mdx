When one repo builds several places, each **place** is a config that `extends` a shared one and adds its own folder to the root directories. Its template merges over the shared one, so it gives the place its own name and port. Each place keeps its config, template, code and project file in its own folder, a small project inside the repo, and the root keeps only the shared config.

<Steps>

<Step>
### Structure the Repository

Give every place a folder of its own, with its code in `src` and its config and template beside it. They stay outside `src`, since anything inside a root directory is synced into the game. The shared code goes in one of two places:

<Tabs items={["Beside the places", "At the root"]}>
  <Tab value="Beside the places">
    The shared core is one more folder under `places/`, so every piece of code has the same shape. This is what `init` sets up for a new project.

    <SystemWindow>
    	<TreeFile name="default.rogen.json" />
    	<TreeFolder name="places" open />
    	<TreeFolder level={1} name="shared" open />
    	<TreeFile level={2} name="template.project.json" />
    	<TreeFolder level={2} name="src" />
    	<TreeFolder level={1} name="lobby" open />
    	<TreeFile level={2} name="lobby.rogen.json" />
    	<TreeFile level={2} name="template.project.json" />
    	<TreeFolder level={2} name="src" />
    </SystemWindow>

    `default.rogen.json` has `"rootDirs": ["places/shared/src"]` and `"template": "places/shared/template.project.json"`.
  </Tab>
  <Tab value="At the root">
    The shared code stays in `src`, as in a one-place project. `init` keeps it there when `src` already holds code.

    <SystemWindow>
    	<TreeFile name="default.rogen.json" />
    	<TreeFile name="template.project.json" />
    	<TreeFolder name="src" />
    	<TreeFolder name="places" open />
    	<TreeFolder level={1} name="lobby" open />
    	<TreeFile level={2} name="lobby.rogen.json" />
    	<TreeFile level={2} name="template.project.json" />
    	<TreeFolder level={2} name="src" />
    </SystemWindow>
  </Tab>
</Tabs>

Run from the root, Rogen [finds every config](/docs/v2/configuration#finding-configs) whose `extends` chain reaches `default.rogen.json`, so one `rogen serve` sees every place, and `rogen serve lobby` finds `places/lobby/lobby.rogen.json` by its name. Each place's project file is written beside its config, as `places/lobby/lobby.project.json`. `default` is still built, for luau-lsp and `rogen build`, but never served while places extend it.

A place's config, template and code can also be a repo of their own, such as a Git submodule, as long as its config extends the shared one.

</Step>

<Step>
### Add the Place

Starting fresh, run `rogen init` and pick **Several places that share code**; it asks where the shared code goes. To add one later, run it again and pick **A place**; it only asks for a name and folder, and puts the folder beside the shared one (`projects/shared/src` gives `projects/lobby`). Scripts and agents can skip the questions:

```bash
rogen init                    # in a terminal, then pick A place
rogen init lobby -y           # without asking
```

What `init` writes depends on your toolchain:

<Tabs items={["Luau", "roblox-ts"]} groupId="language" persist>
  <Tab value="Luau">
    One config and the place's template:

    ```json title="places/lobby/lobby.rogen.json"
    {
    	"$schema": "https://ldgerrits.github.io/rogen/schema/2/rogen.json",
    	"extends": "../../default.rogen.json",
    	"rootDirs": ["src"],
    	"template": "template.project.json"
    }
    ```

    ```json title="places/lobby/template.project.json"
    {
    	"name": "Lobby",
    	"servePort": 34873,
    	"tree": { "$className": "DataModel" }
    }
    ```

    The place's root directory is added to those of `default.rogen.json`. They merge into one tree, and the later one wins a clash, so a place can override shared code. Its template [merges over](/docs/v2/core-concepts/output#merging-templates) the shared one, so it keeps the shared package mounts and `$properties`. Each place gets the first port above 34872 that no other config's template uses.
  </Tab>
  <Tab value="roblox-ts">
    One config, the place's template, and one tsconfig, since the place's compiled files need their own `outDir`:

    ```json title="places/lobby/lobby.rogen.json"
    {
    	"$schema": "https://ldgerrits.github.io/rogen/schema/2/rogen.json",
    	"extends": "../../default.rogen.json",
    	"rootDirs": ["src"],
    	"template": "template.project.json",
    	"syncDir": "../../out/lobby"
    }
    ```

    ```json title="places/lobby/tsconfig.lobby.json"
    {
    	"extends": "../../tsconfig.json",
    	"compilerOptions": {
    		"rootDir": null,
    		"rootDirs": ["../../src", "src"],
    		"outDir": "../../out/lobby"
    	},
    	"include": ["../../src", "src"]
    }
    ```

    `init` won't edit your `tsconfig.json`, but tells you to add `"include"` with the shared root directory if it's missing, so the main build skips the place folders, and to change `"rootDir"` if the shared code isn't where it points.
  </Tab>
</Tabs>

Paths in a config are relative to it, so a place's own paths stay short. A place folder that already holds code is used as it is: `init` adds the folder itself as the root directory, and puts the config and template beside the folder, as `places/lobby.rogen.json` and `places/lobby.template.project.json`, so no code moves and nothing but code is synced. A template already at the place's path is used as it is too, and places whose configs sit at the repo root, as older versions of `init` wrote them, keep working.

</Step>

<Step>
### Serve

Serve every place at once, each on its own port:

<Tabs items={["Luau", "roblox-ts"]} groupId="language" persist>
  <Tab value="Luau">
    ```bash
    rogen serve
    ```
  </Tab>
  <Tab value="roblox-ts">
    ```bash
    rbxtsc -w -p places/lobby/tsconfig.lobby.json --rojo places/lobby/lobby.project.json
    rogen serve
    ```
  </Tab>
</Tabs>

`rogen serve` builds every config and starts a server for each place, on the port its template sets. A place added while it serves gets its server too. In Studio, connect to the place's port. `rogen serve lobby` serves just the one place, which is what `init` prints when other configs here would share a port, such as places set up before they got their own templates. `rogen list` shows every config the repo can build, and the templates each one merges.

</Step>

</Steps>

## With Darklua

Each place needs a project file for its source (for Darklua) and one for the processed output (for Studio), so it becomes two configs in its folder:

```json title="places/lobby/lobby.rogen.json"
{
	"$schema": "https://ldgerrits.github.io/rogen/schema/2/rogen.json",
	"extends": "../../default.rogen.json",
	"rootDirs": ["src"],
	"template": "template.project.json"
}
```

```json title="places/lobby/lobby-sync.rogen.json"
{
	"$schema": "https://ldgerrits.github.io/rogen/schema/2/rogen.json",
	"extends": "./lobby.rogen.json",
	"syncDir": "../../dist/lobby"
}
```

Rojo writes a sourcemap's paths from its project file's folder, so the place's sourcemap goes beside its project file. Darklua finds a sourcemap's files only when the sourcemap sits beside its config, so give the place a copy of your Darklua config in its folder, reading the place's sourcemap:

```json title="places/lobby/lobby.darklua.json"
{
	"rules": [
		{
			"rule": "convert_require",
			"current": { "name": "path" },
			"target": {
				"name": "roblox",
				"rojo_sourcemap": "./lobby.sourcemap.json",
				"indexing_style": "property"
			}
		}
	]
}
```

Darklua reads every path in that config from `places/lobby`. Synced paths keep each root directory's path from the repo root (`dist/lobby/src/…`, `dist/lobby/places/lobby/src/…`), so run Darklua once per root directory, from the root:

```bash
darklua process --config places/lobby/lobby.darklua.json src dist/lobby/src
darklua process --config places/lobby/lobby.darklua.json places/lobby/src dist/lobby/places/lobby/src
rogen serve lobby-sync
rojo sourcemap places/lobby/lobby.project.json --output places/lobby/lobby.sourcemap.json --watch
```

`rogen serve lobby-sync` builds every config, `lobby.project.json` included, and serves the processed one. Name every place's synced config to serve them all, as `rogen serve lobby-sync arena-sync`: a bare `rogen serve` would also serve `sync.rogen.json`, which holds only the shared code.

Each place keeps its own config and sourcemap, so every place processes at once. luau-lsp keeps the root `sourcemap.json` current from `default.project.json` without touching them.

## Editor and Git

luau-lsp reads `default.project.json`, which holds the shared code. To have it see a place's own code while you work on it, have it build the place's sourcemap instead. luau-lsp reads a sourcemap's paths from the workspace root, and Rojo writes a place's from its folder, so ask Rojo for absolute paths:

```json title=".vscode/settings.json"
{
	"luau-lsp.sourcemap.generatorCommand": "rojo sourcemap places/lobby/lobby.project.json --output editor.sourcemap.json --absolute --watch",
	"luau-lsp.sourcemap.sourcemapFile": "editor.sourcemap.json"
}
```

Darklua can't read absolute paths, so this sourcemap stays apart from the ones Darklua reads.

Rogen writes each place's project file in its folder, beside the template you keep. Ignore the written ones, not the templates:

```text title=".gitignore"
*.project.json
!template.project.json
!*.template.project.json
sourcemap.json
*.sourcemap.json
```

<Callout type="info">
	Shared `routes`, `variants`, `modes` and `template` live in the config every place extends, so each place only has to say what's different. A place's own `modes.prod.exclude` adds globs to the shared `prod` mode, and `rogen build --mode prod` builds every place in it, failing if a place lacks that mode so a release never builds one in dev. See [Modes](/docs/v2/core-concepts/modes).
</Callout>
