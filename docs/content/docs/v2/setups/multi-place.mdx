When one repo builds several places, each **place** is a config that `extends` a shared one and adds its own folder to the root directories.

<Steps>

<Step>
### Structure the Repository

Keep shared code in `src` and each place's own code in `places/<name>`.

<SystemWindow>
	<TreeFolder name="src" open />
	<TreeFolder level={1} name="Combat" />
	<TreeFolder name="places" open />
	<TreeFolder level={1} name="lobby" open />
	<TreeFolder level={2} name="Lobby" />
</SystemWindow>

</Step>

<Step>
### Add the Place

Starting fresh, run `rogen init` and pick **Several places that share code**. To add one later, run it again and pick **A place**; it only asks for a name and folder. Scripts and agents can skip the questions:

```bash
rogen init                    # in a terminal, then pick A place
rogen init lobby --no-input   # without asking
```

What `init` writes depends on your toolchain:

<Tabs items={["Luau", "roblox-ts"]} groupId="language" persist>
  <Tab value="Luau">
    One config:

    ```json title="lobby.rogen.json"
    {
    	"$schema": "https://ldgerrits.github.io/rogen/schema/2/rogen.json",
    	"extends": "./default.rogen.json",
    	"rootDirs": ["src", "places/lobby"]
    }
    ```

    Both root directories merge into one tree, and the later one wins a clash, so a place can override shared code.
  </Tab>
  <Tab value="roblox-ts">
    One config and one tsconfig, since the place's compiled files need their own `outDir`:

    ```json title="lobby.rogen.json"
    {
    	"$schema": "https://ldgerrits.github.io/rogen/schema/2/rogen.json",
    	"extends": "./default.rogen.json",
    	"rootDirs": ["src", "places/lobby"],
    	"syncDir": "out/lobby"
    }
    ```

    ```json title="tsconfig.lobby.json"
    {
    	"extends": "./tsconfig.json",
    	"compilerOptions": {
    		"rootDir": null,
    		"rootDirs": ["src", "places/lobby"],
    		"outDir": "out/lobby"
    	},
    	"include": ["src", "places/lobby"]
    }
    ```

    `init` won't edit your `tsconfig.json`, but tells you to add `"include": ["src"]` if it's missing, so the main build skips the place folders.
  </Tab>
</Tabs>

</Step>

<Step>
### Start Watching

Name the place to build it:

<Tabs items={["Luau", "roblox-ts"]} groupId="language" persist>
  <Tab value="Luau">
    ```bash
    rogen watch lobby
    rojo serve lobby.project.json
    ```
  </Tab>
  <Tab value="roblox-ts">
    ```bash
    rbxtsc -w -p tsconfig.lobby.json --rojo lobby.project.json
    rogen watch lobby
    rojo serve lobby.project.json
    ```
  </Tab>
</Tabs>

`rogen list` shows every config the repo can build.

</Step>

</Steps>

## With Darklua

Each place needs a project file for its source (for Darklua) and one for the processed output (for Studio), so it becomes two configs:

```json title="lobby.rogen.json"
{
	"$schema": "https://ldgerrits.github.io/rogen/schema/2/rogen.json",
	"extends": "./default.rogen.json",
	"rootDirs": ["src", "places/lobby"]
}
```

```json title="lobby-sync.rogen.json"
{
	"$schema": "https://ldgerrits.github.io/rogen/schema/2/rogen.json",
	"extends": "./lobby.rogen.json",
	"syncDir": "dist/lobby"
}
```

Synced paths keep each root directory's path from the repo root (`dist/lobby/src/…`, `dist/lobby/places/lobby/…`), so run Darklua once per root directory:

```bash
darklua process src dist/lobby/src
darklua process places/lobby dist/lobby/places/lobby
rogen watch lobby lobby-sync
rojo sourcemap lobby.project.json --output sourcemap.json --watch
rojo serve lobby-sync.project.json
```

One catch: luau-lsp regenerates `sourcemap.json` from `default.project.json` and would overwrite the place's version. While you work on a place, set `"luau-lsp.sourcemap.rojoProjectFile": "lobby.project.json"`, or turn off `luau-lsp.sourcemap.autogenerate`.

<Callout type="info">
	Shared `routes`, `variants` and `template` live in the config every place extends, so each place only has to say what's different.
</Callout>
