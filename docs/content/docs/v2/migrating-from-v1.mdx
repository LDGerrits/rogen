import { Callout } from "fumadocs-ui/components/callout";

v2 is a clean break. It won't read a v1 `.rogen.json`, and a `default.rogen.json` with v1's keys is an error that points here. There's no `migrate` command. A fresh config only takes `init` a few seconds; the real work is in how v2 reads your **tree** differently, which is what this page covers.

<Steps>

<Step>
### Run `rogen init`

[Install v2](/docs/v2/installation), then run `init` in the project root:

```bash
rogen init
```

It writes `default.rogen.json`. If you have a hand-written `default.project.json`, its keys are lifted into `default.rogen.json`, because v2 [owns its output](/docs/v2/core-concepts/output#output). Rogen writes `default.project.json` from then on, so `init` prints `git rm --cached default.project.json` to stop git tracking it.

v2 doesn't look for a `.rogen.json`, so your v1 config stays where it is for the comparison below. Rename it if you want it out of the way:

```bash
mv .rogen.json .rogen.json.v1
```

</Step>

<Step>
### Match Your Old Paths

v1 added a wrapper folder under each service (`ServerScriptService/server`, `ReplicatedStorage/shared`). In v2 the target is the whole path, so write the wrappers in to keep your v1 `require` paths working:

```json title="default.rogen.json"
{
	"rogen": {
		"routes": {
			"server": "ServerScriptService/server",
			"client": "StarterPlayer/StarterPlayerScripts/client",
			"shared": "ReplicatedStorage/shared",
			"*": "ReplicatedStorage/shared"
		}
	}
}
```

If you used `unwrap`, leave the wrapper out. If you used `casing: "PascalCase"`, capitalize it. Any `aliases` become routes too.

</Step>

<Step>
### Rename Your Files

v2 has fewer ways to route by name, so most projects have files to rename. The [removed features](#removed-features) below each say what replaces them.

</Step>

<Step>
### Build and Compare

```bash
rogen build
```

Read the warnings. Files that used an old suffix no longer route, so they fall through to the `*` route. You can find them with:

```bash
rogen where | grep fallback
```

Then compare the result in Studio with your v1 build, and delete `.rogen.json.v1` once they match.

</Step>

</Steps>

## Removed Features

### Prefixes and Most Suffixes

v1 routed files by a keyword anywhere at the start or end of a name, which made accidents easy: `HttpClient.luau` went to the client and lost its `Client`. v2 only routes by name with `@key` at the end, or with Rojo's own `.server` and `.client` on a script. A [routing folder](/docs/v2/core-concepts/routing#routing-folders) is usually even better:

```
v1: src/Combat/server_Combat.luau     v2: src/Combat/Server/Combat.luau
v1: src/Combat/Combat_Server.luau     v2: src/Combat/Combat@server.luau
v1: src/Combat/CombatServer.luau      v2: src/Combat/Combat@server.luau
v1: src/Combat/Types.shared.luau      v2: src/Combat/Types@shared.luau
v1: src/Combat/Hud.client.luau        v2: unchanged
v1: src/Combat/Gun.server.rbxm        v2: src/Combat/Gun@server.rbxm
v1: src/Combat/.server                v2: src/Combat/@server
```

Route marker files now take `@` too: v1's `.server` becomes `@server`. So do models and data files, which have no script class for Rojo to read: `Gun.server.rbxm` becomes `Gun@server.rbxm`. Rogen warns about each dot-file or dot part that spells a route key and names its `@` form, and `--json` lists the renames, so the build output is a checklist.

### Tags

v2 has no tags. A file that v1 built only while a tag was on now lives in an **overlay source path**, a folder of its own that only the config files wanting it list. A later source path wins a clash without a warning, and a file with no plain twin is simply added. Put the overlay in `default.rogen.json` if your everyday build wants it, and write a second complete file, `release.rogen.json`, that leaves it out. A second file repeats `name`, `routes` and `tree` and changes only what differs; it needs its own `name`, because Rojo can't open a project file without one:

```
v1: src/Teleport/Teleport.luau, src/Teleport/TeleportDev.luau (tag dev)
v2: src/Teleport/Teleport.luau, dev/Teleport/Teleport.luau (the dev source path)
```

```json title="default.rogen.json"
{
	"name": "Game",
	"rogen": {
		"sourcePaths": ["src", "dev"],
		"routes": { "server": "ServerScriptService", "*": "ReplicatedStorage" }
	}
}
```

```json title="release.rogen.json"
{
	"name": "Game",
	"rogen": {
		"sourcePaths": ["src"],
		"routes": { "server": "ServerScriptService", "*": "ReplicatedStorage" }
	}
}
```

`rogen build` writes `default.project.json` with the overlay, and `rogen build release` writes `release.project.json` without it. Each command writes only the file you name, so `rogen list` shows how `release` differs from `default`. A file that is not an overlay of anything, such as a spec, is left out of a project with `globIgnorePaths` instead. See [Replacing a File](/docs/v2/core-concepts/project-layout#replacing-a-file).

<Callout type="warn" title="Old tag names ship">
	v1 dropped `TeleportDev.luau` when `dev` was off. In v2 it's an ordinary file that ships in every build, and a dot suffix such as `Teleport.dev.luau` is part of the name, so move these files before your first v2 release.
</Callout>

### The Deepest Rule Wins

In v1 the deepest rule won, so a suffix beat its folder. In v2 the [outermost route governs](/docs/v2/core-concepts/routing#the-governing-route) and everything below it is ignored. That fixes v1's best-known surprise:

```
src/ReplicatedFirst/main.client.luau
v1: StarterPlayer/StarterPlayerScripts/client/main   (the .client suffix won)
v2: ReplicatedFirst/main                             (the folder governs; still a LocalScript)
```

### Built-in Service Keywords

v1 routed any folder named after a service. In v2 only declared routes exist, so add the ones you use, like `"ReplicatedFirst": "ReplicatedFirst"`.

### `.unwrap`, `unwrap` and `casing`

Targets are paths, so the wrapper folder is whatever the target says: `"ServerScriptService"` is unwrapped and `"ReplicatedStorage/Shared"` is PascalCase.

### `.verbatim` and `verbatim`

These kept keywords like the `Client` in `HttpClient`. v2 doesn't strip them in the first place.

### `.structure`

Put the marker file of the route you want in the folder instead, such as `@shared`. As the outer route, it governs everything below.

### `.sync`

Mount the folder in the [tree](/docs/v2/configuration#tree) as a plain `$path`, and Rogen leaves it alone:

```json title="default.rogen.json"
{
	"name": "my-game",
	"tree": {
		"$className": "DataModel",
		"ReplicatedStorage": {
			"Roact": { "$path": "src/Vendor/Roact" }
		}
	},
	"rogen": {
		"routes": { "*": "ReplicatedStorage/Shared" }
	}
}
```

### `^` Hoisting

Make the folders above the file [invisible](/docs/v2/core-concepts/project-layout#invisible-folders) instead. That hoists everything inside them, not just one file:

```
v1: src/Physics/Server/^CollisionService.luau
v2: src/(Physics)/Server/CollisionService.luau  ->  ServerScriptService/CollisionService
```

### The `ReplicatedStorage` Default

v1 sent unmatched files to `ReplicatedStorage`, which could leak server code to clients. v2 never guesses, so declare the [fallback route](/docs/v2/core-concepts/routing#files-that-match-no-route) `"*"` yourself.

### Modes and Profiles

A v1 mode changed which files a build had and where Rojo read them. In v2 it is a second complete file beside `default.rogen.json`: `dist.rogen.json` writes `dist.project.json`. The file repeats `name`, `routes` and `tree` and changes the keys that differ. Nothing is inherited, so a change to the routes is made in each file, and `rogen list` shows how every file differs from `default`.

```json title="dist.rogen.json"
{
	"name": "Game",
	"rogen": {
		"sourcePaths": ["src"],
		"routes": {
			"Server": "ServerScriptService",
			"Client": "StarterPlayer/StarterPlayerScripts",
			"Shared": "ReplicatedStorage/Shared",
			"*": "ReplicatedStorage/Shared"
		},
		"compiledPath": "dist"
	}
}
```

`rogen serve dist` or `rogen build dist -o game.rbxl` picks it by name. A bare `rogen serve` serves `default.rogen.json`, as a bare `rojo serve` serves `default.project.json`, so `init` prints the command that fits your setup. A v1 mode that only flipped tags becomes a file with its own `sourcePaths`, as above.

A repo that built several places from one config becomes a [folder per place](/docs/v2/setups/places): each place has its own complete `default.rogen.json`, and the code they share is a plain folder that each place lists in `sourcePaths`.

## Config Fields

| v1 | v2 |
|---|---|
| `.rogen.json`, or the first `*.rogen.json` | `default.rogen.json` (or `default.rogen.jsonc`) in a folder, and `<name>.rogen.json` for a second output; `init` writes the default |
| `source` | `sourcePaths`, inside the `rogen` block |
| modes (`luau`, `ts`, `darklua`, custom) | a second complete file, `<name>.rogen.json`, that repeats the keys and changes the ones that differ |
| a mode's `build` | `compiledPath`, inside the `rogen` block of the file for that mode |
| a mode's `output` | removed. Rogen writes `<name>.project.json` beside `<name>.rogen.json` |
| `tags` at the root and in modes | removed. An overlay source path that only the config files wanting those files list, or `globIgnorePaths` |
| `globIgnorePaths` | `globIgnorePaths`, Rojo's own key, which Rogen also writes to the project file |
| `aliases` and built-in service keywords | `routes`, inside the `rogen` block. Only declared keys route |
| `casing`, `unwrap` | route targets as paths |
| `verbatim` | removed; nothing routes by accident |
| `project`, or the legacy `template` | `tree`, written inline in `default.rogen.json` |

## Behavior

| v1 | v2 |
|---|---|
| the mode is picked from the detected toolchain | only `init` detects anything; a build does what the config says |
| `build` replaces the first path segment | `compiledPath` replaces the [common root](/docs/v2/core-concepts/output#compiled-path) of the source paths |
| Rogen adopts an existing project file | Rogen owns the project files it writes and replaces them; hand-written content goes in `tree` |
| packages and `rbxts_include` injected from the toolchain | mounted in the `tree`, which `init` writes |
| empty placeholder files for compiled toolchains | none: every emitted `$path` is optional |
| a full rebuild on every change | incremental rebuilds, and the config reloads while watching |

## CLI

| v1 | v2 |
|---|---|
| `-m, --mode <mode>` | removed. Name a file: `rogen build release`, `rogen serve dist` |
| `-b, --build <path>` | removed. Set `compiledPath` in the `rogen` block |
| `-s, --source <path>` | removed. Set `sourcePaths` in the `rogen` block |
| `-o, --output <path>` | not the same. Rogen writes the project file beside the `.rogen.json`; `rogen build -o game.rbxl` has Rojo build a place file from it |
| `-p, --project <path>` | removed. Set `tree` in `default.rogen.json`. `-p` now builds a plugin: `rogen build -p Tool.rbxm` |
| `-t, --tag <tag>` | removed. Name the file whose `sourcePaths` list the overlay |
| `-v, --version` | `-V, --version` |

<Callout type="warn" title="-v changed meaning">
	In v1, `-v` printed the version. In v2 it's `--verbose`, and `-V` prints the version, as in Rojo, Wally and Selene. A bare `rogen` prints usage instead of building. Check any scripts that call Rogen.
</Callout>

v2 also adds `rogen list`, `rogen where`, `rogen check`, `--json`, JSONC configs, Rojo's keys in the config, and diagnostics with a file and position. See the [CLI](/docs/v2/cli) and [Configuration](/docs/v2/configuration) reference. The keys that v2 itself removed along the way are listed under [Removed Keys](/docs/v2/configuration#removed-keys).

## From a Pre-release v2 Config

A `rogen.json` from a pre-release of v2 is not read either: Rogen says to rename it to `default.rogen.json`. Rogen's keys moved into one `rogen` block, and the keys that selected or multiplied outputs are gone.

| Pre-release | Now |
|---|---|
| `rogen.json` | `default.rogen.json` (or `.jsonc`). `X.rogen.json` writes `X.project.json` beside it |
| `sourcePaths`, `routes` at the top level | the same keys inside `"rogen": { ... }`. Rojo's keys stay at the top level |
| `syncPath`, `syncDir` | `compiledPath`, inside the `rogen` block |
| `projects` | a second complete `<name>.rogen.json` per project, repeating `name`, `routes` and `tree` |
| `serveProject` | removed. `rogen serve dist` names the file to serve; a bare `rogen serve` serves `default` |
| `placePaths` | removed. A place is a folder with its own complete `default.rogen.json`, served by naming it: `rogen serve places/lobby` |
| `extends` | removed. Files do not read each other: repeat the keys in each file |
| a place's ports, computed from its index | removed. Rogen writes and chooses no port; a second place served at once takes `--port` |

A config that still has one of these keys is an error that names its replacement ([`config.removedField`](/docs/v2/diagnostics#config-removedfield), [`config.rogenKeyOutsideBlock`](/docs/v2/diagnostics#config-rogenkeyoutsideblock)).
