v2 doesn't read v1's config or most v1 file names, and every command stops with [`legacy.config`](/docs/v2/diagnostics#legacy-config) while a v1 config is in the folder. To migrate, write a new config with `rogen init`, then rename files until `rogen check` is clean.

## Why v2 Changed

v1 placed a file by many small rules that could disagree, often without a warning, and each problem got its own switch or marker file. v2 replaces them with rules that hold everywhere.

**The outermost route governs.** In v1 the deepest rule won, so a suffix could override its folder: `ReplicatedFirst/main.client.luau` went to `StarterPlayerScripts`. Because any deeper rule could move a file, v1 needed the `.structure` and `.sync` markers to hold a folder still. In v2 a folder's route covers everything inside it, with no marker, and the routes below it are ignored.

**Only `@` routes a name.** v1 read routes from prefixes and from suffixes after almost any separator, so ordinary names matched by accident: `HttpClient.luau` went to the client as `Http`. Keeping a keyword in a name took `verbatim` or a `.verbatim` marker. In v2 a name routes only with `@`, as in `Save@server.luau`: this name, at that place. Rojo's `.server` and `.client` keep their meaning.

**You write every route.** v1's keywords and wrapper folders were built in, so changing them took `aliases`, `casing`, `unwrap` and `.unwrap`. Files that matched nothing went to `ReplicatedStorage`, where server code could reach clients. In v2 a route is a key and a target path that you write, such as `"Shared": "ReplicatedStorage/Shared"`, and the target can be any path under a service that Rojo writes to. Only declared routes exist, and a file that matches none is left out with a warning.

The config itself is a Rojo project file with three more keys, so Rojo's documentation covers the rest of it.

## Move a Project to v2

<Steps>

<Step>
### Set the v1 Config Aside

Rename `.rogen.json`, and any other `*.rogen.json` that v1 read, so v2 skips it and you can compare against it:

```bash
mv .rogen.json .rogen.json.v1
```

</Step>

<Step>
### Run `rogen init`

[Install v2](/docs/v2/installation), then run:

```bash
rogen init
```

It writes `default.rogen.json` and lifts an existing `default.project.json` into it. Rogen owns `default.project.json` from then on, so run the `git rm --cached` command that `init` prints.

</Step>

<Step>
### Match Your Old Paths

v1 put a wrapper folder under each service. To keep your v1 `require` paths, write the wrappers into the targets:

```json title="default.rogen.json"
{
	"routes": {
		"server": "ServerScriptService/server",
		"client": "StarterPlayer/StarterPlayerScripts/client",
		"shared": "ReplicatedStorage/shared",
		"*": "ReplicatedStorage/shared"
	}
}
```

Leave the wrappers out if you used `unwrap`, or capitalise them if you used `casing: "PascalCase"`. Add each of your `aliases` as a route.

</Step>

<Step>
### Rename Files Until `rogen check` Is Clean

```bash
rogen check
```

Each v1 name that no longer routes gets a warning that names the fix, and `--json` lists the renames. Run `rogen write` when `check` asks. The step is done when `rogen check` prints nothing and exits 0. Files that v1 built only under a tag get no warning, so move them as [Tags](#tags) describes.

</Step>

<Step>
### Compare With Your v1 Build

Run `rogen serve` and compare Studio's Explorer with your v1 build. When every script sits where it did, delete `.rogen.json.v1`.

</Step>

</Steps>

## What Replaces Each v1 Feature

| v1 | v2 |
|---|---|
| `source`, `-s` | `sourcePaths` |
| `aliases`, built-in keywords | `routes` |
| `casing`, `unwrap`, `.unwrap` | the route's target path |
| `verbatim`, `.verbatim` | not needed |
| keywords in names | `@key` or a routing folder. See [Names](#names) |
| `tags`, `-t` | an overlay source path. See [Tags](#tags) |
| modes, `-m` | a second config, such as `dist.rogen.json` (`rogen serve dist`) |
| a mode's `build`, `-b` | `compiledPath` |
| a mode's `output`, `-o` | none. `rogen build -o` now builds a place |
| `project`, `template`, `-p` | `tree` in the config. `-p` now builds a plugin |
| `.structure` | a marker file such as `@shared` |
| `.sync` | a plain `$path` node in the `tree` |
| `^` at the service's root | `^` at the route's target, which includes any wrapper folder you kept |
| several places from one config | a folder per place, each with its own `default.rogen.json` |

### Names

A [routing folder](/docs/v2/core-concepts/routing#routing-folders) is often the better choice:

```
v1: src/Combat/server_Combat.luau     v2: src/Combat/Server/Combat.luau
v1: src/Combat/Combat_Server.luau     v2: src/Combat/Combat@server.luau
v1: src/Combat/Types.shared.luau      v2: src/Combat/Types@shared.luau
v1: src/Combat/Hud.client.luau        v2: unchanged
v1: src/Combat/Gun.server.rbxm        v2: src/Combat/Gun@server.rbxm
v1: src/Combat/.server                v2: src/Combat/@server
```

Marker files, models and data files take `@`, because Rojo reads `.server` only on a script.

### Tags

Few projects used tags. A file that v1 built only while a tag was on moves to an **overlay source path**, a folder that only the configs that want it list. A file there replaces its twin in an earlier source path, or is added:

```
v1: src/Teleport/TeleportDev.luau (tag dev)
v2: dev/Teleport/Teleport.luau (the dev source path)
```

List the overlay in `default.rogen.json`, and write a second config without it, such as `release.rogen.json` with `"sourcePaths": ["src"]`. The second config needs its own `name`, because Rojo crashes on a project file other than `default.project.json` that has none.
