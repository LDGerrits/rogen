title: Requires
description: How code in one feature folder reaches code that runs somewhere else.
---

import { Callout } from "fumadocs-ui/components/callout";

A feature folder keeps its files side by side on disk, but in the game they end up in different services:

```
src/Inventory/Server/InventoryService.luau  ->  ServerScriptService/Inventory/InventoryService
src/Inventory/Shared/InventoryTypes.luau    ->  ReplicatedStorage/Shared/Inventory/InventoryTypes
```

A `require` runs in the game, so it resolves against the **instance tree**, not your folders. `InventoryService` can't reach `InventoryTypes` as a sibling, because in the game it isn't one. How you write the require depends on your setup.

<Tabs items={["Luau", "Luau with Darklua", "roblox-ts"]} groupId="language" persist>
  <Tab value="Luau">
    Require by instance path:

    ```luau title="src/Inventory/Server/InventoryService.luau"
    local ReplicatedStorage = game:GetService("ReplicatedStorage")
    local InventoryTypes = require(ReplicatedStorage.Shared.Inventory.InventoryTypes)
    ```

    luau-lsp resolves these through the sourcemap it generates from `default.project.json`, so types, completion and go-to-definition all follow the require to the right file.

    Relative string requires also resolve against the instance tree, so `./` only reaches files that end up in the same folder in the game. `require("./InventoryData")` from `Server/InventoryService.luau` works if `InventoryData.luau` is in `Server/` too. A require that crosses into another service doesn't.
  </Tab>
  <Tab value="Luau with Darklua">
    Write requires as paths on disk, and let Darklua's `convert_require` rule rewrite them into instance requires:

    ```luau title="src/Inventory/Server/InventoryService.luau"
    local InventoryTypes = require("../Shared/InventoryTypes")
    ```

    ```json title=".darklua.json"
    {
    	"rules": [
    		{
    			"rule": "convert_require",
    			"current": { "name": "path" },
    			"target": {
    				"name": "roblox",
    				"rojo_sourcemap": "./sourcemap.json",
    				"indexing_style": "property"
    			}
    		}
    	]
    }
    ```

    Darklua looks up each file in `sourcemap.json` to find the instance it becomes. That's why `default.project.json` points at your source, and why the sourcemap has to stay current as files move. See the [Darklua guide](/docs/v2/setups/darklua).
  </Tab>
  <Tab value="roblox-ts">
    Import by file path:

    ```ts title="src/Inventory/server/InventoryService.ts"
    import { InventoryTypes } from "../shared/InventoryTypes";
    ```

    `rbxtsc` reads the project file to turn each import into an instance require, so the compiled code finds `ReplicatedStorage` no matter where the file sits on disk. Keep `rogen watch` running next to `rbxtsc -w` so the project file is up to date before it compiles.
  </Tab>
</Tabs>

A file routed with `@` keeps the `@` on disk but not in the game. An instance require uses the game name, `InventoryService`. A path, with Darklua or roblox-ts, uses the file name, `@` and all: `require("./InventoryService@server")`.

## What Each Side Can See

Where a file lands decides who can require it. Shared code in `ReplicatedStorage` runs on both sides, so it can't require anything only the server can see, like `ServerScriptService` or `ServerStorage`. Two files in the same feature folder can end up on sides that can't see each other, so check where a file lands before you require it.

<Callout type="info" title="Find the instance path of a file">
	`rogen where <file>` prints the instance path a file lands at, even for a file you haven't created yet. It works the other way too: `rogen where ServerScriptService.Inventory.Save` prints the file behind an instance.
</Callout>
