Each **build** turns your source paths into one **project**: the Rojo project file for a `rogen.json`. This page covers that file and how its paths find your code.

## Output

The output is always `default.project.json`, beside the `rogen.json` that describes it. It is a plain Rojo project file: Rogen's keys are gone, your `tree` has the routed nodes merged in, paths are relative to the file, and it is formatted as `rojo fmt-project` formats it. It carries a `$schema` that says it was written from `rogen.json`, and `name` only when `rogen.json` sets one. Rojo names the project after its folder otherwise.

Every other Rojo key in `rogen.json` (`servePort`, `servePlaceIds`, `globIgnorePaths` and the rest) is copied across, so the tools that read the file see them.

**Rogen owns the output.** Every build replaces the file, hand-written or not, so anything Rogen can't know about goes in the [`tree`](/docs/v2/configuration#tree) of `rogen.json`. When nothing has changed, the file is left untouched, so Rojo doesn't re-sync for no reason.

A bare `rojo serve`, `rbxtsc` and luau-lsp's sourcemap all use `default.project.json`, so they read the file Rogen writes with nothing to configure.

### Commit the project file

Commit `default.project.json`. The cost shows up on a fresh clone, where nothing has run `rogen build` yet:

- **Committed:** the clone works at once. `rojo serve`, `rbxtsc`, luau-lsp's sourcemap and the Rojo plugin for VS Code all find the file. CI can run `git diff --exit-code -- default.project.json` after `rogen build` to catch a stale one (see [Continuous integration](/docs/v2/cli#continuous-integration)), and `rogen check` warns when the file on disk differs from what `build` would write ([`output.differs`](/docs/v2/diagnostics#output-differs)). The file is small and deterministic. The price is a merge conflict now and then in a generated file, fixed by running `rogen build`.
- **Ignored:** the file never conflicts, but on a clone `rojo serve` fails until someone runs `rogen build` (`rogen serve` builds first, so it works). So does `rbxtsc`, which reads the project file, and luau-lsp and the Rojo plugin find nothing. New contributors and CI hit this first, so put `rogen build` before `rojo serve` or `rbxtsc` in your setup instructions.

## Sync Path

With a compiler, Rojo syncs from its output instead of your source. That folder is the **sync path**, set by `syncPath`: typically `out` for roblox-ts and `dist` for Darklua. Rogen still reads your source to decide where things go, but writes paths into the sync path, with `.ts` and `.tsx` turned into `.luau`. Plain Luau doesn't need one.

  </Tab>
</Tabs>

With one source path, `syncPath` simply takes its place. With several, Rogen keeps each path relative to their **common root**, the deepest folder containing all of them, just like `tsc` does. For `["core", "places/lobby"]` that's the repo root, so paths land at `dist/core/…` and `dist/places/lobby/…`. `rogen list --json` shows the common root.

A few things to keep in mind:

- `syncPath` only affects paths Rogen generates. `tree` paths like Wally's `Packages` are copied through untouched.
- Rojo syncs from the sync path, and there is one project file. The one you serve is the one luau-lsp and Darklua read, so its `$path`s point into the sync path, not into your source. See the [Darklua guide](/docs/v2/setups/darklua).
- If none of the paths Rogen writes for a source path exist after a build, Rogen warns and suggests the closest match. Usually the compiler just hasn't run yet.
- Rogen never reads the sync path, so compiled leftovers whose source is gone still sync. Clean it as part of your compile step.

## Serving

`rogen serve` builds, starts Rojo on `default.project.json`, and rebuilds as `watch` does. Rojo reads the port from the project file, so a `servePort` in `rogen.json` applies. When a Rojo you started yourself already serves the project, `serve` builds for it instead of starting another. See [`serve`](/docs/v2/cli#serve) for which Rojo runs, the port, `--json` and exit codes.

## Place Files

Rogen writes the project file, not the place file. To get an `.rbxl` or `.rbxm` for publishing or a test run, build the project file with Rojo:

```bash
rogen build
rojo build default.project.json -o game.rbxl
```

Rojo, and not Rogen, runs the second command, and `rogen build` needs no Rojo to run. Which Rojo version builds the file is yours to pin in `rokit.toml`.

With [Darklua](/docs/v2/setups/darklua) or roblox-ts, run the compiler first, so the place holds the compiled code the `syncPath` points at.

A place that differs from your default build, such as one with the specs in it, comes from a `rogen.json` of its own in another folder. See [Testing](/docs/v2/testing).

## Building While Watching

It's safe to run `rogen build` while `rogen watch` or `rogen serve` writes the same file, so you can always run a build after moving files and trust the result. What a build writes depends only on your files and config, so it matches what the running command writes.
