A **write** writes the **project file** of one config: a Rojo project file, beside the `.rogen.json` it comes from. This page covers that file and how its paths find your code.

## Output

A config named `X.rogen.json` writes `X.project.json` beside it, the way Rojo names project files, and `default.rogen.json` writes `default.project.json`. A second project, such as a Darklua build or a release without the specs, is a second complete config with its own project file. See [Configuration](/docs/v2/configuration#more-files).

The project file is a plain Rojo project file: Rogen's keys are gone, your `tree` has the routed nodes merged in, paths are relative to the file, and it is formatted as `rojo fmt-project` formats it.

`default.project.json` carries `name` only when the config sets one. Rojo names the project after its folder otherwise. Every other project file carries a `name`, the config's or the file's stem, since Rojo can't open a project file without one.

Every other Rojo key in the config (`servePort`, `servePlaceIds`, `globIgnorePaths` and the rest) is copied across, so the tools that read the file see them.

**Rogen owns the project file.** Every build replaces it, so anything Rogen can't know about goes in the [`tree`](/docs/v2/configuration#tree) of the config. When nothing has changed, the file is left untouched, so Rojo doesn't re-sync for no reason. `build` says `wrote` when it replaced a file with different content. A `*.project.json` that has a `.rogen.json` beside it is overwritten by every build, so an edit made to it by hand is lost: edit the `.rogen.json`, whose `tree` holds what names can't express. A `*.project.json` with no `.rogen.json` beside it is a plain Rojo project, and Rogen runs it as it is and writes nothing to it.

A bare `rojo serve`, `rbxtsc` and luau-lsp's sourcemap all use `default.project.json`, so they read the file Rogen writes with nothing to configure.

### The project file is as fresh as its last write

A Rojo command writes only the file it is given. `rogen serve dist` writes `dist.project.json` and serves it, and `rogen build release -o game.rbxl` writes `release.project.json`. Nothing else is written, so `default.project.json` is as fresh as your last `rogen write`. `rogen serve` and `rogen write --watch` keep the file they write current while they run.

**A stale file loads without complaint.** Every `$path` Rogen writes is `optional`, since a compiler's or Darklua's output may not exist yet and a file can go while `serve` is running. So when a source file is renamed and `rogen write` has not run, Rojo builds a place without it and does not fail. Run `rogen write` before `rojo`, the editor or the compiler. After you add a feature folder, or a file with an `@key` name, run it so they read the new file; a file added to a folder that is already mounted whole needs nothing.

`rogen check` reports a project file that differs from what a write would make, as [`output.differs`](/docs/v2/diagnostics#output-differs) with no path, and `write` writes it again.

### Ignore or commit the project files

`rogen init` writes `*.project.json` into the `.gitignore` it creates, beside `sourcemap.json`, and Rogen never edits one that exists. Whether the files it writes are committed is yours to decide.

- **Ignored:** `*.project.json` and `sourcemap.json`, as Wally's `Packages/` is listed. The files are generated and regenerated by one command, so they never conflict, and a script does not change a committed file every time it is added. After a clone, `rogen write` writes `default.project.json`, and CI runs it before `rojo build`; `rogen serve` writes first on its own. On a clone, `rojo serve` and `rbxtsc` find no project file until someone has run it, and nor do luau-lsp and the Rojo plugin, so put `rogen write` first in your setup instructions. The pattern also hides project files you write by hand: add `!name.project.json` to keep one tracked.
- **Committed:** a clone works at once, for a repo whose collaborators or CI do not install Rogen. `rogen check` warns when the file on disk differs from what `write` would make ([`output.differs`](/docs/v2/diagnostics#output-differs)), committed or not, and CI can run `git diff --exit-code -- '*.project.json'` after `rogen write`. Remove `*.project.json` from `.gitignore` for this. The price is a merge conflict now and then in a generated file, fixed by running `rogen write`.

## Compiled Path

With a compiler, Rojo syncs from its output instead of your source. That folder is the **compiled path**, set by `compiledPath`: typically `out` for roblox-ts and `dist` for Darklua. Rogen still reads your source to decide where things go, but writes paths into the compiled path, with `.ts` and `.tsx` turned into `.luau`. Plain Luau doesn't need one.

<Tabs items={["Luau", "roblox-ts"]} groupId="language" persist>
  <Tab value="Luau">
    Darklua processes `src` into `dist`, so with `"compiledPath": "dist"`:

    ```
    src/Inventory/Server/Save.luau  ->  $path: dist/Inventory/Server/Save.luau
    ```
  </Tab>
  <Tab value="roblox-ts">
    `rbxtsc` compiles `src` into `out`, so with `"compiledPath": "out"`:

    ```
    src/Inventory/server/Save.ts  ->  $path: out/Inventory/server/Save.luau
    ```
  </Tab>
</Tabs>

With one source path, `compiledPath` simply takes its place. With several, Rogen keeps each path relative to their **common root**, the deepest folder containing all of them, just like `tsc` does. A place `places/lobby` with `["../shared/src", "src"]` and `"compiledPath": "out"` reads `out/shared/src/…` and `out/lobby/src/…`, which is what a compiler listing both folders writes. Adding a source path can change the common root, and so the layout.

A few things to keep in mind:

- `compiledPath` only affects paths Rogen generates. `tree` paths like Wally's `Packages` are copied through untouched.
- Rojo syncs from the compiled path, but luau-lsp and Darklua read a sourcemap of your source. Keep `default.rogen.json` pointing at the source, and give the compiled path to a second config such as `dist.rogen.json`, which Studio serves with `rogen serve dist`. See the [Darklua guide](/docs/v2/setups/darklua).
- If none of the paths Rogen writes for a source path exist after a write, Rogen warns and suggests the closest match. Usually the compiler just hasn't run yet.
- Rogen never reads the compiled path, so compiled leftovers whose source is gone still sync. Clean it as part of your compile step.

## Serving

`rogen serve` writes the project it is given, starts Rojo on it, and writes again as `build --watch` does. With no argument that is `default.rogen.json` of the current folder, so in a Darklua setup a bare `rogen serve` serves your source and `rogen serve dist` serves the processed code. Rojo reads the port from the project file, so a `servePort` in the config applies. When a Rojo you started yourself already serves the project, `serve` builds for it instead of starting another. See [`serve`](/docs/v2/cli#serve) for which Rojo runs, the port, `--json` and exit codes.

## Place Files

Rogen writes the project files, and `build -o` has Rojo make a place or model file from one of them, as `rojo build` does:

```bash
rogen build -o game.rbxl
```

It writes the project file first and then runs the Rojo your tool manager's file (`rokit.toml`, `aftman.toml` or `foreman.toml`) pins on it, so the place always matches the file.

Name another config to build that one: a place that differs from your default build, such as one with the specs in it or without the dev packages, is a second config file, built with `rogen build release -o game.rbxl`. See [Testing](/docs/v2/testing).

`-p Tool.rbxm` builds a plugin into Roblox's plugins folder, and `rogen upload` uploads the place.

`rogen build` needs `-o` or `-p`, as `rojo build` does; to write the project files without building, run `rogen write`, and `rojo build default.project.json -o game.rbxl` after it works the same.

With [Darklua](/docs/v2/setups/darklua) or roblox-ts, run the compiler first, so the place holds the compiled code the `compiledPath` points at.

## Writing While Watching

It's safe to run `rogen write` while `rogen write --watch` or `rogen serve` writes the same file, so you can always run a write after moving files and trust the result. What a write makes depends only on your files and config, so it matches what the running command writes.
