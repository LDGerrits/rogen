Each **build** turns your root directories into one **output**: the Rojo project file for a config. This page covers that file and how its paths find your code.

## Output

The output is set by `outFile` and named after the config by default, so `lobby.rogen.json` writes `lobby.project.json`. `outFile` isn't inherited, so every config writes its own file. Need a second project file? Add a second config.

**Rogen owns the output.** Every build replaces the file, hand-written or not, so anything Rogen can't know about goes in the [template](#template). When nothing has changed, the file is left untouched, so Rojo doesn't re-sync for no reason.

<Callout type="info" title="The default output is the one tools find">
	A bare `rojo serve` and luau-lsp's sourcemap both use `default.project.json`. With Darklua they need different files, so `default` points at your source and `sync.project.json` is the one served, which `rogen serve` picks on its own. See the [Darklua guide](/docs/v2/setups/darklua).
</Callout>

### Commit the project file

Commit the project files Rogen writes. The cost shows up on a fresh clone, where nothing has run `rogen build` yet:

- **Committed:** the clone works at once. `rojo serve`, `rbxtsc`, luau-lsp's sourcemap and the Rojo plugin for VS Code all find the file. CI can run `git diff --exit-code -- '*.project.json'` after `rogen build` to catch a stale one (see [Continuous integration](/docs/v2/cli#continuous-integration)). The file is small and deterministic. The price is a merge conflict now and then in a generated file, fixed by running `rogen build`.
- **Ignored:** the file never conflicts, but on a clone `rojo serve` fails until someone runs `rogen build` (`rogen serve` builds first, so it works). So does `rbxtsc`, which reads the project file, and luau-lsp and the Rojo plugin find nothing. New contributors and CI hit this first, so put `rogen build` before `rojo serve` or `rbxtsc` in your setup instructions.

## Template

The **template** is a Rojo project file that Rogen merges its tree into. It holds what Rogen can't know: the DataModel name, package mounts and `$properties`. Without one, Rogen starts from an empty `DataModel` named after the config's folder.

- If the template and the generated tree define the same instance, the template wins and Rogen warns. A `$path` below a service, like a package mount, owns that whole folder.
- A `$path` that points inside a root directory hands that path to Rojo. Rogen skips it entirely and `rogen where` reports it as `mounted`, which is how you sync a vendored library as-is. Mounting a root directory itself, a folder above one, or something inside an init folder is an error.
- An `exclude` glob that matches a `$path` drops the node, so a [mode](/docs/v2/core-concepts/modes#template-nodes) can leave a mount such as `DevPackages` out of prod.
- A child config's `template` replaces its parent's.

`rogen init` writes a template when it finds packages to mount, or keeps your hand-written project file as one.

## Sync Directory

With a compiler, Rojo syncs from its output instead of your source. That folder is the **sync directory**, set by `syncDir`: typically `out` for roblox-ts and `dist` for Darklua. Rogen still reads your source to decide where things go, but writes paths into the sync directory, with `.ts` and `.tsx` turned into `.luau`. Plain Luau doesn't need one.

<Tabs items={["Luau", "roblox-ts"]} groupId="language" persist>
  <Tab value="Luau">
    Darklua processes `src` into `dist`, so with `"syncDir": "dist"`:

    ```
    src/Inventory/Server/Save.luau  ->  $path: dist/Inventory/Server/Save.luau
    ```
  </Tab>
  <Tab value="roblox-ts">
    `rbxtsc` compiles `src` into `out`, so with `"syncDir": "out"`:

    ```
    src/Inventory/server/Save.ts  ->  $path: out/Inventory/server/Save.luau
    ```
  </Tab>
</Tabs>

With one root directory, `syncDir` simply takes its place. With several, Rogen keeps each path relative to their **common root**, the deepest folder containing all of them, just like `tsc` does. For `["core", "places/lobby"]` that's the repo root, so paths land at `dist/core/…` and `dist/places/lobby/…`. `rogen list --json` shows the common root.

A few things to keep in mind:

- `syncDir` only affects paths Rogen generates. Template paths like Wally's `Packages` are copied through untouched.
- If none of a root directory's paths exist after a build, Rogen warns and suggests the closest match. Usually the compiler just hasn't run yet.
- Rogen never reads the sync directory, so compiled leftovers whose source is gone still sync. Clean it as part of your compile step.

### One Tree, Two Renderings

To write the same tree with paths into a different folder, add a config that `extends` the first and sets a `syncDir`. Each of these project files is a **rendering**. That's how a Darklua setup gets one project file for your editor and another for Studio.

## Serving

`rogen serve` builds every config, starts Rojo or Argon on each rendering no other config extends, and rebuilds as `watch` does. With Darklua that's `sync.project.json`; in a multi-place repo, each place. The server reads the port from the project file, so a `servePort` in the template applies. See [`serve`](/docs/v2/cli#serve) for which server runs, the port, `--json` and exit codes.

## Building While Watching

It's safe to run `rogen build` while `rogen watch` or `rogen serve` writes the same file, so you can always run a build after moving files and trust the result.
