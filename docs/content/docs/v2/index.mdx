A bad folder structure slows you down. You spend effort remembering where the related pieces live, and time hunting for them.

## The Problem: Technical Grouping

Most Roblox codebases group files by what kind of code they are rather than what they're about. This is **technical grouping**, and it shows up in two forms:

1. **By type:** a folder per technical role, like `Controllers`, `Services` and `Utils`. Every industry does this, and it's a well-known anti-pattern.
2. **By runtime, at the root:** `server`, `client` and `shared` at the top of the tree. Rojo maps folders one-to-one onto instances, so Roblox tooling pushes you into this one. It's the form Rogen removes.

Either way, a single feature ends up scattered across the tree. To change the **Inventory** system you search three folders for its pieces, and to delete it you have to find every one of them.

David Parnas called this a mistake back in 1972. Modules, he argued, should hide design decisions instead of following the order the program runs in:

> Since, in most cases, design decisions transcend time of execution, modules will not correspond to steps in the processing.
>
> — D. L. Parnas, [_On the Criteria To Be Used in Decomposing Systems into Modules_](https://wstomv.win.tue.nl/edu/2ip30/references/criteria_for_modularization.pdf) (1972)

On Roblox, _where code runs_ is one of those steps. A feature has server, client and shared code, so the feature should be the module, and where each piece runs is a detail inside it.

## The Solution: Package by Feature

Put all the code for one feature (client, server and shared) in a single **feature folder** named after what it does in your game. This is **package by feature**, and domain-driven design says the same thing: name modules after the concepts in your domain (`Trading`, `Quests`), not after technical roles.

Rogen reads your folders and file names and generates a Rojo **project file** that puts every script in the Roblox **service** where it needs to run. It doesn't sync anything itself. Rojo or Argon reads that project file and syncs your code into Studio.

The **routes** in your [config](/docs/v2/configuration) say where each kind of code goes:

```json title="default.rogen.json"
{
	"routes": {
		"Server": "ServerScriptService",
		"Client": "StarterPlayer/StarterPlayerScripts",
		"Shared": "ReplicatedStorage/Shared",
		"*": "ReplicatedStorage/Shared"
	}
}
```

<Callout type="info">
	**The result:** your repository stays organized by feature, and Studio still
	gets every script in the right container.
</Callout>

Feature folders are a good place to start, but not the only option. Layers work too, as long as dependencies point one way and each layer is split by feature. [Architectures](/docs/v2/architectures) compares the layouts that suit Rogen.
