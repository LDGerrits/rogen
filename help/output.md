# Output

Diagnostics print as `file:line:col - severity: message (code)`, on stderr, except those of `check`, which prints them on stdout; `rogen help <code>` explains the code. An error stops the config from being written. Warnings don't, and still name something to fix.

Exit codes: 0 done, warnings included (`check` exits 1 on any diagnostic about the paths it is given, or about the whole project, for CI); 1 the project has errors (an invalid config, build errors, a failed write, a cancelled init); 2 the command line is wrong (an unknown command, option or name, or a combination that isn't allowed). `rogen serve` exits 130 on Ctrl+C (143 on SIGTERM, 129 on SIGHUP), and with the server's code when a server stops on its own; it exits 0 when another `rogen serve` already serves the project. `--json` keeps the same codes.

Under GitHub Actions, `build` and `check` also write each diagnostic as a workflow command on stderr (`::warning file=src/Save@sever.luau,title=route.strayAt::did you mean "@Server"?`), one per file for a warning about several; never with `--json`.

When a person runs Rogen in a terminal and a newer stable release is out, one line on stderr after the command names the fix for how Rogen was installed: the pin in `rokit.toml`, `aftman.toml` or `foreman.toml` and the install command to run after, an `npm i` command (`npm i -g` for a global install), or the release. `watch` and `serve` print it before their first build. A prerelease also hears about later prereleases. It is never printed under CI or an agent, in a pipe, with `--json` or `--quiet`, or for `--version` and `help`, and names a version once a day. GitHub's list of releases is read in the background once a day and kept in the user's cache folder (`$XDG_CACHE_HOME`, `~/Library/Caches` or `%LOCALAPPDATA%`); the line comes from the last check, and a command that ends before a check does stays open for it two seconds at most. `ROGEN_NO_UPDATE_CHECK=1` or `NO_UPDATE_NOTIFIER=1` turns the request and the line off.

Plain lines (in pipes, CI and under an agent) put results on stdout and warnings, errors, diagnostics and `--verbose` debug lines on stderr. `--json` on `build`, `sourcemap`, `upload`, `where`, `check`, `init`, `fmt-project`, `doc` and `help` prints one JSON document on one line of stdout, whatever the exit code, and nothing else. `serve --json` prints one JSON object per line instead, what the server says included, and so do `build --watch --json` and `sourcemap --watch --json`. Read them instead of parsing text.

`rogen help --json` lists the commands with their arguments, options and what each does beyond printing (`writesFiles`, `runsProcesses`, `opensBrowser`, `longRunning`; none is read-only), and the exit codes and error kinds. `rogen help <command> --json`, or `rogen <command> --help --json`, adds the descriptions, the examples and the shape of the command's document: `output` in a compact notation where `{a:string,b?:int}` is an object with an optional key, `[T]` an array, `A|B` either, `{*:T}` an object of any keys and a capitalised name a shape written out under `shapes`. `rogen help <code> --json` prints `{ "code", "text", "url" }`, and `rogen help codes --json` lists every code with its severity and meaning. What follows is what the keys mean.

- The commands that write, `build`, `fmt-project`, `init`, `sourcemap`, `syncback` and `upload`, start their document with `changed`, true when the run wrote anything, and give each file an `outcome` of `wrote`, `unchanged`, `failed` or `notWritten` (`wouldWrite` in a dry run).
- `build --json`: one entry for the config it ran, with `file` (the `.rogen.json`) and `projectFile` (the project it writes), where `outcome` is `wrote`, `unchanged` or `notWritten`. A config that doesn't load is an entry too, with `projectFile` null and its errors in `diagnostics`; a config not written because others failed or didn't load has `blockedBy`, their names. With `-o` or `-p`, `rojo` holds Rojo's build, where `outcome` is `built`, `failed` or `notRun`.
- `sourcemap --json`: `configs` as in `build`, and `sourcemaps`, one entry per run of Rojo shaped as `rojo` in `build --json` with `command` `sourcemap`, where `outcome` is `built` when the file was written. It needs `-o`, since the sourcemap is what a plain run prints.
- `upload --json`: `configs` as in `build`, and `rojo`, shaped as in `build --json` with `command` `upload`, where `outcome` is `built` when Rojo exited without an error. The flags you gave are not in it.
- `syncback --json`: `configs` as in `build`, and `syncback`, with `outcome` `written`, `planned` (a dry run), `failed` or `notRun`; `changes`, the files written and removed, each with its `kind`; and `unplaced`, the instances of the place no folder could take, each with its `reason`.
- `where --json`: one entry per config and path; the `diagnostics` at the top hold the errors of a config that didn't load. `exists` says whether the path is there now or only placed as it would be once created; a placed Luau module has `require`, the expression that reaches it (none under the Starter containers, for scripts or for roblox-ts). The `diagnostics` of an entry are what a build would raise about that path, narrowed to it.
- `check --json`: the diagnostics about the given paths (about the whole project with none), each once; exit 1 when there are any.
- `serve --json`: one line per event, keyed by what it reports. `build` per config per build, shaped as a `build --json` entry; `notice` when a config is added, removed, broken or recovered; `serving` once Studio can connect (after the first build that succeeds: when the first build fails, `serve` keeps watching and prints it later; `reportsConnections` says whether `connected` and `disconnected` lines follow when a Studio plugin connects or leaves; Rojo 7.7+ only), with `alreadyRunning` when a server already served the project; `output` for each warning, error or unrecognised line the server prints (the rest of its output is dropped); `refused` when a config added or edited while serving can't be served because its port is taken (the server it already has, if any, goes on); `stopped` when a server stops, with a `reason` that is `exited` (on its own, with `code` and `signal`), `removed` or `moved` (its config was deleted, or moved to another address), or `shutdown` (serve was asked to stop, the last line of a clean run). A failed run ends with a failure document.
- `fmt-project --json`: one entry per file; exit 1 when any failed.
- `doc --json`: the address and the topics, or the text of one topic.
- `init --json`: the `files` it wrote (`appended` when it added to a file that existed), the `directories` it created (source paths that didn't exist), `decided` (each choice it took without being asked, with the flag that changes it), its notes, and its `nextSteps`. `init --dry-run --json` prints it without writing or building: `dryRun` is true, `changed` false, and each file's `outcome` is `wouldWrite`. Every question has a flag (`rogen help init` lists them).
- A command that fails before it has anything else to show prints `{ "diagnostics": [...] }` or `{ "error": { "kind", "message", "hint"? } }`, never both. `kind` is `usage` (exit 2), `project`, `tool`, `io`, `cancelled` or `internal` (exit 1 each); `hint` names the one next step when there is one.

An entry that is a config has `config` (its project name) and `file` (the absolute path of its `.rogen.json`); an entry that belongs to a config has `config`. Identity comes first and `diagnostics` last.

Each JSON diagnostic has `file`, `line` and `column` (when it has a position), `severity`, a stable `code` to match on, `message`, and a `url` to the code's docs. `rogen help <code>` prints the same section offline. A diagnostic whose fix is one rename has `fixes`: `[{ "rename": { "from", "to" } }]`, one for every name it covers. Rogen never applies them; after a rename, update the requires and imports that name the file. An unknown config key or route target with a close match has `[{ "replace": { "file", "line", "column", "from", "to" } }]`: the JSON text at that position and its replacement. A `serve` error whose fix is a command has `[{ "run": { "command", "cwd" } }]` instead; Rogen never runs it. A warning about several files has `related`: `[{ "file", "message" }]`, one for every file, uncapped (the text stops at ten). A diagnostic is about a file when its `file` is that file or `related[].file` includes it.

`rogen where` is `write`'s dry run: it computes the same tree and writes nothing, so it shows where a file lands, and why a file is left out (replaced, ignored, displaced or mounted), before you build. It prints the warnings a build would raise about each path under its line, except the compiled path's. With nothing in the source paths it says so, and a missing path named with a trailing separator says to name a file in it.

`rogen check <paths>` is `where`'s verdict: it prints only the diagnostics about the paths (a clean path prints nothing), writes nothing and exits 1 on any; with no path it reports every `.rogen.json` of the folder whole, the compiled path's warnings included, and each project file on disk that differs from what `write` would write.

`rogen write` is safe beside a running `rogen write --watch` or `rogen serve`: it writes only bytes that changed.
